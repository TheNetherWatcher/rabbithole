Every word a model writes leaves behind a little memory: keys and values for each layer, stored on the GPU so the next word can look back. That's the KV cache. Here is the space for it, cut into 16 blocks of 4 token slots.

The old way. Request A arrives with a 7-token prompt. Nobody knows how long the answer will be, so the server reserves room for the longest possible one: a single slab of 8 blocks.

7 of its 32 slots hold anything. The striped ones are paid for and empty.

Request C takes blocks 11–13. Now Request B needs 4 blocks in a row.

Five blocks are free, but they're split 3 + 2. B waits, with free memory sitting right there. This is how servers ended up using 20–38% of their KV memory.

The paged way, borrowed from how operating systems have managed RAM since 1962. Hand out memory one small block at a time, from anywhere.

A's 7 tokens land in block #7 and block #1. A tiny block table remembers the order: [7, 1].

A keeps talking. Token 8 fills the last slot of #1. Token 9 needs room, so the allocator grabs any free block, #3. Table: [7, 1, 3].

The only waste left is the unfilled tail of the last block. Never more than one block per request.

Request B shows up with the same opening 4 tokens (a shared system prompt). Its table just points at A's block #7: computed once, read twice, reference count 2.

If a shared block ever has to change, the writer copies only that block. That's copy-on-write.

More requests pour in and the pool fills completely. That's the goal: every block busy.

But A has just filled #3 and needs one more block. None is free.

The scheduler preempts the newest request, B, as a whole: its private blocks go back to the pool (block #7 stays, A still uses it). A takes #10 and carries on. B is recomputed from its tokens later.

Paging turned wasted memory into a scheduling problem, which is far cheaper.

Same GPU, same model. Contiguous servers kept real tokens in 20–38% of KV memory; vLLM keeps them in 96.3%. More conversations fit at once, so throughput rises 2–4×.
