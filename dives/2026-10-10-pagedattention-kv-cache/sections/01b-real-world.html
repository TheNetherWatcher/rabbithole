What it is

PagedAttention stores the KV cache in fixed-size blocks (16 tokens by default in vLLM) that can sit anywhere in GPU memory. A per-request block table maps logical blocks to physical ones, and the attention kernel follows it. Blocks are allocated one at a time as the sequence grows. They are refcounted so requests can share them (prefixes, parallel samples, beams) and copied only on write. It is OS paging applied to the KV cache, introduced by Kwon et al. at SOSP 2023 (arXiv 2309.06180).

Why it exists

  • The pain. FasterTransformer and Orca stored each request's KV as one contiguous tensor pre-allocated for max length. Measured utilization was 20.4%–38.2%; vLLM reached 96.3%.
  • Why it matters. Decode is memory-bound, so throughput is roughly proportional to batch size, and wasted KV memory means a smaller batch.
  • Payoff. 2–4× throughput at the same latency, with bigger gains for long sequences, big models and complex decoding.

How it's used

vllm serve meta-llama/Llama-3.1-8B-Instruct \
  --gpu-memory-utilization 0.90 \   # weights + activations + KV pool
  --max-model-len 8192 \            # longest sequence; caps blocks/request
  --block-size 16 \                 # tokens per KV block (default 16)
  --enable-prefix-caching \         # hash full blocks, reuse across requests (V1 default on)
  --kv-cache-dtype fp8              # halve KV bytes per token (optional)
from vllm import LLM, SamplingParams
llm = LLM(model="meta-llama/Llama-3.1-8B-Instruct",
          gpu_memory_utilization=0.9, max_model_len=8192)
# n=4 samples share the prompt's blocks via refcounts; only the tail block is copied
outs = llm.generate(["Write a haiku about rain."], SamplingParams(n=4, max_tokens=64))

Typical values: block 16 (vLLM) or 64–128 (TRT-LLM), memory utilization 0.85–0.95. At startup the engine profiles memory, then turns what's left into a fixed pool of KV blocks. The startup log line "# GPU blocks" is the capacity number to watch.

When to use it, when not to

Use it
  • Many concurrent, variable-length generations: chat, agents, batch inference, RAG.
  • Parallel sampling, beam search, shared system prompts.
  • It's the default everywhere, so the real choice is block size and prefix-cache policy.
Skip / reconsider
  • Single-stream batch-1 latency, where fragmentation is irrelevant and a dense contiguous kernel can win.
  • vAttention: contiguous virtual memory with on-demand physical pages through CUDA VMM, unmodified kernels, up to 1.23× throughput.
  • Warning signs: frequent preemption, low prefix-hit rate at block 128, KV full while compute sits idle.

Who should care

ML infra / serving: capacity, block size, preemption tuning. Backend: put stable prompt content first so prefix caching hits. Security: shared prefix caches are a cross-tenant timing channel. Kernel authors: every attention kernel must handle indirect, non-contiguous KV.
