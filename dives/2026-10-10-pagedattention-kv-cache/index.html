PagedAttention: KV-cache block tables, fragmentation, copy-on-write, preemption

TL;DR. An LLM's KV cache grows by one row per generated token, and nobody knows in advance how long the output will be. Pre-2023 servers reserved a contiguous max-length slab per request and used only 20–38% of it. PagedAttention splits the cache into fixed 16-token blocks placed anywhere in GPU memory, tracked by a per-request block table, allocated on demand, refcounted and copied only on write. The attention kernel follows the table and merges per-block softmax results exactly, so the output is unchanged and 96% of the memory holds real data.

Why it matters. Decode is memory-bandwidth-bound, so throughput scales with how many sequences fit in the batch. Packing KV well gave vLLM 2–4× throughput at the same latency, and every major open serving engine now pages its KV cache.

Explain it simply

Picture a busy restaurant with one long bench. When a party walks in, the host doesn't know how long they'll stay or how many friends will join later. So the cautious host blocks off enough bench for the biggest party that could possibly arrive, maybe 20 seats for a group of 3. The bench fills with empty "reserved" seats, and new guests wait outside while the room is two-thirds empty.

A large language model has the same problem with its working memory. While it writes an answer, it keeps a running notebook of everything said so far (the "KV cache"), and that notebook grows by one line per word. Older servers set aside one solid stretch of GPU memory per conversation, sized for the longest possible answer, and most of it sat empty. PagedAttention swaps the bench for small four-seat tables. A party gets one table, takes another when it fills up, and the tables don't have to be next to each other. A little card (the "block table") records which tables belong to which party. Nearly every seat ends up in use, so the GPU serves two to four times as many conversations at once.

Everyday example

Maya asks a chatbot: "Write a haiku about rain." That's 7 words of question. Tables seat 4, so her notebook needs 2 tables: table #7 holds words 1–4 and table #1 holds words 5–7, with one seat free. The model writes "Soft", which lands in that free seat. Now table #1 is full. When it writes "drops", the host grabs any free table (#3, across the room). Maya's card reads 7 → 1 → 3.

A minute later Maya's friend asks the same question with "give me two versions". Both versions share tables #7 and #1. Only when version 2 needs to write somewhere different does it get its own copy of the last table. When Maya finishes, her tables are wiped and handed to the next guest straight away.

Now the same thing, technically.

1 · Bare-minimum context

  • Autoregressive decoding. One token per forward pass; each attends to all previous tokens. (Vaswani 2017)
  • KV cache. Per-layer key/value vectors of past tokens, cached so they aren't recomputed. Grows one row per token. (HF docs)
  • Prefill vs decode. Prefill is the whole prompt in parallel and compute-bound. Decode is one token at a time and memory-bandwidth-bound, so throughput comes from batching. (DistServe)
  • Continuous batching. Requests join and leave the batch at every step. (Orca, OSDI'22)
  • OS virtual memory. Pages, page tables, copy-on-write fork(), swapping. (OSTEP)
  • GQA. Several query heads share one K/V head, which shrinks the KV cache. (Ainslie 2023)

1b · Real-world context

What it is

PagedAttention stores the KV cache in fixed-size blocks (16 tokens by default in vLLM) that can sit anywhere in GPU memory. A per-request block table maps logical blocks to physical ones, and the attention kernel follows it. Blocks are allocated one at a time as the sequence grows. They are refcounted so requests can share them (prefixes, parallel samples, beams) and copied only on write. It is OS paging applied to the KV cache, introduced by Kwon et al. at SOSP 2023 (arXiv 2309.06180).

Why it exists

  • The pain. FasterTransformer and Orca stored each request's KV as one contiguous tensor pre-allocated for max length. Measured utilization was 20.4%–38.2%; vLLM reached 96.3%.
  • Why it matters. Decode is memory-bound, so throughput is roughly proportional to batch size, and wasted KV memory means a smaller batch.
  • Payoff. 2–4× throughput at the same latency, with bigger gains for long sequences, big models and complex decoding.

How it's used

vllm serve meta-llama/Llama-3.1-8B-Instruct \
  --gpu-memory-utilization 0.90 \   # weights + activations + KV pool
  --max-model-len 8192 \            # longest sequence; caps blocks/request
  --block-size 16 \                 # tokens per KV block (default 16)
  --enable-prefix-caching \         # hash full blocks, reuse across requests (V1 default on)
  --kv-cache-dtype fp8              # halve KV bytes per token (optional)
from vllm import LLM, SamplingParams
llm = LLM(model="meta-llama/Llama-3.1-8B-Instruct",
          gpu_memory_utilization=0.9, max_model_len=8192)
# n=4 samples share the prompt's blocks via refcounts; only the tail block is copied
outs = llm.generate(["Write a haiku about rain."], SamplingParams(n=4, max_tokens=64))

Typical values: block 16 (vLLM) or 64–128 (TRT-LLM), memory utilization 0.85–0.95. At startup the engine profiles memory, then turns what's left into a fixed pool of KV blocks. The startup log line "# GPU blocks" is the capacity number to watch.

When to use it, when not to

Use it
  • Many concurrent, variable-length generations: chat, agents, batch inference, RAG.
  • Parallel sampling, beam search, shared system prompts.
  • It's the default everywhere, so the real choice is block size and prefix-cache policy.
Skip / reconsider
  • Single-stream batch-1 latency, where fragmentation is irrelevant and a dense contiguous kernel can win.
  • vAttention: contiguous virtual memory with on-demand physical pages through CUDA VMM, unmodified kernels, up to 1.23× throughput.
  • Warning signs: frequent preemption, low prefix-hit rate at block 128, KV full while compute sits idle.

Who should care

ML infra / serving: capacity, block size, preemption tuning. Backend: put stable prompt content first so prefix caching hits. Security: shared prefix caches are a cross-tenant timing channel. Kernel authors: every attention kernel must handle indirect, non-contiguous KV.

Technical deep dive

2 · The one-liner, and what it hides

"PagedAttention is virtual memory for the KV cache. It cuts fragmentation so you can batch more."
  1. The kernel changes. Softmax over scattered keys is computed block by block with exact global renormalization. The paper's kernel was 20–26% slower in isolation.
  2. Fragmentation drops but doesn't vanish. Internal waste is bounded to the last block, which trades block size against kernel efficiency and sharing granularity.
  3. On-demand allocation can run out mid-generation, which forces preemption (swap or recompute).
  4. Sharing is the second win (refcounts plus copy-on-write), and it's also a security hole.
  5. No MMU involved. Translation is a software table lookup inside the kernel, which is why vAttention exists.

3 · The problem

bytes/token = 2 · L · Hkv · dhead · s→ in plain terms: K and V, for every layer, every KV head and every head dimension, at s bytes each.

4 · Mental model

OS paging. Request = process. Token = byte. KV block = page. Block table = page table. Free pool = frame allocator. Parallel samples = fork() with copy-on-write. Preemption = swap-out.

Where it breaks. (1) No MMU or TLB: the kernel loads block_table[j] and computes addresses itself. (2) Every step reads every block, so there's no working set and you evict whole sequences, all or nothing. (3) KV can be recomputed instead of swapped (vLLM V1's default). (4) Blocks are append-only, so the last block is the only fragmentation.

5 · The mechanism, traced

The paper's Fig. 6 example, block size B = 4: Maya's 7-token prompt, then decode, then a second request with n=2.

Attention over scattered blocks

m, l, acc = -inf, 0.0, zeros(d)
for j, phys in enumerate(block_table):        # [7, 1, 3]
    K = kv_pool.K[layer, phys]                # (B, d), contiguous inside the block
    V = kv_pool.V[layer, phys]
    n = min(B, seq_len - j*B)                 # last block partially filled
    s = K[:n] @ q / sqrt(d)
    m_new = max(m, s.max())
    scale = exp(m - m_new)
    p = exp(s - m_new)
    l = l * scale + p.sum()
    acc = acc * scale + p @ V[:n]
    m = m_new
out = acc / l

Each warp reads one block, so loads are coalesced inside a block and only the jump between blocks is indirect.

Preemption and prefix caching

When the pool is full and a sequence needs a block, vLLM (FCFS) preempts the most recently arrived sequence group. Recompute (V1 default) frees all of its blocks and requeues it with prompt + generated. Swap (original paper) copies its blocks to a CPU block pool over PCIe. Groups are preempted together because they share blocks.

With automatic prefix caching, a finished request's full blocks keep their hash in an LRU free queue:

hash(block_k) = H(hash(block_{k-1}), token_ids_in_block_k, extra_keys)
extra_keys: LoRA id, multimodal hashes, cache_salt

Only full blocks are hashed, so a 7-token match reuses 4 tokens, not 7.

6 · The math

6.1 Footprint and batch size

T = M / b,   Ncontig = ⌊T / Lmax⌋,   Npaged ≈ T / E[ B·⌈ℓ/B⌉ ]→ in plain terms: contiguous pays for the worst case; paging pays for the actual average plus at most one block per sequence.

Back-of-envelope (not measured): A100-80GB, Llama-3-8B FP16, utilization 0.92, ~16 GB weights, ~2 GB activations, so M ≈ 55 GB and T ≈ 420k slots. With Lmax = 8192, contiguous fits 51 sequences; paged at mean length 700 fits about 590, before compute and max_num_seqs caps kick in.

6.2 Internal fragmentation

w = B·⌈ℓ/B⌉ − ℓ ∈ [0, B−1],   E[w] = (B−1)/2,   waste ≈ (B−1) / (2·E[ℓ])→ in plain terms: B = 16 with 600-token sequences wastes about 1.25%; B = 512 wastes about 42%.

Why not B = 1: per-block overhead (an indirect lookup, less coalescing) scales with ℓ/B. Total cost is roughly α(B−1)/2 + βℓ/B, minimized near B* ≈ √(2βℓ/α). This cost model is illustrative, not from the paper. The paper's empirical best was 16–128 on ShareGPT, with 16 as the default.

6.3 Block-wise softmax is exact

o = (Σt est vt) / (Σt est),   st = q·kt/√d→ in plain terms: the output is a weighted average of values, and the normalizer runs over all tokens.

Per block j, keep mj = max s, lj = Σ es−mj and aj = Σ es−mj v. Merging two blocks:

m = max(m1, m2);   l = em1−m l1 + em2−m l2;   a = em1−m a1 + em2−m a2;   o = a / l→ in plain terms: each block reports its local max, local sum and local weighted value; rescaling puts them on a common scale, so the result equals contiguous attention up to float rounding. Paging is lossless.

Why this form: per-block softmaxes can't be averaged because the normalizer is global. Subtracting the max prevents FP16 overflow (e11.1 > 65504). The paper's Eq. 4 writes the global denominator; FlashAttention and FlashInfer kernels use the running-max form.

6.4 Swap vs recompute

tswap ≈ 2ℓb / BWpcie + (per-transfer overhead × blocks);   trecompute ≈ 2Pℓ / Feff→ in plain terms: swap pays PCIe bytes plus a fixed cost per block; recompute pays prefill FLOPs.

Back-of-envelope for Llama-3-8B with ℓ = 1000: 131 MB, about 5 ms each way at ~25 GB/s, vs 1.6e13 FLOP, about 50–100 ms. Swap looks cheaper per byte, but per-block overhead dominates at small B. Paper (Fig. 19, OPT-13B): swap is bad at small blocks, recompute is flat across block sizes, the two are comparable at B = 16–64, and recompute never cost more than about 20% over swap. vLLM V1 defaults to recompute.

7 · Why it works

Core insight: the KV cache only grows at the end and is read in order, so it needs neither contiguity nor reservation. It needs a cheap index from logical position to physical location, and chunked softmax.

RefcountsNo sharing; beam-search savings of 37.6–66.3% lost

Online-softmax mergeMust materialize contiguous K/V, a copy every step

Fixed-size blocks end external fragmentation: every allocation asks for exactly one unit, so any free block satisfies it.

  • Contiguous + length prediction: mispredictions plus external fragmentation. Lost even with a perfect oracle.
  • vAttention (ASPLOS'25): virtually contiguous, physically demand-paged through CUDA VMM. Unmodified kernels, up to 1.23×. Constrained by driver page granularity, and sharing is less natural.
  • SGLang RadixAttention: pages indexed by a radix tree, with cache-aware scheduling for branching programs.
  • Compression (StreamingLLM, H2O, SnapKV, KIVI): shrinks the KV itself. Orthogonal to paging, but lossy.

9 · Where it breaks

Preemption thrash. Admission is based on prompt blocks, and growth is on demand. Under load many sequences need a block at once, and the newest is evicted, recomputed and evicted again. The toy simulation (§13) shows 818 preemptions at B = 16 with greedy admission. Mitigations are watermarks and max_num_seqs. I found no published measurement of thrash itself.
  • Output-length uncertainty remains the root problem; paging turns waste into preemption risk (2607.16892, Azure LLM 2024 trace).
  • Head-of-line blocking from long prefills. Chunked prefill (Sarathi-Serve: 2.6× capacity for Mistral-7B, up to 5.6× for Falcon-180B vs vLLM) is on by default in vLLM V1.
  • Hash collisions in prefix caching would serve another prompt's KV. vLLM defaults to SHA-256 and warns about xxhash in multi-tenant setups.
  • Kernel overhead (20–26% at op level) matters at small batch.
Cross-tenant timing side channel. Cache hits lower time-to-first-token. Early Bird (Song et al., IEEE TIFS) recovers other users' prompts token by token from KV-cache timing, with black-box tests on online services. Gu et al. (ICML'25) found global cross-user prompt-cache sharing at 7 API providers, including OpenAI. Mitigations: per-tenant cache_salt or per-user isolation, both of which give up reuse.
Misconceptions. "Saves memory like quantization": no, it stores exactly the same KV and output is identical. "Zero fragmentation": only external fragmentation is zero; tail waste is up to B−1 slots. "Uses hardware page faults": no, the lookup is a load inside the kernel. "Prefix caching is free": it costs hashing, LRU bookkeeping and a security boundary.

10 · In the wild

  • vLLM V1. Block 16. gpu_memory_utilization is 0.92 in code (older docs say 0.9). Prefix caching on with hash chains and LRU that evicts the tail block first. Recompute preemption, chunked prefill on with decodes first, append-only block tables. Deviates from the paper, which defaulted to swap and pre-reserved shared prefixes explicitly.
  • TensorRT-LLM. 128 tokens per block, fixed at build. Reuse on by default, but blocks become reusable only after the producing request terminates. Host secondary cache.
  • TGI. vLLM kernels plus a block table; prefix-cache policy not documented (unverified).
  • SGLang. Radix-tree reuse. Up to 6.4× throughput, but that's the whole runtime, not RadixAttention alone. Page-size default unverified.
  • Mooncake / LMCache / CachedAttention. Blocks move across HBM, DRAM, SSD and machines. Mooncake: up to 525% (simulated), +75% requests in production.

11b · Open problems

  • Admission under unknown output length. Keeping utilization high without thrash. Predictors are noisy, and watermarks bring the waste back.
  • Sharing vs privacy. Global caches leak and per-user caches lose reuse. Middle grounds: k-anonymous sharing, TTFT noise, per-org salts. Recent contention work (2608.09225, 2609.06853) is unverified.
  • Lossy compression vs retrieval. SnapKV stays within about 1.5% on LongBench at 10% retention (FastKV), but needle-style retrieval breaks and low budgets can lengthen reasoning traces.
  • Speculative decoding + paging + preemption: interaction unmeasured.
  • Software tables vs hardware VM: unresolved.
  • Head-to-head contiguous vs paged on the public Azure LLM trace: not found.

14 · Question ladder

Mechanism

1. What does the kernel load, in order, for token 9 in the trace?

It reads the table [7, 1, 3] and seq_len 9: physical #7 (4 tokens), #1 (4 tokens), then #3 with 1 valid token. It computes block-local max and sum and merges them with online-softmax rescaling. Loads are coalesced within a block; only the jumps between blocks are indirect.

2. When does vLLM allocate a new physical block?

At prefill, ⌈prompt/B⌉ blocks. During decode, only when the last block is full and a token must be written. It pops any free block id and appends it to the table. If none is free, the scheduler preempts first.

3. n=4 samples, prompt 30, B=16: blocks copied on the first decode?

Block 0 is full and block 1 is partial (14 tokens), both refcount 4. The first three writers to block 1 see refcount > 1 and copy; the fourth writes in place. 3 copies, and block 0 is never copied.

4. Finished blocks with prefix caching on vs off?

Off: refcount 0, blocks go to the free pool with meaningless contents. On: full blocks keep their hash in an LRU free queue, reusable by a matching hash chain or evicted under pressure. Tail blocks evict first.

Why

5. Why do fixed-size blocks eliminate external fragmentation?

Every allocation asks for exactly one block, so any free block satisfies it. "Enough free memory, but no hole big enough" can't happen.

6. Why does an oracle contiguous allocator still lose?

External fragmentation (79% of free memory outside the largest hole in the simulation), head-of-line blocking, and no sharing of prompt blocks.

7. Why B = 16?

Tail waste of about (B−1)/2 favors small B; coalescing, fewer lookups and fewer tiny swaps favor large B. The paper's sweep found 16–128 best on ShareGPT and 16–32 on Alpaca. TRT-LLM picks 128 for its kernels.

8. Why is preemption all-or-nothing per group?

Every step reads every block, so there's no cold subset, and a sequence missing any block can't run. Group members share blocks, so they're gang-scheduled and preempted together.

9. Why hash only full blocks, and why chain the parent?

A partial block's contents still change. KV at position t depends on every earlier token, so identical 16 tokens after a different prefix have different K,V. The parent hash encodes the whole prefix.

Counterfactual

10. Remove refcounts but keep block tables?

The packing benefit stays, but sharing is unsafe because you can't know when to free or copy. You lose parallel-sampling and beam savings (37.6–66.3% for beams) and prefix caching.

11. If output lengths were known exactly, is paging still worth it?

Yes, though less so. External fragmentation (unless you compact by copying) and lack of sharing remain. vLLM's gain shrinks from 2.7–8× (vs Orca-Max) to 1.7–2.7× (vs Orca-Oracle).

12. With a cheap hardware MMU for GPU memory?

Software tables and kernel indirection disappear (vAttention-like). On-demand mapping, refcounts or CoW, preemption policy and prefix hashing remain.

Adversarial

13. How do you extract another tenant's prompt from a shared prefix cache?

Probe guessed prefixes and measure TTFT; a fast response means a hit. Extend block by block or token by token (Early Bird). Larger B means more candidates per step. Defenses: salts, isolation, noise.

14. Design a workload that maximizes thrash.

Bursts of short prompts with long outputs, high max_num_seqs, no watermark. Sequences cross block boundaries together, the pool empties, the newest are recomputed and evicted again. Each cycle costs a full prefill.

15. How can a prefix-hash collision fail?

Request B reuses A's KV: wrong outputs conditioned on A's text, and possible leakage of A's content. That's why the default is SHA-256 with a warning about xxhash.

Connection

16. Relation to fork() and where it fails?

Samples are forked processes sharing refcounted pages copied on write. There are no MMU faults (the scheduler checks refcounts), no locality-driven paging, and contents can be recomputed.

17. How does disaggregation depend on blocks?

KV moves between prefill and decode nodes and tiers (RDMA, DRAM, SSD) as fixed-size blocks, mapped into the decoder's table without contiguity.

18. How does KIVI compose with paging?

They're orthogonal: fewer bytes per token, so more tokens per pool. Key quantization works on token groups, which interacts with block boundaries and the full-precision residual tail.

19. Online softmax and FlashAttention?

Same running max and sum merge. FlashAttention tiles for SRAM; paged variants just take tiles from table-indexed blocks.

Open

20. Near-100% utilization with no preemption under unknown lengths?

Open. It's a trade between over-reservation and preemption risk, with no guarantee under heavy-tailed lengths.

21. Provably safe prefix sharing with most of the benefit?

Open. k-tenant thresholds, noise, salts and constant-time responses all cost hit rate or latency, and formal guarantees are rare.

22. Will hardware VM replace software block tables?

Open. vAttention is competitive, but page granularity and the lack of hardware CoW limit it. Software tables remain the default in vLLM, TRT-LLM and SGLang as of 2026.
