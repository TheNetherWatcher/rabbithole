E-graphs and equality saturation: union-find, rebuilding, extraction, and why Cranelift won't saturate

An e-graph stores many equal programs at once: e-classes of e-nodes whose children point at classes, merged by union-find and kept consistent by congruence. Equality saturation applies every rewrite without deleting anything, then extraction picks the cheapest term. It pays off when the space stays small: Cranelift's aegraph measured 23% overhead just to round-trip through the graph. Saturation is undecidable in general, so real systems stop on limits, and the result depends on those limits again.

Why it matters: phase ordering is why compilers run 100-pass pipelines. E-graphs take the order out of the rewrite step, and the same machinery powers Herbie's float-accuracy fixes, Tensat's tensor graphs and lean-egg's proofs.

Plain English
In everyday words

A binder of same-meaning phrases, then keep the cheapest

Each rule staples a new equal phrase onto the same page instead of erasing the old one. Nothing is thrown away until the end, when the cheapest phrase on the page is kept.

In the calculator example, a×2÷2 collapses to just a, and the multiply and divide disappear.

Explain it simply. Picture a librarian who keeps a "same-meaning" binder. Every time someone proves two phrases mean the same thing ("twice a, then halved" = "a"; "a times two" = "a shifted left by one"), the librarian doesn't erase the old phrase. They staple the new phrase to the same page. Pages can point at other pages ("the thing on page 7, halved"), so one stapled fact can make many other pages equal too, and they have to go round and staple those as well.

A normal optimizing compiler is a cook who follows a recipe of tweaks in a fixed order, throwing away the old version each time. If it does step 3 before step 5 it may miss a shortcut that only appears the other way round. The binder approach avoids that: apply every known tweak, keep every version, and only at the end flip through the binder and pick the cheapest phrase on the page you care about. That's an e-graph (the binder), equality saturation (keep stapling until nothing new turns up), and extraction (pick the cheapest phrase).

Everyday example

A calculator program sees "take a, multiply by 2, divide by 2". The binder starts with four pages: a, 2, "a×2", and "(a×2)÷2". Round 1: one rule says "×2 is the same as shift-left-by-1", so "a shifted by 1" is stapled onto the "a×2" page. Another rule says "(x×y)÷z = x×(y÷z)", so "a×(2÷2)" is stapled onto the last page. Round 2: "anything divided by itself is 1", so "2÷2" joins the page for "1". Round 3: "x×1 = x" puts "a×(2÷2)" (now known to be "a×1") on the same page as "a". The last page and page a become one page. Round 4 finds nothing new. Flip to that page, take the shortest phrase: just a. The compiler deletes both the multiply and the divide.

Bridge: now the same thing, technically.

Context
§1 · Prerequisites

Four ideas to know first: terms, union-find, congruence, phase ordering

  • Term: a tree; rewrites turn one term into an equal one.
  • Union-find: answers "same set?" in near-constant time.
  • Congruence: if a ≡ b then f(a) ≡ f(b).
  • Phase ordering: the order of passes changes the output.
  • Term / AST: a tree like (/ (* a 2) 2). Rewrites turn one term into an equal one. (egg tutorial)
  • Union-find: a forest that answers "are x and y in the same set?" in near-constant amortized time; find returns the set's canonical representative, union links two roots. (Wikipedia)
  • Hash-consing: never build the same node twice; a hash map from node → id gives structural sharing (a DAG instead of a tree).
  • Congruence: if a ≡ b then f(a) ≡ f(b). The "closure" is everything you can derive this way. (Nelson & Oppen 1980)
  • Phase ordering: an optimizer's passes destroy information, so the order you run them in changes the output. That's the problem e-graphs attack.
  • Datalog / conjunctive query: rules over relations joined on shared variables; relevant because modern e-matching is a database join. (relational e-matching)
§1b · Real-world context

Cranelift runs one in production, and egg made it fast enough

Cranelift has used an acyclic e-graph in production since 2023. Herbie's float-accuracy rewriting runs on egg, which is over 3000× faster than Herbie's old simplifier. Cranelift measured 23% overhead for a zero-rewrite round trip, so its JIT-speed mid-end kept only directional, eager rules.

Library and egglog code samples inside.

What it is. An e-graph is a data structure that stores a large (even infinite) set of equivalent programs compactly, by grouping nodes into e-classes (sets of nodes known to be equal) whose children point to e-classes, not to individual nodes. Equality saturation (eqsat) is the algorithm that repeatedly applies rewrite rules without deleting anything, adding each rewritten form to the matching e-class, until no rule adds anything new ("saturation") or a limit hits. Then an extractor picks the cheapest representative under a cost model.

Why it exists. Destructive rewriting forces you to choose a rule order, and a greedy choice can block a better one later (phase ordering). Tate, Stepp, Tatlock and Lerner (POPL 2009) proposed keeping all choices and deciding at the end. The idea sat in research for a decade because the data structure was slow: in Herbie (a floating-point accuracy tool) the old Racket e-graph simplifier took 98.1% of Herbie's runtime. egg (POPL 2021) made it fast, and the egg backend is "over 3000× faster than Herbie's initial simplifier" (egg §6.1). Before e-graphs, people hand-ordered pass pipelines (LLVM's ~100-pass -O2) and hand-wrote peepholes (InstCombine), where Alive found 8 bugs in 334 hand-coded transforms (cited in Cranelift RFC).

Where it's used (checked against source or primary pages unless tagged):

  • Cranelift / Wasmtime: production mid-end since Jan 2023 (#5587), as an acyclic e-graph ("aegraph") with ISLE rewrite rules in cranelift/codegen/src/opts/*.isle; does GVN, LICM, constant folding, algebraic simplification in one pass.
  • Herbie: floating-point accuracy rewriting; Racket core calls Rust egg via FFI (egg-herbie), plus an egglog backend (repo).
  • Tensat (MLSys 2021): tensor-graph superoptimization with ILP extraction; "up to 16% speedup … 48× less time optimizing" vs TASO (arXiv).
  • Luminal (Rust ML inference compiler): lowers its graph to (a fork of) egglog and searches kernel variants by measured GPU time (repo).
  • ROVER (Imperial + Intel authors): RTL datapath rewriting, "up to a 63% reduction in circuit area" (arXiv). SEER does HLS via MLIR + e-graphs (ASPLOS 2024, secondary).
  • Ruler / Enumo: synthesize rewrite rules with eqsat; Ruler's rule sets are 5.8× smaller and found 25× faster than a CVC4-based tool (arXiv).
  • lean-egg: Lean 4 tactic that turns theorems into rewrite rules, searches with egg, and rebuilds a Lean proof (POPL 2026, PDF).
  • RisingLight (educational OLAP DB): SQL optimizer built on egg 0.9.5 (repo); wasm-mutate uses egg to generate semantically equal fuzz mutants (Cargo.toml).

Not found: no upstream LLVM or GCC e-graph pass. Claims about Certora, DataFusion or Mojo using egg could not be confirmed (unverified, don't repeat them).

How it's used. Library route (egg 0.11, verbatim from tests/simple.rs):

use egg::*;
define_language! { enum SimpleLanguage {
    Num(i32), "+" = Add([Id; 2]), "*" = Mul([Id; 2]), Symbol(Symbol), } }

let rules: Vec<Rewrite<SimpleLanguage, ()>> = vec![
    rewrite!("commute-add"; "(+ ?a ?b)" => "(+ ?b ?a)"),
    rewrite!("add-0"; "(+ ?a 0)" => "?a"),
    rewrite!("mul-1"; "(* ?a 1)" => "?a"),
];
let expr: RecExpr<SimpleLanguage> = "(+ 0 (* 1 foo))".parse().unwrap();
let runner = Runner::default().with_expr(&expr).run(&rules);
let (cost, best) = Extractor::new(&runner.egraph, AstSize).find_best(runner.roots[0]);
// best = foo

Typical knobs: Runner defaults are iter_limit 30, node_limit 10_000, time_limit 5 s. The default scheduler is BackoffScheduler with match limit 1,000 and ban length 5 iterations, both doubling each time a rule gets banned (run.rs, docs). Language route: egglog ((datatype …), (rewrite …), (run 10), (extract …)), or pip install egglog for the Python bindings. Compiler route: Cranelift ISLE rules such as

(rule iadd_x_plus_zero (simplify (iadd ty x (all_zero ty))) (subsume x))

When to use / when not. Use full eqsat when result quality matters far more than search time and the rule set interacts in ways you can't order by hand: hardware datapaths, tensor graphs, numerical accuracy, rule synthesis, theorem proving, superoptimization. Don't use it in a JIT or fast AOT compiler's hot path. Cranelift tried egg and measured 23% overhead just to round-trip through the e-graph with zero rewrites, against an optimizer budget of ~10% of compile time (Fallin 2026). Signs you picked wrong: you're hitting NodeLimit on every run, outputs change when you add an unrelated rule, or extraction quality is dominated by a cost model you can't make accurate.

Who should care. Compiler engineers (mid-end design, phase ordering), ML-compiler people (graph rewriting, kernel fusion), hardware/EDA (datapath and logic optimization), verification people (proof search, translation validation), DB query-optimizer authors (Cascades is a cousin).

Technical deep dive
§2 · The one-liner

Saturation is easy to state; congruence, limits and extraction are the hard parts

"Apply all rewrites, keep every version, pick the best" hides five problems. Congruence repair is the slow part. Saturation rarely terminates, so limits bring phase ordering back. Picking the best is NP-hard under sharing. One unsound rule spreads globally.

"Apply all rewrites at once, keep every version, pick the best at the end, so no phase ordering."

It hides:

  1. Congruence maintenance is the hard, slow part, not rewriting. Merging two classes can make parents equal, which can make their parents equal. egg's main trick (deferred rebuilding) is about when to do that work.
  2. Saturation usually never comes. Termination is undecidable in general; real systems stop on node/time limits, and then the result depends on rule order and schedule again, so phase ordering comes back through the limits.
  3. "Pick the best" is NP-hard when shared subexpressions count once, and the answer is only as good as the cost model.
  4. One unsound rule poisons everything, because merges are global and congruence spreads them.
  5. E-graphs are pure-dataflow structures. Loops, side effects, and variable binding need extra machinery (PEG θ-nodes, Cranelift's side-effect skeleton, slotted e-graphs).
§3 · The problem

Destructive rewriting commits too early and loses <code>a</code>

Strength-reducing a*2 first turns (a*2)/2 into (a<<1)/2, and the algebra rule no longer matches. Keeping every form needs sharing, or the search space explodes. Egg's speed made that practical; before it, e-graph upkeep took 98.1% of Herbie's runtime.

Destructive rewriting commits. Take (a*2)/2 and two rules: strength-reduce x*2 → x<<1, and the algebraic (x*y)/z → x*(y/z). Run strength reduction first and the term becomes (a<<1)/2; the algebraic rule no longer matches, and you've lost a. Zucker shows exactly this failure for eager e-graph rewriting (smart-constructor aegraph). Production compilers paper over it by running passes many times in hand-tuned orders.

The obvious fix (search all orders) is exponential: k rules applicable in n places gives a branching tree of terms, most of which share almost all of their structure. The constraint that forced the e-graph design is sharing: represent all those terms in space roughly proportional to the distinct subterms plus the equalities among them. The second constraint is speed: before egg, the e-graph upkeep dominated runtime (98.1% of Herbie), so the idea was a research curiosity.

§4 · Mental model

An e-class behaves like a spreadsheet cell that holds formulas

An e-class is a cell holding a set of formulas that all equal one value, and formulas refer to cells, not to other formulas. Merging two cells can force other cells to merge too, which spreadsheets never do. A cell can also refer to itself.

Analogy: a spreadsheet where each cell (e-class) holds a set of formulas that all evaluate to the same value, and formulas refer to other cells, not to other formulas. Proving a new equality = moving a formula into a cell, or merging two cells. Picking the output = for each cell, choosing which of its formulas to display.

Where it breaks:

  1. Merging two cells can make two other cells hold identical formulas (f(A) and f(B) once A and B merge), and those must merge too. Spreadsheets never do that.
  2. A cell may contain a formula that refers to itself (a = a*1), so a cell can stand for infinitely many expressions.
  3. Choosing per cell independently is optimal only if every use pays for its own copy. Once shared cells count once, the choices interact globally.
§5 · Mechanism, traced

One term saturates in four iterations and extracts to <code>a</code>

On (a*2)/2, two rules merge the root with a in iteration 2 through a self-pointing class. Four iterations saturate it to 4 classes and 8 nodes. Extraction picks a at cost 1. Adding one commutativity rule breaks termination.

The structure (egg's definitions, §2.1):

E-graph = (U, M, H)
  U  union-find over e-class ids          find(e3) -> e0 after merges
  M  e-class id -> set of e-nodes          e0 -> {a, (* e0 e6), (/ e2 e1)}
  H  hashcons: canonical e-node -> id      ('*', 0, 1) -> e2
  e-node = (op, child e-class ids...)      children are CLASSES, not nodes
  parents[c] = e-nodes that use class c    needed to repair congruence

Step 0: add the term. Each subterm is hash-consed bottom-up:

e0: {a}   e1: {2}   e2: {(* e0 e1)}   e3: {(/ e2 e1)}     root = e3

Note that 2 appears twice in the term but once in the graph: sharing.

Iteration 0, read phase (search every rule against every class; invariants intact):

mul-two    @ e2  {?a=e0}
div-assoc  @ e3  {?a=e0, ?b=e1, ?c=e1}

Write phase (instantiate the right-hand side, union(class, new); invariants now broken, merged ids go on a worklist):

mul-two:   add 1 -> e4, add (<< e0 e4) -> e5, union(e2,e5)
div-assoc: add (/ e1 e1) -> e6, add (* e0 e6) -> e7, union(e3,e7)
worklist = [e2, e3]

Rebuild (dedup the worklist, re-canonicalize parents, merge newly congruent parents):

e0:{a}  e1:{2}  e2:{(* e0 e1),(<< e0 e4)}  e3:{(* e0 e6),(/ e2 e1)}  e4:{1}  e6:{(/ e1 e1)}

Iteration 1. div-same now matches e6 = (/ e1 e1) and does union(e6, e4). Rebuild visits e6's parents, finds (<< e0 e4) whose child id is no longer canonical, and rewrites its hashcons key to (<< e0 e6). This re-canonicalization is the whole job of rebuilding.

e2:{(* e0 e1),(<< e0 e6)}   e3:{(* e0 e6),(/ e2 e1)}   e6:{(/ e1 e1), 1}

Iteration 2. e6 now contains 1, so mul-one matches (* e0 e6) inside e3 with ?a = e0, and does union(e3, e0). The root class and a are now the same class.

e0:{a, (* e0 e6), (/ e2 e1)}   e1:{2}   e2:{(* e0 e1),(<< e0 e6)}   e6:{(/ e1 e1), 1}

e0 now contains (* e0 e6), a node whose child is its own class: a cycle. e0 represents a, a*1, a*1*1, … (infinitely many terms) in 3 nodes.

Iteration 3. Four matches, every union is a no-op, so the graph is saturated. Final: 4 e-classes, 8 e-nodes.

Extraction (greedy bottom-up, AstSize: cost(node) = 1 + Σ cost(best child)):

e1: 2 -> cost 1      e6: 1 -> cost 1      e0: a -> cost 1   (beats (/ e2 e1) at 1+3+1=5)
e2: (* a 2) -> 3     root find(e3)=e0 -> "a"
            iteration 0                iteration 1             iteration 2
 e3:[ / e2 e1 ]       e3:[ / e2 e1 | * e0 e6 ]   ...     e0:[ a | * e0 e6 | / e2 e1 ]
      |   \                    |        \                         ^    |
 e2:[ * e0 e1 ]       e2:[ * e0 e1 | << e0 e4 ]           e6:[ / e1 e1 | 1 ]
                      e6:[ / e1 e1 ]   e4:[1]              (e0 points to itself: cycle)

One added rule breaks termination. Add mul-comm (* ?a ?b)→(* ?b ?a) and the same term never saturates: (* 2 a) plus div-assoc gives (* 2 (/ a 2)), then a/4, a/8, …. The demo prints e-nodes 9 → 12 → 13 → 20 → 28 → 39 → 52 → 67 → 84 → 103 and stops on the iteration limit. Extraction still returns a, because it was found early.

The loop itself (egg Fig. 5b; the read/write split makes results independent of rule-list order within an iteration):

while not saturated and under_limits:
    matches = [(rw, subst, c) for rw in rules for (subst, c) in ematch(rw.lhs)]  # read
    for rw, subst, c in matches:
        union(c, add(instantiate(rw.rhs, subst)))                              # write
    rebuild()                                                                   # once
§6 · The math

Commutativity plus associativity needs 3ⁿ nodes, and matching is a join

Under AC, n summed leaves need 2ⁿ − 1 classes and 3ⁿ − 2ⁿ⁺¹ + n + 1 nodes: 57,010 nodes at n = 10. Relational e-matching treats each pattern as a database join and reports up to 6 orders of magnitude on deep patterns.

AC calculator inside.

6.1 The invariants

Let ≡id be the union-find relation and ≡node the relation "two e-nodes are in the same class". The congruence invariant (egg Def 2.6) says ≡node equals its own congruence closure:

f(a₁,…,aₖ) ≡node f(b₁,…,bₖ)  ⇐  ∀i. find(aᵢ) = find(bᵢ)→ in plain terms: two nodes with the same operator and the same canonical children must be in the same class.

The hashcons invariant (Def 2.7): n ∈ M[a] ⇔ H[canon(n)] = find(a), where canon(f(a₁…aₖ)) = f(find(a₁)…find(aₖ)).

n ∈ M[a]  ⇔  H[canon(n)] = find(a)→ in plain terms: the lookup table is keyed by nodes whose children are representatives, so "have I seen this node?" is one hash probe.

Why this form and not "keep a tree per term": the right-hand side quantifies over classes, so one equality a ≡ b instantly covers every term containing a. That's what makes the representation exponentially compact, and it's also why one merge can cascade.

6.2 Why deferring rebuild wins

Take n terms f1(x), …, fn(x) plus leaves y1..yn, then merge x with each yi (egg §3.2.1). Immediate maintenance repairs x's parent list after every merge: n merges × n parents = O(n²) hashcons updates. Deferred: all n merges go on the worklist, deduplicate to one canonical class, and its n parents are repaired once: O(n). For w chains of depth d whose leaves get merged, immediate costs O(wd) repairs, deferred O(d), because the w upward paths coalesce after dedup.

→ in plain terms: rebuilding pays once per distinct dirty class per iteration, not once per merge.

Measured on egg's 32-test suite: 88× geometric-mean speedup on congruence closure, 21× on whole eqsat, deferred vs immediate rebuilding inside egg (not vs Herbie; that's a common misquote). egg proves rebuilding terminates (Thm 3.1) via a lexicographically decreasing (|incongruent pairs|, |worklist|) measure, but gives no online complexity bound ("likely highly workload dependent").

6.3 AC blowup, derived

Saturate x1 + … + xn (distinct leaves) under commutativity and associativity. Any regrouping and reordering is reachable, so every non-empty subset S of the leaves is the sum of some subterm: 2ⁿ − 1 e-classes. A class for a subset of size k ≥ 2 contains one + node per ordered split of S into two non-empty parts: 2k − 2 of them. Summing:

#(+-nodes) = Σk=2n C(n,k)(2k − 2) = 3n − 2n+1 + 1(the k = 0 and k = 1 terms of the two sums cancel to −1, hence +1). Adding the n leaf nodes gives 3n − 2n+1 + n + 1 e-nodes, matching Rosin, Ullrich and Hack's EGRAPHS 2026 paper.

→ in plain terms: 10 summed variables → 1,023 classes and 57,010 nodes; 20 → over 3.4 billion nodes. Commutativity alone is mild; the pair with associativity is what explodes.

6.4 E-matching as a join

Relational e-matching (Zhang et al., POPL 2022) stores each e-node f(j1..jk) in class i as a tuple R_f(i, j1, …, jk). The pattern f(α, g(α)) becomes the conjunctive query

Q(root, α) ← Rf(root, α, x), Rg(x, α)

Backtracking checks the repeated α last: O(N²) for N matches. A join checks it during the join: O(N). Using Generic Join (worst-case optimal), the time is bounded by the AGM bound; Thm 10 gives O(√(|Q(I)| · ∏ᵢ|Rᵢ|)). The paper reports "over 6 orders of magnitude faster" on deep patterns with repeated variables. The speedup plot below is that evaluation: bars right of the 1× line mean relational e-matching is faster.

→ in plain terms: e-matching is NP-hard in pattern size, but patterns are tiny; in e-graph size, it's polynomial and a database planner does it well.

6.5 Extraction

With a monotone local cost (cost(f(c1..ck)) > every child cost), greedy bottom-up fixpoint is optimal for tree cost (each use counted separately). Under DAG cost (a shared class counted once) it's NP-hard (Stepp 2011 thesis) and inapproximable to any constant factor (Goharshady et al., OOPSLA 2024). The standard exact method is ILP (Tensat):

min Σᵢ cᵢxᵢ   s.t.   Σi∈root xᵢ = 1,   xᵢ ≤ Σj∈m xⱼ  ∀i, ∀m ∈ children(i)plus acyclicity via order variables tₘ: tg(i) − tₘ − ε + A(1 − xᵢ) ≥ 0. In plain terms: pick exactly one node at the root; picking a node forces you to pick some node in each child class; and the picks must not form a loop. The cycle constraint is what makes the ILP slow; Tensat filters cycles during exploration and drops it.
§7 · Why it works

Congruence repair and the read/write split keep the graph consistent

Deferred rebuilding turns O(n²) parent repairs into O(n), a measured 88× geometric-mean speedup inside egg. The read/write split makes each iteration depend only on the graph at its start. Remove the hashcons and congruent nodes stay apart; remove the limits and ordinary rule sets never stop.

Core insight: equality is a global fact about classes, and congruence makes it propagate structurally, so you can apply a rewrite once to a class and every term that contains it benefits. Combined with hash-consing, a set of terms that grows exponentially in the number of rewrites applied often stays polynomial in the e-graph. That's Tensat's and the Showdown paper's argument for matrix chains: the exponential space of parenthesizations sits in O(n³) nodes.

Ablations (what breaks when you remove each piece):

  • Remove the union-find → you can't tell that e3 and e0 are the same class. Every merge would rewrite all pointers eagerly (expensive) or leave duplicate classes (wrong answers). Cranelift did remove it in 2025 (#10471), but only because its rules are directional and it never repairs congruence anyway.
  • Remove the hashcons → (/ e1 e1) can be added twice into different classes. Congruent nodes stay apart; the graph is no longer a DAG with sharing; matching cost multiplies.
  • Remove rebuild (union without repairing parents) → after union(e6, e4), (<< e0 e4) keeps a stale key. A future add((<< e0 e6)) makes a duplicate class, and some equalities are never discovered. This is what aegraphs accept on purpose (Fallin counts 2 misses in ~4M value nodes).
  • Remove the read/write split → applying matches while searching makes results depend on rule-list order and can invalidate iterators mid-search.
  • Remove limits → nontermination on ordinary rule sets (the mul-comm demo).
  • Remove e-class analyses → no constant folding, no x/x → 1 if x ≠ 0. You're stuck with purely syntactic rules, and Herbie had to use unsound ones.
§8 · Knobs & alternatives

Limits, scheduler and extraction decide what you actually get

Egg defaults to 30 iterations, 10,000 nodes and 5 seconds, with a backoff scheduler. Directional rules stay small, while bidirectional AC explodes. On matrix chains, eqsat stays within 1% of optimal up to about 800 matrices, then drifts as far as 65% off.

  • Stochastic superoptimization (STOKE, MCMC): the EGRAPHS 2026 "Rewrite System Showdown" finds neither dominates. MCMC was always within 0.3% of optimal on matrix chains; eqsat was within 1% up to ~800 matrices and up to 65% off on some larger ones. The plot below shows that comparison for matrix chains.
  • SMT synthesis (Souper): discovers peepholes offline; same role Ruler plays for e-graph rule sets.
  • Aegraphs (Cranelift): e-graph-flavoured sea-of-nodes, eager, one pass, limits of 5. Won for a JIT-speed compiler; full eqsat won where compile time is cheap.
§9 · Where it breaks

Blowup, unsound rules and limits make results unpredictable

AC needs 3ⁿ nodes. A single unsound rule like x/x → 1 merges 0 with 1, and congruence spreads the merge to every class built on them. Limits make runtime predictable but results not. One Cranelift rule addition moved a fuzz case from 0.08 s to about 10 s.

  • Blowup. AC: 3ⁿ nodes (§6.3). Unguided eqsat on matrix-multiply optimizations found only 2 of 7 known optimizations after an hour and 60 GB; with ≤3 human "sketches" all 7 appear in seconds under 1 GB (sketch-guided eqsat). Tensat reports multi-pattern rules causing "double exponential growth" and caps them separately.
  • Limits make results unpredictable. Flatt (UW PLSE, 2025): limits make runtime predictable but results not. "Adding new program optimizations results in the resource limits being triggered earlier, preventing optimizations that were previously applied" (post).
  • Unsound rule → collapse. x/x → 1 puts 0/0 in the class of 1. Any rule deriving 0/0 = 0 then merges 0 and 1, and congruence spreads it to every class built on them. Herbie relied on such rules and "must validate the results … and discard them if unsoundness was detected". Removing them made Herbie "useless on a large portion of its benchmark suite" (egglog paper). Herbie's FAQ still has an "Unsound rule application detected" warning.
  • Production blowup even with directional rules. Cranelift #13068 and #13204 (2026): adding rules like (x−z)−(y−z) → x−y moved one fuzz case from 0.08 s to ~10 s, with one rule firing ~3,000,000 times. It was fixed by subsuming x−x → 0 for vectors. Also #13476 (stack overflow in constructor_simplify).
  • Extraction ignores sharing. Cranelift deliberately counts each use anew. #12156 shows costs saturating to infinity because of that.
  • Binders. With names or de Bruijn indices, α-equivalent subterms don't share. De Bruijn needs shift rewrites that themselves blow up (§11).
  • Control flow and effects. Loops make cyclic terms that greedy extraction can't extract. PEGs used θ-nodes plus a pseudo-Boolean solver; Cranelift keeps side-effecting instructions in a fixed CFG "skeleton" and only floats pure ops.

Misconceptions:

  • "Eqsat eliminates phase ordering." Only at saturation. Under limits, order returns through scheduling; eager aegraphs reintroduce it outright (Zucker's (a*2)/2).
  • "E-graphs give optimal output." Only with respect to the explored space × the cost model × an exact extractor (NP-hard, inapproximable).
  • "It's rewriting with backtracking." Nothing is undone; space only grows; choice is deferred to extraction.
  • "egg is 88× faster than Herbie's old e-graph." No: 88× is deferred vs immediate rebuild inside egg. Against Herbie's original simplifier it's over 3000×.
  • "The aegraph caused Wasmtime CVEs." The Wasmtime GHSA list shows the miscompile CVEs (e.g. CVE-2023-26489, CVE-2026-34971) are in backend ISLE lowering, not the egraph mid-end.
§10 · In the wild

Cranelift drops most textbook choices to fit a JIT

Cranelift's aegraph rewrites eagerly at node creation, has no rebuild, and caps work at 5 matches per call. Its average e-class holds 1.13 nodes, and scoped elaboration recovers GVN and LICM. egglog's Datalog core is 3.34× faster than egg building the same graph.

  • Cranelift aegraph deviates on every axis. Rules are applied eagerly when a node is created, in one RPO pass; there is no rebuild; the union-find was removed in 2025 (#10471). Limits: MATCHES_LIMIT = 5 rewrites per ISLE call, ECLASS_ENODE_LIMIT = 5, REWRITE_LIMIT = 5 recursion depth, EXTRACTOR_FUEL = 500 (egraph/mod.rs). subsume drops alternatives outright. Pure ops float free and are placed back by scoped elaboration over the dominator tree, which yields GVN, LICM and rematerialization.
  • Fallin's own 2026 evaluation: about a 2% runtime win over a classical pipeline using the same rules, for ~7–8% more compile time. Keeping multiple forms per value is worth ~0.1% ("in the noise"). The average e-class has 1.13 nodes. His conclusion: "the sea-of-nodes-with-CFG aspect of this mid-end works great, but the aegraph itself … may not (yet?) be pulling its weight."
  • egg is textbook-plus: deferred rebuild, e-class analyses, backtracking pattern compilation (no inverted path index), backoff scheduling, and explanations (FMCAD 2022: proofs 72.8% the size of Z3's on average).
  • egglog replaces the single-language, single-analysis model with Datalog: functions with :merge expressions and semi-naive incremental matching. It is 3.34× faster than egg building the identical e-graph, and 9.27× with semi-naive (PLDI 2023). It now supports -j parallel execution.
  • Herbie uses egg with unsound rules plus post-validation. The egglog rewrite is sound via interval and non-zero analyses.
  • Tensat caps multi-pattern rules with a separate iteration limit and pre-filters cycles so ILP extraction stays tractable.
  • Luminal extracts by measured GPU runtime of candidates, sidestepping the cost-model problem at the price of benchmarking.
Research edge
§11 · Frontier

The frontier moved to slots, differentiable extraction and termination limits

Slotted e-graphs handle binders without shift rewrites, cutting one four-parameter case from over 4 GB to 6 MB. SmoothE extracts on a GPU with 8–37× speedups. Suciu et al. show termination over all terms is Π₂-complete, so limits are necessary, not just engineering.

Primary-checked unless tagged.

  1. Slotted E-Graphs: Schneider, Rossel, Shaikhha, Goens, Kœhler, Steuwer. PLDI 2025. E-classes are parameterized by slots (free variables); e-nodes point to classes through a renaming; congruence holds modulo renaming; each class stores a permutation group of its symmetries (Schreier–Sims). On a function-fission benchmark, egg with de Bruijn indices exceeded 4 GB at 4 parameters (1,827k nodes, 52 s); slotted needed ≤214 nodes, 6 MB, 0.22 s. On Mathlib's not_supIrred, egg grew to 2.6M nodes and crashed at 40 GB; slotted finished in under 1 s. Cost: 2.7× memory and 7.8× slower on a plain de Bruijn workload (the prototype lacks egg's engineering). (PDF)
  2. SmoothE: Differentiable E-Graph Extraction: Cai, Yang, Deng, Yu, Zhang. ASPLOS 2025 Best Paper. Each class gets a probability distribution over its nodes; expected cost is minimized by gradient descent on a GPU. Acyclicity comes from a NOTEARS-style trace-of-matrix-exponential penalty per SCC. Comparable or better than 10-hour CPLEX on 4 of 5 datasets, with 8–37× speedup; supports nonlinear costs. (PDF)
  3. Fast and Optimal Extraction for Sparse Equality Graphs: Goharshady, Lam, Parreaux. OOPSLA 2024 Distinguished Paper. Exact extraction is linear-time for bounded treewidth (fine up to ~10 on Cranelift e-graphs). It also shows extraction is inapproximable. (secondary for the venue page) (page)
  4. Semantic Foundations of Equality Saturation: Suciu, Wang, Zhang. ICDT 2025. E-graphs as tree automata; eqsat = least fixpoint = universal model; two-way reductions to the database chase. Termination on one input is R.E.-complete; on all terms it is Π₂-complete; on all e-graphs it is undecidable. Gives "weak term acyclicity" as a syntactic sufficient condition. (arXiv)
  5. Optimism in Equality Saturation: Arbore, Cheung, Willsey. PLDI 2026. E-class analyses are pessimistic and lose precision on cyclic SSA. Naive optimism is unsound in e-graphs, so they give an abstract-interpretation algorithm that analyzes optimistically during saturation, more precise than clang and gcc on their examples. (arXiv)
  6. eqsat MLIR dialect: Merckx, Lopoukhine, Coward, Cheng, De Sutter, Grosser. EGRAPHS 2025. E-graphs as native MLIR IR, so matching and extraction reuse MLIR passes; the follow-up Tamagoyaki (2026) reports a 1.18× average speedup. DialEgg (Zayed, Dubach, CGO 2025) instead round-trips MLIR ↔ egglog. (arXiv)
  7. Rewrite System Showdown: Stochastic Search vs. EqSat: Hong, Soi, Zhang, Aiken. EGRAPHS 2026. The first head-to-head with identical rule sets on 5 benchmarks. Neither Pareto-dominates. On Caviar/Halide inequalities, 40% are solved by both, 6% only by eqsat, 3% only by MCMC, and ~50% by neither. (arXiv)
  8. Scaling via scheduling: CERES (EGRAPHS 2026, secondary) matches Herbie's expression quality with 8–12× less memory. EggMind (arXiv 2604.17364, Apr 2026, no venue) has an LLM synthesize saturation strategies, reporting −45.1% cost and −69.1% peak RAM. A parallel eqsat engine (CC 2026, secondary).
  9. New domains: Quasar quantum-circuit eqsat (PLDI 2026, secondary: −33.5% total gates, geomean). EqiForge tensor superoptimization deriving FlashAttention-style kernels (arXiv 2609.12330, Sept 2026, no venue: up to 2.74×). e-boost extraction for logic synthesis (ICCAD 2025, secondary: 558× faster than ILP).
  10. Equational proofs in Lean: Rossel, Schneider, Kœhler, Steuwer, Goens. POPL 2026. Conditional rewrites, type classes, and proof reconstruction from egg explanations. (PDF)

Dissection 1: slotted e-graphs. Problem: λx. x+1 and λy. y+1 never share. Under de Bruijn indices, moving a subterm under a binder needs explicit shift rewrites, shifted copies of the same class aren't equal, and the graph explodes (81% of one 4,657-step egg explanation was shifts). Mechanism: a class c(s1,s2) is a function of its slots, and an e-node +(c1[s1↦x], c2[…]) carries a renaming per child. The hashcons key is the node's shape (renamings normalized), so α-variants hash together. Symmetries like x+y = y+x live in the class's permutation group instead of as extra nodes. Limits: constant-factor overhead; matching must infer renamings; case studies, no broad suite. Follow-up: Zucker's "Lifting E-Graphs" (EGRAPHS 2026) uses thinning bitvectors on ids instead.

Dissection 2: the extraction line. Greedy is sharing-blind; ILP is exact but slow, mainly because of the acyclicity constraint. The treewidth DP exploits that real e-graphs are sparse. SmoothE relaxes to continuous probabilities, making extraction a GPU optimization problem and admitting nonlinear costs, with no optimality guarantee. e-boost combines parallel heuristics, pruning, and a warm-started ILP. It reports beating SmoothE by 19%, but it shares authors with SmoothE, so it is not an independent comparison. ASP (Yang & Sergey, EGRAPHS 2026) shows that a naive answer-set encoding of matches competes with a tuned ILP.

Dissection 3: theory meets reality. Suciu, Wang and Zhang make "will it terminate?" formally hopeless in general (Π₂-complete over all terms), so limits and schedulers are necessary, not just engineering. The Showdown then asks whether the e-graph's sharing is worth its cost against plain randomized search. The answer is mostly a tie: the e-graph wins where an exponential space compresses well (matrix chains), and MCMC wins where rules are one-way or unsound. The matrix-chain plot in the knobs section shows the e-graph side of that trade. Cranelift's 1.13 nodes per class is the production version of the same message: when rules are directional, the "multiple versions" part barely matters.

§11b · Open problems

Predictable limits, sharing-aware costs and effects are still open

Termination is undecidable in general, so limits stay heuristic. Extraction that models register pressure is unsolved. Control flow has no agreed representation, and whether the aegraph earns its keep in fast compilers is measured both ways.

  • Predictable scaling. Limits trade unpredictable runtime for unpredictable results. Flatt's parameterized-complexity work on "linear-matching" rules (UW) and schedulers like CERES attack it, but nobody has a general guarantee. It is hard because termination itself is undecidable (ICDT 2025).
  • Rule scheduling and guidance. Backoff is a heuristic; sketches need a human; MCTS, RL and LLM strategies (EggMind) report wins on their own benchmarks without a shared suite. The obvious approach, learning which rule helps, fails because a rule's value shows up only many iterations later, after interacting with others.
  • Sharing-aware, cost-accurate extraction. NP-hard and inapproximable. Cranelift's cost model can't see register pressure or instruction selection ("in a 'conventional compiler', cost func + extraction is everything", Fallin's Dagstuhl 2026 slides). Multi-root extraction changes the problem again.
  • Control flow and effects. PEGs, RVSDG (eggcc, Jamey Sharp's optir), Cranelift's skeleton, and E-Path (2026, unchecked) all disagree on representation. Fallin lists rewriting control flow in the skeleton as open (#5623, #6109).
  • Context-dependent equality (x ≠ 0 only inside a branch). Colored e-graphs copy per assumption and are "notably resource-intensive". Predicate e-graphs and relational contextual eqsat (2025–26) are early.
  • Binders. Slotted vs lifting vs categorical approaches; the overhead-versus-expressiveness trade-off is not settled.
  • AC and theories natively. Generic AC is 3ⁿ. Bespoke multiset and polynomial handling (Zucker's "Omelets Need Onions", AC-canonizing e-graphs at EGRAPHS 2026) is an active direction.
  • Is the e-graph worth it at all in fast compilers? Fallin's 2026 data says the multi-version part is "within the noise" for Cranelift. The counter-position (UW PLSE's eggcc) is that you only see the benefit with richer, non-directional rule sets, which then need full eqsat. Unresolved, and the two positions are measuring different rule sets.
§12 · Lineage

From 1980 congruence closure to eqsat in production

Nelson and Oppen's congruence closure (1980) gave the e-graph. Tate et al. (2009) named equality saturation. Egg (2021) made it fast, relational e-matching (2022) made matching a join, and Cranelift shipped an aegraph in 2023.

  • 1977 Kozen, finitely presented algebras (congruence closure origin; e-matching NP-completeness).
  • 1980 Nelson & Oppen, congruence closure decision procedure (O(m²)); Downey–Sethi–Tarjan, O(m log m) with hashing; Nelson's thesis: the e-graph.
  • 1995 (side branch) Graefe's Cascades memo for query optimization.
  • 2002 Denali superoptimizer: e-graphs for codegen, saturate then SAT.
  • 2005 Simplify prover (Detlefs, Nelson, Saxe): e-graph plus backtracking e-matching.
  • 2007 de Moura & Bjørner, efficient e-matching (code trees, inverted path index) in Z3.
  • 2009 Tate, Stepp, Tatlock, Lerner, Equality Saturation (POPL): PEGs, Peggy for Java bytecode.
  • 2011 Stepp thesis (extraction NP-hard); eqsat translation validation for LLVM (CAV).
  • 2021 egg (POPL, Distinguished Paper): rebuilding and e-class analyses; Ruler, Tensat, Diospyros.
  • 2022 relational e-matching (POPL); small proofs (FMCAD); Cranelift RFC.
  • 2023 egglog (PLDI); Cranelift aegraph on by default; EGRAPHS workshop series.
  • 2024–26 guided eqsat, treewidth and differentiable extraction, slotted e-graphs, semantic foundations, MLIR dialects, a Lean tactic, and Fallin's "is the aegraph pulling its weight?" evaluation.

§14 · Question ladder

Test yourself

21 questions from mechanism to open problems. Reveal, then mark ✓ or ✗; marks feed your progress ring.

Answer in your head first, then reveal and mark yourself honestly. Marks are saved in this browser and feed the progress ring.

Mechanism
1. What exactly happens to the hashcons when union(e6, e4) runs, and when?

Nothing at union time: union only links e4 under e6 in the union-find, merges node sets, and pushes e6 on the worklist. At rebuild, repair(e6) walks e6's (now combined) parent list, removes each parent's stale key such as (<< e0 e4), re-canonicalizes it to (<< e0 e6), and reinserts it pointing at the parent's canonical class. If two re-canonicalized parents collide, their classes are unioned and pushed on the worklist.

→ related card
2. Why does e-class e0 end up containing a node whose child is e0, and what set of terms does it represent?

mul-one matched (* e0 e6) where e6 contains 1, and unioned that node's class (e3) with e0. So e0 holds (* e0 e6). The class represents a, a*1, a*(2/2), (a*1)*1, and so on: every finite unrolling of the cycle. That is an infinite set, stored in 3 nodes.

→ related card
3. In egg's loop, why are all matches collected before any are applied?

Searching while the e-graph is mutating would see half-updated, non-canonical state and invalidate iterators. Applying rule A's results before searching rule B would make the outcome depend on the order rules are listed. Collecting first means each iteration is a function of the e-graph at its start, and the invariants hold during search, so rebuilding can be deferred to once per iteration.

→ related card
4. What does subsume do in a Cranelift ISLE rule, and why must rules that drop uses use it?

It marks the rewritten value as strictly better, so the e-class keeps only that value and drops the alternatives. It is required for correctness when the right-hand side uses fewer values than the left-hand side: elaboration might otherwise pick the old form, whose operands may not be available at the placement point (dominance). It also keeps classes small.

→ related card
Why
5. Why do e-nodes point to e-classes rather than to e-nodes?

That is what makes one equality cover every term containing the subterm: a parent automatically "contains" every alternative of its child, so the number of represented terms is the product of class sizes while storage is their sum. Pointing at nodes would require copying parents for each alternative child.

→ related card
6. Why does deferring rebuilding turn O(n²) work into O(n)?

Merges with overlapping upward paths dirty the same classes. Deduplicating the worklist to canonical ids means each dirty class is repaired once per rebuild, not once per merge. For n merges into one class with n parents, immediate repair touches n×n parent entries, while deferred repair touches n.

→ related card
7. Why is greedy extraction optimal for tree cost but not DAG cost?

With tree cost, a class's best cost is independent of who uses it, so choosing each class's minimum bottom-up is optimal (dynamic programming over a monotone cost). With DAG cost, a shared class is paid once. Choosing a slightly costlier node that reuses an already-paid class can beat the locally cheapest one, so choices are coupled across the whole graph, giving set-cover-like hardness.

→ related card
8. Why did Cranelift choose eager, directional rewriting instead of saturation?

The compile-time budget: egg round-tripping cost 23% with no rewrites, against roughly 10% for the whole optimizer. Directional rules (right-hand side no worse than left) mean the first good rewrite is almost always the final answer (2 misses in ~4M nodes), so saturation and rebuilding buy little. Avoiding AC rules prevents blowup, and limits of 5 bound the worst cases.

→ related card
Counterfactual
9. What breaks if you keep the union-find but drop parent lists?

After a union you couldn't find the e-nodes whose children changed without scanning the whole hashcons. Congruence repair becomes O(graph) per rebuild, or stale keys remain and congruent nodes stay in separate classes, so equalities are missed.

→ related card
10. If every rule were directional and cost-decreasing, what would full eqsat buy over a single eager pass?

Little. If every rule moves strictly downhill in one cost, the greedy eager result is usually already a local optimum. Eqsat still helps when two downhill paths diverge and only one leads to a deeper minimum, or when an uphill-then-downhill sequence is needed, which directional rule sets forbid by construction. That is the 1.13 nodes-per-class result from Cranelift.

→ related card
11. What happens to the (a*2)/2 result if mul-two is applied destructively before div-assoc?

The term becomes (a<<1)/2. div-assoc needs a * under the /, which is gone, so a is unreachable. That is phase ordering, and it is exactly Zucker's example of eager aegraph rewriting missing an optimization.

→ related card
Adversarial
12. Construct a rule set and input that collapse the e-graph to one class.

Use rules x/x → 1 and 0/x → 0 with input containing 0/0. Then 0/0 joins both the class of 1 and the class of 0, so 0 ≡ 1. Congruence then merges x+0 with x+1, x*0 with x*1, and so on. With x*0 → 0 and x*1 → x, every x merges with 0, and everything ends in one class.

→ related card
13. How would you make egg's BackoffScheduler miss the optimal result on a term where it saturates without limits?

Make the needed rule match explosively (for example, a commutativity-style rule matching everywhere) so it exceeds its 1,000-match limit and is banned for 5 iterations, right when its one useful application is needed. Meanwhile a node limit may fire. The result depends on the ban schedule, not on whether the optimum is reachable.

→ related card
14. Given Cranelift's limits of 5, design a rule set that silently loses an optimization.

Write more than 5 rules whose left-hand sides match the same node, with the useful one produced last in ISLE's ordering: MATCHES_LIMIT truncates the rest. Or require a 6-deep rewrite chain to reach the good form, since REWRITE_LIMIT stops at depth 5. Or use one rule with cost(g) > cost(f) whose eager choice blocks a later win.

→ related card
Connection
15. How is relational e-matching related to worst-case optimal joins in databases?

Each operator is a relation (class id, child ids…), a pattern is a conjunctive query, and repeated pattern variables are join keys. Generic Join is worst-case optimal (it runs within the AGM bound), so e-matching inherits its output-size optimality. Cyclic patterns behave like the triangle query.

→ related card
16. How does an e-graph differ from a Cascades memo?

Both group equivalent expressions whose children are groups. Cascades explores top-down, goal-directed, with physical properties and branch-and-bound pruning, and usually doesn't maintain congruence closure across merges. E-graphs explore bottom-up via saturation, maintain congruence, and extract afterwards.

→ related card
17. How does egglog's :merge generalize egg's e-class analysis join?

Egg has one analysis per e-graph, joined with a semilattice join on class merge. Egglog lets any function have a :merge expression that resolves conflicting outputs for the same inputs (min, max, set union, or any expression). Congruence itself is the merge rule for constructor functions (union the ids). So analyses become ordinary Datalog functions, and a program can have many of them.

→ related card
18. How does eqsat relate to the database chase?

Suciu, Wang and Zhang give two-way reductions: eqsat terminates iff some chase sequence terminates iff all "EGD-fair" ones do. Rewrite rules behave like tuple-generating plus equality-generating dependencies, and e-graph merges are the EGD steps. This imports chase termination results, for example weak acyclicity becomes weak term acyclicity.

→ related card
Open
19. Can you predict, before running, whether a rule set will saturate on your inputs?

Not in general: termination over all terms is Π₂-complete. Sufficient syntactic tests exist (weak term acyclicity), and rule sets that are directional with respect to a well-founded order terminate. Practical prediction for real rule sets is open.

→ related card
20. Is there a cost model for extraction that captures register pressure without making extraction intractable?

Open. Register pressure depends on the schedule and live ranges, so it depends on the global choice; it is non-local and nonlinear. Options being explored: nonlinear costs (SmoothE), extraction with measured cost (Luminal), or folding lowering into extraction (Cranelift #8529). None is both accurate and tractable yet.

→ related card
21. Do slotted e-graphs' constant-factor costs disappear with egg-level engineering?

Unknown. The paper attributes part of the 2.7× memory and 7.8× time overhead to missing engineering (deferred rebuilding, compiled e-matching), and part to slots themselves (renamings per edge, permutation groups). No optimized implementation has been benchmarked yet.

→ related card
