Linux EEVDF scheduler: virtual lag, eligibility, virtual deadlines

TL;DR. Since Linux 6.6 the default CPU scheduler picks the eligible task (not ahead of its fair share) with the earliest virtual deadline. Fairness (weight) and latency (slice) become two independent dials. Why it matters: every modern Linux box (Ubuntu 24.04, Debian 13, Android 6.6+ GKI, Kubernetes nodes) runs it, and tail-latency regressions after 6.5→6.6 were EEVDF's.

Plain English first

Explain it simply

Picture one barista (the CPU) and a line of customers (programs). Everyone should get a fair share of the barista's time. The old Linux rule (CFS) was: "serve whoever has been served the least so far." Fair, but no way to say "this customer only wants a 20-second chat, serve them quickly." Linux bolted on piles of guesses about who "seems interactive."

EEVDF replaces the guesses with two honest ideas. Fairness: keep a ledger of who is owed time and who has had too much; only people owed time (or square) may be served next. Urgency: every customer states how long a turn they want, which gives a "finish-by" time; short turns finish by earlier. Among those allowed, serve the earliest finish-by. Short turn = served sooner, but total time over the day stays equal. Latency and fairness are separate dials.

Everyday example

Three people share a whiteboard: Ann and Bob want 3-minute turns, Cy wants 1-minute turns. All start equally owed. Cy's finish-by is earliest (1 vs 3), so Cy goes first for a minute. Now Cy has had more than average, so Cy is not allowed until the others catch up. Ann goes, then Bob. When all are square, Cy's next finish-by is again earliest, so Cy jumps back in. By the end of the day each had exactly the same total minutes, but Cy got many more, shorter turns and never waited long.

Now the same thing, technically.

Real-world context

What it is

A proportional-share scheduling algorithm (Stoica & Abdel-Wahab, 1995). Linux 6.6 replaced CFS's "pick smallest vruntime" with it. Each task has a weight (CPU share) and a slice (requested turn length). The scheduler runs the eligible task with the earliest virtual deadline.

Why it exists

CFS equalised vruntime but had no latency notion, so Linux accreted sched_latency_ns, sched_min_granularity_ns, sched_wakeup_granularity_ns, GENTLE_FAIR_SLEEPERS… that conflicted. LWN reports ~450 lines of heuristics removed (secondary claim, not re-counted). Latency-sensitive work needed a way to ask for short turns without raising weight (which steals share).

Where it's used

How it's used

// per-task custom slice (Linux >= 6.12): 0.5 ms turns, normal weight
struct sched_attr a = {
    .size = sizeof(a),
    .sched_policy = SCHED_OTHER,
    .sched_nice = 0,
    .sched_runtime = 500 * 1000,   // ns; clamped to [100us, 100ms]
};
syscall(SYS_sched_setattr, 0, &a, 0);

# shell
nice -n -5 ./app                            # weight = CPU share
cat /sys/kernel/debug/sched/base_slice_ns   # default slice
cat /sys/kernel/debug/sched/features        # PLACE_LAG RUN_TO_PARITY DELAY_DEQUEUE
echo NO_RUN_TO_PARITY > /sys/kernel/debug/sched/features

Default base slice (verified in fair.c): 700000 ns × (1 + ilog2(min(ncpu,8))) = 0.7 / 1.4 / 2.1 / 2.8 ms for 1 / 2 / 4 / ≥8 CPUs. Docs often say "3 ms" (older 0.75 ms × 4).

Use it / custom slice
  • latency-sensitive, non-RT (UI, RPC workers, mixers)
  • general multi-tenant, cgroup-heavy hosts
  • want latency without paying CPU share
Skip it
  • hard deadlines → SCHED_DEADLINE (CBS+EDF admission)
  • static-priority RT → SCHED_FIFO/RR
  • workload-specific policy → sched_ext
  • wrong sign: p99 tracks nr_running even with tiny slices

Who should care: backend/infra engineers chasing tail latency, SREs reading regressions after kernel upgrades, audio/game developers, kernel and BPF-scheduler authors, anyone with tight cgroup CPU limits.

TECHNICAL DEEP DIVE

Bare-minimum context

  • Scheduler picks the next task per-CPU runqueue; a separate load balancer migrates tasks between runqueues.
  • Weight w from nice (nice 0 → 1024, ≈1.25× per step).
  • vruntime v = CPU time × 1024/w: heavy tasks age slower.
  • GPS: ideal fluid scheduler gives each task w_i/Σw at every instant.
  • Entities live in a red-black tree; a sched_entity is a task or a cgroup group.
  • cgroups nest entities; each level has its own runqueue.

The one-liner, and what it hides

"EEVDF runs the eligible task with the earliest virtual deadline."
  1. "Virtual": V is a weighted average of vruntimes and moves when tasks join, leave, reweight.
  2. "Eligible": lag ≥ 0, tested in fixed point without division and with overflow handling.
  3. Sleep: forget lag at sleep and it can be gamed; remember it and placement must compensate for the task's own effect on V.
  4. Slice vs weight: slice sets when, weight sets how much.
  5. One CPU only: cross-CPU fairness is the unchanged load balancer's job.

The problem

CFS picks the smallest vruntime: long-run fair, but the only latency lever is where a waking task is placed relative to min_vruntime, steered by tunables with mixed units scaled by log2(ncpu). A task wanting 100 µs turns and one wanting 10 ms were treated alike unless priority was abused, and lag was not even a tracked quantity. Needed: (a) a bounded-error fairness guarantee, (b) a per-task latency request orthogonal to weight, (c) fewer magic numbers.

Mental model

Bank ledger + due dates. Lag = your account with the CPU: positive means it owes you; negative means you overdrew. Only non-negative accounts are served (eligibility). Each request has a due date (virtual deadline); serve the earliest among the eligible.

Where it breaks: the reference V is the weighted mean of whoever is currently queued, so your balance changes when others arrive or leave. That is why sleep/wake, reweighting and cgroups produce most real bugs.

Kernel flow

tick / wakeup

  update_deadline():  if v >= vd: vd = v + slice*1024/w     # new request

/* Heap search for the EEVD entity */
while (node) {
    struct rb_node *left = node->rb_left;
    /* Eligible entities in left subtree are always better choices,
       since they have earlier deadlines. */
    if (left && vruntime_eligible(cfs_rq, __node_2_se(left)->min_vruntime)) {
        node = left; continue;
    }
    se = __node_2_se(node);
    if (entity_eligible(cfs_rq, se)) { best = se; break; }
    node = node->rb_right;
}

The tree is keyed by deadline; each node stores subtree min_vruntime, so subtrees with no eligible task are pruned: O(log n).

Sleep and wake

On dequeue update_entity_lag() stores vlag = V − v (clamped). On enqueue place_entity() restores it:

vl' = vl · (W + w_i) / W v_i = V − vl' vd_i = v_i + slice·1024/w_i (new tasks: half a slice, PLACE_DEADLINE_INITIAL)

DELAY_DEQUEUE (6.12): a task sleeping with negative lag stays on the tree as sched_delayed, ineligible, burning lag off in virtual time; really dequeued only when picked (lag ≥ 0 by definition) or woken. DELAY_ZERO clips lag to ≤ 0.

Try it: slice vs share

Try: shrink C's slice (more switches, same share); raise C's weight (more share); untick eligibility (C with tiny slice starves A and B: pure virtual-EDF, no lag bound).

The math

Paper setup

V(t) = ∫₀ᵗ dτ / Σⱼ wⱼ(τ) lag_i(t) = S_i(t₀,t) − s_i(t₀,t)

V counts how much service one unit of weight should have received; lag = ideal minus actual service, positive = owed.

Kernel form

lag_i = w_i (V − v_i) vlag_i = V − v_i V = Σ wⱼvⱼ / Σ wⱼ

V is the weighted mean vruntime; being left of the mean means being owed. Tracking virtual lag avoids carrying w_i everywhere.

Eligibility

lag_i ≥ 0 ⇔ V ≥ v_i ⇔ Σ wⱼ(vⱼ−v₀) ≥ (v_i−v₀) · Σ wⱼ

The kernel uses the cross-multiplied right side because dividing loses precision (comment in fair.c). Sums are kept relative to a moving zero_vruntime and the product uses __int128 or check_mul_overflow.

Virtual eligible time and deadline

V(e) = V(t₀) + s(t₀,t)/w V(d) = V(e) + c/w kernel: vd_i = ve_i + r_i/w_i

A request of size c costs c/w of virtual time, so heavier tasks get earlier deadlines per real ms and run more.

Placement derivation (from the kernel comment)

V' = (W·V + w_i(V − vl_i)) / (W + w_i) = V − w_i·vl_i/(W + w_i) vl'_i = V' − v_i = vl_i · W/(W + w_i) < vl_i fix: place with vl_i = vl'_i · (W + w_i)/W

A creditor joining pulls the mean toward itself and its apparent credit shrinks; inflate before placement or the lag evaporates. This is lag *= load + weight; lag /= load.

Lag conservation and bounds

Σ_i lag_i(t) = 0 −c < lag_k(t) < max(c_max, q) f < d + q

Slides of Stoica & Abdel-Wahab (UNC): nobody is ever more than about one max slice ahead or behind the fluid schedule, and a request finishes at most one quantum q after its virtual deadline d. Proof sketch: partition by deadline before/after d; lags sum to zero, the "after" group cannot be owed more than q, so all "before" requests finish by d+q.

Why not simpler: picking by earliest virtual finish with no eligibility (WFQ) can serve a task ahead of its fluid schedule (WF2Q's observation). The eligibility gate gives the lower lag bound.

Why it works

Two properties factor the problem: eligibility ⇒ bounded unfairness (a task ahead of V can't be picked); deadline order among eligibles ⇒ latency chosen by the task. Ablations:

RemoveWhat breaks
eligibilitypure virtual-EDF: tiny-slice stream starves others, lag unbounded
deadlines (min vruntime)= CFS: fair, no latency control
PLACE_LAGsleep resets debt; sleep briefly each slice to wipe negative lag
DELAY_DEQUEUEsame exploit via ineligible-then-sleep, or lag kept forever and long sleepers punished
RUN_TO_PARITYevery wakeup with slightly earlier deadline preempts; switch storms (hackbench-style regressions after merge)

Alternatives: CFS (heuristic latency); BORE/MuQSS (burst-score heuristics, popular on desktop kernels); SCHED_DEADLINE (wall-clock EDF+CBS reservations); stride/lottery (no latency input); BPF sched_ext (any policy). EEVDF won mainline with one theory-backed rule and fewer tunables.

Where it breaks

  • Merge regressions (6.6): over-scheduling when lag ≈ slice (fixed by wakeup-preemption curbing / RUN_TO_PARITY); vhost/netperf, schbench/tbench shifts blamed on lag-based placement. Magnitudes come from forum/LKML summaries: unverified.
  • CVE-2024-35985 (verified): reweight_eevdf() scaled vlag without the clamp used elsewhere; s64 multiply overflowed (weight is 20-bit fixed-point), entity_eligible() said nothing is eligible, pick_eevdf() returned NULL → NULL deref. "Rare, but fatal." Fixed in 6.9-rc6 (commit 1560d1f6eb6b), backported.
  • Per-CPU only: bursty tasks pile onto one CPU until the balancer (tens to 100+ ms) reacts.
  • cgroups: reweighting a group entity changes the units of queued members; clamping and deadline pushes interact. Placement fixes landed around 6.13 (Phoronix) and later (later commit history unverified).
  • Tick granularity: a 3 ms slice at HZ=1000 can fire up to 1 ms early/late; HRTICK exists but is false by default.
Misconceptions. "Short slice = more CPU": no, same weight ⇒ same share, just in smaller earlier pieces plus switch cost. "EEVDF is real-time": no, deadlines are virtual, relative to the queued set on one runqueue.

In the wild

Linux vs the 1995 paper: tick/clock-driven time instead of exact quanta (update_deadline() comment: "strictly vd_i += N*r_i/w_i… good enough"); lag clamped and remembered across sleep; RUN_TO_PARITY (not in paper) using the shortest queued slice; hierarchical group entities with h_load; augmented rbtree (key deadline, aug subtree min_vruntime); DELAY_DEQUEUE as a Linux-specific answer to sleep gaming. Kernel docs: "There are ongoing discussions on how to manage lag, especially for sleeping tasks."

Open problems

  1. Latency SLOs: slice is a proxy; "p99 ≤ 5 ms" is not expressible without RT or weight changes.
  2. Cross-CPU fairness: the theorem is per-runqueue; global share relies on a periodic balancer that equalises load, not lag.
  3. cgroup hierarchy correctness: reweight cascades (CVE-2024-35985 was one).
  4. Heterogeneous / SMT / NUMA: capacity and cache effects are not in the lag model.
  5. Tick-free precision without hrtick cost.
  6. Interactive tuning: desktop kernels still ship BORE or tuned slices (anecdotal).
  7. Policy-synthesis safety: the BPF verifier proves memory safety, not starvation-freedom.
