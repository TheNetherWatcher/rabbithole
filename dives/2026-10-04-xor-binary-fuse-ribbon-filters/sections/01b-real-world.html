What it is

A way to store an immutable set of keys so you can ask "might x be in it?" in about 3 memory reads, using about 9 bits per key for a 0.4% false-positive rate. Instead of inserting keys, you solve for a table such that the XOR of three cells equals each key's fingerprint.

Why it exists

Bloom filters guard disk and network lookups but waste 44% over the information-theoretic minimum and need k scattered probes. For data that never changes, the table can be computed, not grown: 23% overhead (XOR, 2019), 13% and 8% (binary fuse, 2022), or under 10% with a tunable knob (Ribbon, 2021), and under 1% with experimental variants. Filters in an LSM tree stay in RAM for hours, so every saved bit is multiplied by lifetime.

Where it's used (verified)

  • RocksDB: NewRibbonFilterPolicy, with Ribbon for compaction output and Bloom for flushes. The RocksDB blog reports about 30% memory saved versus Bloom (7 vs 10 bits/key typical), about 4.4× construction CPU (140 vs 32 ns/key), and about 20% more query CPU; break-even at roughly one hour of filter lifetime.
  • Mozilla Firefox CRLite: certificate revocation moved from Bloom cascades to "Clubcard", a partitioned two-level cascade of Ribbon filters. Users download about 300 kB/day (a 4 MB snapshot every 45 days plus deltas).
  • FastFilter/xor_singleheader (C), xorfilter (Go), xorf (Rust), fastfilter_java and fastfilter_cpp: reference implementations of XOR and binary fuse filters.
  • Bioinformatics, analytics, networking: the ZOR abstract lists storage systems, analytics, networking and bioinformatics as consumers of peeling-based filters.
  • Not adopted (as far as I found): ClickHouse, DuckDB and Parquet use split-block Bloom filters; I found no evidence of XOR or fuse there.

How it's used

#include "binaryfusefilter.h"             // FastFilter/xor_singleheader
binary_fuse8_t f;
binary_fuse8_allocate(n, &f);             // ~1.13*n bytes
binary_fuse8_populate(keys, n, &f);      // keys: uint64_t[n], pre-hashed; false after 100 failed seeds
bool maybe = binary_fuse8_contain(x, &f); // 3 loads + XOR + compare; FPR ~ 1/256
binary_fuse8_free(&f);
// RocksDB: Ribbon with Bloom-equivalent 10 bits/key; Bloom for L0/flush
table_options.filter_policy.reset(rocksdb::NewRibbonFilterPolicy(10.0));
// bloom_before_level (since 6.24): use Bloom on levels below the given one

Typical: 8-bit fingerprints (ε ≈ 0.39%, about 9 bits/key) or 16-bit (ε ≈ 1.5e-5, about 18 bits/key); keys pre-hashed to 64 bits.

When to use, and when not

Use when the set is built once and queried many times (SSTables, immutable segments, blocklists, k-mer sets). Avoid when you need inserts or deletes (Bloom, cuckoo, quotient filters), when the build must stream (Bloom), or when build memory is tight (peeling holds all hashes: about 24 B/key transient per implementation notes, unverified exactly). Pick binary fuse for speed, Ribbon for tunable, smaller space and LSM integration, and Bloom for very short-lived filters such as L0.

Who should care

Storage and DB engineers (LSM filters), infra teams (blocklists, certificate revocation), search and genomics engineers (membership over huge immutable sets), and anyone paying RAM per key.
