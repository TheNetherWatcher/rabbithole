Static approximate-membership filters: XOR and binary fuse (peeling) vs Ribbon (banded elimination)

A static filter for a fixed key set stores one fingerprint per key in a table where three cells XOR to that fingerprint. Solving the table is a peeling game on a random 3-uniform hypergraph, and it succeeds only above 1.22 slots per key. Binary fuse windows push this to 1.125, and Ribbon trades hypergraphs for banded Gaussian elimination to reach under 10% overhead.

Why it matters: LSM trees keep filters in RAM for hours, so every saved bit is paid again and again. RocksDB and Firefox certificate revocation now run on these structures.

Plain English
In everyday words

A guest list kept as a board of numbered slots

A bouncer cannot carry a million names, so he carries a board of numbered slots. Each guest's name hashes to three slots whose numbers XOR to a short code. Everyone on the list always matches; a stranger matches with probability 1 in 256 at 8 bits.

The board is filled by peeling guests who own a private slot, then filling in reverse.

Explain it simply. Picture a bouncer at a club with a guest list of a million names. The list is too big to carry, so the bouncer carries a small cheat-sheet instead: a board of numbered slots with a number in each. To check a visitor, the bouncer hashes the name into three slot numbers, adds up (XORs) the three numbers on the board, and compares the result to a short "secret code" derived from the name. If they match, the visitor is waved through. Everyone on the list always matches. A stranger matches only by luck: with an 8-bit code, 1 in 256.

The clever part is how the board is filled in. We need, for every guest, "slot a + slot b + slot c = my code", all at the same time. That is a big puzzle. The trick: find a guest who owns one slot alone (nobody else touches it), park that guest on a stack, forget about them for now, and repeat. Eventually every guest is on the stack. Then fill the board in reverse: the last guest parked gets their lonely slot set to whatever makes their sum work; each earlier guest has already-fixed neighbours when their turn comes. The board only needs about 1.23 slots per guest for this to work out almost every time. Ribbon filters solve the same puzzle differently: as a school-style system of equations where every equation only touches a short nearby stretch of slots, so it can be solved in one pass, with as little as 5 to 10% spare room.

Everyday example. Three guests (Ana, Ben, Cy) and a board of six slots in three pairs (A0 A1 | B0 B1 | C0 C1). Ana → A0, B0, C0 and code 5. Ben → A0, B1, C1 and code 3. Cy → A1, B0, C1 and code 6. Slot C0 is touched only by Ana, A1 only by Cy, and after those two are parked, A0 is touched only by Ben. Park Ana, Cy, Ben (in that order). Fill backwards: Ben first (set A0 to 3), then Cy (set A1 to 6), then Ana (set C0 so the sum is 5, which turns out to be 6). Board: A0=3, A1=6, B0=0, B1=0, C0=6, C1=0. Ana: 3+0+6 → 5 ✓. A stranger who hashes to A1, B1, C0 sums to 0 and is rejected unless their own code is 0.

Context
§1 · Prerequisites

Six things to know first

  • AMQ filter: no false negatives, false-positive rate ε.
  • Fingerprint: a random f-bit hash, so a stranger collides with probability 2-f.
  • Random hypergraph: each key is an edge over three slots; peeling removes degree-1 slots.
  • Static: the key set is fixed before the build.
  • AMQ filter: answers "is x in S?" with no false negatives and false-positive rate ε. Information-theoretic minimum ≈ log₂(1/ε) bits per key (Carter et al. 1978; Pagh–Pagh–Rao 2005).
  • Bloom filter: k hash positions in a bit array; needs ≈ 1.44·log₂(1/ε) bits/key, 44% over the minimum.
  • Fingerprint: f-bit hash of the key; collision with a random stranger has probability 2-f.
  • XOR / GF(2) linear algebra: addition mod 2; a system of XOR equations can be solved with Gaussian elimination.
  • Random hypergraph: each key is an edge joining 3 slots (vertices). Peeling removes degree-1 vertices repeatedly; the leftover is the 2-core.
  • Static: the full key set is known up front; no inserts or deletes after build (LSM SSTables, Parquet segments, blocklists).
§1b · Real-world context

Where it runs: RocksDB, Firefox CRLite and the xor libraries

RocksDB's Ribbon filter saves about 30% of filter RAM against Bloom. Firefox revocation checks ship a Ribbon cascade of about 300 kB/day. The xor and fuse libraries in C, Go and Rust are the reference code. Pick them for immutable sets; avoid them when keys change.

What it is

A way to store an immutable set of keys so you can ask "might x be in it?" in about 3 memory reads, using about 9 bits per key for a 0.4% false-positive rate. Instead of inserting keys, you solve for a table such that the XOR of three cells equals each key's fingerprint.

Why it exists

Bloom filters guard disk and network lookups but waste 44% over the information-theoretic minimum and need k scattered probes. For data that never changes, the table can be computed, not grown: 23% overhead (XOR, 2019), 13% and 8% (binary fuse, 2022), or under 10% with a tunable knob (Ribbon, 2021), and under 1% with experimental variants. Filters in an LSM tree stay in RAM for hours, so every saved bit is multiplied by lifetime.

Where it's used (verified)

  • RocksDB: NewRibbonFilterPolicy, with Ribbon for compaction output and Bloom for flushes. The RocksDB blog reports about 30% memory saved versus Bloom (7 vs 10 bits/key typical), about 4.4× construction CPU (140 vs 32 ns/key), and about 20% more query CPU; break-even at roughly one hour of filter lifetime.
  • Mozilla Firefox CRLite: certificate revocation moved from Bloom cascades to "Clubcard", a partitioned two-level cascade of Ribbon filters. Users download about 300 kB/day (a 4 MB snapshot every 45 days plus deltas).
  • FastFilter/xor_singleheader (C), xorfilter (Go), xorf (Rust), fastfilter_java and fastfilter_cpp: reference implementations of XOR and binary fuse filters.
  • Bioinformatics, analytics, networking: the ZOR abstract lists storage systems, analytics, networking and bioinformatics as consumers of peeling-based filters.
  • Not adopted (as far as I found): ClickHouse, DuckDB and Parquet use split-block Bloom filters; I found no evidence of XOR or fuse there.

How it's used

#include "binaryfusefilter.h"             // FastFilter/xor_singleheader
binary_fuse8_t f;
binary_fuse8_allocate(n, &f);             // ~1.13*n bytes
binary_fuse8_populate(keys, n, &f);      // keys: uint64_t[n], pre-hashed; false after 100 failed seeds
bool maybe = binary_fuse8_contain(x, &f); // 3 loads + XOR + compare; FPR ~ 1/256
binary_fuse8_free(&f);
// RocksDB: Ribbon with Bloom-equivalent 10 bits/key; Bloom for L0/flush
table_options.filter_policy.reset(rocksdb::NewRibbonFilterPolicy(10.0));
// bloom_before_level (since 6.24): use Bloom on levels below the given one

Typical: 8-bit fingerprints (ε ≈ 0.39%, about 9 bits/key) or 16-bit (ε ≈ 1.5e-5, about 18 bits/key); keys pre-hashed to 64 bits.

When to use, and when not

Use when the set is built once and queried many times (SSTables, immutable segments, blocklists, k-mer sets). Avoid when you need inserts or deletes (Bloom, cuckoo, quotient filters), when the build must stream (Bloom), or when build memory is tight (peeling holds all hashes: about 24 B/key transient per implementation notes, unverified exactly). Pick binary fuse for speed, Ribbon for tunable, smaller space and LSM integration, and Bloom for very short-lived filters such as L0.

Who should care

Storage and DB engineers (LSM filters), infra teams (blocklists, certificate revocation), search and genomics engineers (membership over huge immutable sets), and anyone paying RAM per key.

Technical deep dive
§2 · The one-liner

"A precomputed table where three cells XOR to the fingerprint" hides five things

The table exists only when the random hypergraph is peelable, which needs at least 1.22 slots per key. Binary fuse pushes that to 1.13 with windows. Ribbon drops hypergraphs for banded elimination. Duplicates, retries, adversarial seeds and build memory are the costs.

"XOR filters are Bloom filters that are smaller and faster because you precompute a table where three cells XOR to the fingerprint." It hides five things:

  1. Why the table can always be computed: only if the 3-uniform hypergraph is peelable, which needs at least 1.22× slots per key. That is a phase transition, not a heuristic.
  2. Why the FPR is exactly 2-f (and when it isn't).
  3. How binary fuse beats the threshold (1.22 down to 1.13 and 1.08) by restricting each key to a window of consecutive segments (spatial coupling).
  4. That Ribbon abandons hypergraphs entirely: banded linear algebra, a different space/time tradeoff.
  5. What breaks: duplicates, construction-failure retries, adversarial keys, a memory spike at build, the 64-bit hash assumption, and no updates.
§3 · The problem

Bloom filters waste 44% over the information minimum

An optimal Bloom filter at ε = 1% needs about 9.6 bits per key, against a 6.64-bit minimum. Each probe is a cache miss. In a 10-billion-key LSM tree, 3 bits per key is 3.75 GB of RAM. Static sets do not need insertability, and that is what costs the 44%.

A Bloom filter at ε = 1% needs about 9.6 bits per key with the optimal number of probes (k ≈ 7) into a large bit array, and each probe is a likely cache miss. The information minimum is log₂(100) ≈ 6.64 bits per key. For ε = 2-8, Bloom needs about 11.5 bits against an 8-bit minimum. In a 10-billion-key LSM tree, 3 bits per key is 3.75 GB of RAM.

Forcing constraint: static sets do not need Bloom's incremental insertability. The requirement that keys be insertable one at a time is what costs the 44%.

§4 · Mental model

A bulletin board of sticky notes solved all at once

Each guest owns three notes that must XOR to their code. Peeling sets aside a guest with a private note, and filling in reverse lets that note absorb the slack. The board has only 1.23 slots per guest, so the analogy breaks: solvability is a global property of the random hypergraph.

Think of a bulletin board of sticky notes. Each guest has three notes assigned, and the notes must XOR to the guest's code. Filling the board means solving every guest's equation at once. Peeling means repeatedly setting aside a guest who owns a private note, then filling the board in reverse so that the private note absorbs the slack.

The analogy breaks on sharing. The board has only about 1.23 slots per guest while each guest touches 3, so slots are heavily shared. Solvability is not a local guarantee. It comes from a global property of the random hypergraph: no dense core below roughly 82% load.

§5 · Mechanism, traced

Peeling three keys by hand, then filling the board backwards

Three keys over six slots. Peel C0, then A1, then A0, which empties the 2-core. Assign in reverse: A0 = 3, A1 = 6, C0 = 6. Ana checks out (3 ^ 0 ^ 6 = 5), and a stranger with code 4 is rejected.

7-step interactive walkthrough inside.

Three keys, six slots, 3-bit fingerprints. Each block holds one slot per key position:

Ana: A0 B0 C0   fp=5 (101)      slots: A0 A1 | B0 B1 | C0 C1
Ben: A0 B1 C1   fp=3 (011)
Cy : A1 B0 C1   fp=6 (110)
degrees: A0=2 A1=1 B0=2 B1=1 C0=1 C1=2
Step 0 / 7

Peeling. The queue starts with the degree-1 vertices {A1, B1, C0}. Pop C0 (only Ana) and push (Ana via C0). Pop A1 (only Cy) and push (Cy via A1). Pop A0, which now touches only Ben, and push (Ben via A0). The stack is [Ana/C0, Cy/A1, Ben/A0]; all three keys peeled means the 2-core is empty, so construction succeeds.

Assignment, in reverse stack order (the board starts all zero):

  • Ben via A0: A0 = fp(Ben) ^ B1 ^ C1 = 3 ^ 0 ^ 0 = 3
  • Cy via A1: A1 = 6 ^ B0 ^ C1 = 6
  • Ana via C0: C0 = 5 ^ A0 ^ B0 = 5 ^ 3 ^ 0 = 6
Board: A0=3 A1=6 | B0=0 B1=0 | C0=6 C1=0
Check Ana: 3^0^6 = 5 ✓   Ben: 3^0^0 = 3 ✓   Cy: 6^0^0 = 6 ✓

Why reverse order works. The vertex a key was peeled through was touched by no other unpeeled key at that moment. In reverse, any key assigned later was peeled earlier and writes only its own private vertex, so it never disturbs a key assigned before it. Each cell is written at most once.

Query a stranger y: h = (A1, B1, C0), fp(y) = 4 (100). The sum is 6 ^ 0 ^ 6 = 0 ≠ 4, so reject. If fp(y) were 0, that would be a false positive.

Binary fuse query, as shipped

hash = murmur64(key + seed);   f = (uint8_t)(hash ^ (hash >> 32));
h0 = mulhi(hash, SegmentCountLength);                        // uniform over first SegmentCount segments
h1 = (h0 + SegmentLength)   ^ ((hash >> 18) & SegmentLengthMask);  // next segment, random in-segment offset
h2 = (h0 + 2*SegmentLength) ^ ( hash        & SegmentLengthMask);  // segment after that
return f == (F[h0] ^ F[h1] ^ F[h2]);

Segment length is a power of two, 2floor(ln n / ln 3.33 + 2.25) for arity 3. The array size factor is max(1.125, 0.875 + 0.25·ln(10⁶)/ln n). Build retries up to XOR_MAX_ITERATIONS = 100 seeds. Keys are sorted into segment-order buckets first for cache locality, and the current C code detects and drops duplicate keys when a round fails (source: FastFilter/xor_singleheader, read directly).

Ribbon, traced

Each key becomes (start s, w-bit coefficient word c with bit 0 set, r-bit fingerprint b). On insert, if pivot row s is empty, store the equation. Otherwise XOR it with the stored equation, shift out the leading zeros (c ← c≫j, s ← s+j) and continue. If c becomes 0 with b = 0, the equation was redundant; with b ≠ 0 the system is inconsistent and you retry with a new seed. Back-substitute from the last row up: Z[i] = bi ⊕ ⨁j>0, ci[j]=1 Z[i+j]. A query XORs the Z rows picked by c's set bits, all inside one w-row window (64 rows × 8 bits = 64 B, about one cache line), versus three random cache lines for XOR.

§6 · The math

Peeling holds at 1.2218 slots per key, and the Bloom gap is 1.44 bits

The information bound is n·log₂(1/ε) bits. Bloom needs 1.44·log₂(1/ε). A random 3-hypergraph peels only above c* = 0.8185, so 1.2218 slots per key. XOR's FPR is exactly 2-f.

Plots of the theory and the peeling success rate inside.

(a) Information bound

n · log₂(1/ε) bits→ in plain terms: each key must "pay" for forgetting everything except its ε-sized neighbourhood. A filter for S accepts a set A ⊇ S with |A| ≈ n + εu; the states needed are about C(u,n)/C(εu,n) ≈ (1/ε)n.

(b) Why Bloom wastes 44%

m/n = log₂e · log₂(1/ε) ≈ 1.44 · log₂(1/ε)→ in plain terms: an optimal Bloom filter has half its bits set, so each bit carries less than one bit of information.

(c) Why FPR = 2-f

P[false positive] = 2-f, bits per key = f × (slots per key)→ in plain terms: for y not in S, the three cells hold values set by other keys' random fingerprints. Their XOR is effectively uniform on f bits and independent of fp(y). Space is the fingerprint width times the slot overhead: 1.23f for XOR, about 1.13f for fuse-3 and 1.08f for fuse-4.

(d) Peeling threshold

Let m be the slots, n the keys and c = n/m. Each slot has Poisson(3c) incident edges. Let q be the probability that an edge, seen from one endpoint, survives peeling. An endpoint keeps the edge alive if it has at least one other surviving edge, with probability 1 − e^(−3cq). The edge survives if both other endpoints do:

q = (1 − e^(−3cq))²→ q = 0 is always a solution (full peeling). A nonzero solution (a 2-core) appears at the smallest c where c(q) = −ln(1−√q) / (3q) bottoms out.

Numerically (my run): c* = 0.8185 for arity 3, so slots per key ≥ 1/c* = 1.2218 (about 1.23 with slack). Arity 4 gives c* = 0.7723 (1.295), and arity 5 gives c* = 0.7018 (1.425). Below about 82% load a random 3-hypergraph has no dense knot; above it, a knot of unsolvable keys appears suddenly. Larger arity peels worse, which makes arity 3 the sweet spot.

Why not use orientability instead (every key gets its own cell; threshold about 0.918, giving 1.089 for arity 3, quoted from the literature and not re-derived here)? Orientable is not the same as peelable. A solution exists, but greedy peeling cannot find it. Gaussian elimination can, at O(n³)-ish cost, or banded cost, which is where Ribbon comes in.

(e) Fuse windows

Keys pick a start segment s and use segments s, s+1 and s+2. The two end segments have lower degree, so peeling starts there and a wave moves inward. This is the spatial-coupling and threshold-saturation effect that Walzer proved (arXiv:2001.10500), which moves the peeling threshold toward the orientability bound. The result is 1.125 for arity 3 or 1.075 for arity 4 at large n, with the size factor growing for small n (the formula above).

(f) Ribbon

⟨h(x), Z⟩ = b(x) over GF(2), with h(x) = 0s · c · 0m−s−w→ in plain terms: every key is one row with a random block of width w. Dietzfelbinger and Walzer (arXiv:1907.04750) show that with m = n/(1−ε) columns, such matrices have full row rank with high probability for w = O(log n / ε), and elimination costs O(n/ε²).

Ribbon uses w = 64 (one machine word) and reaches an overhead of a few percent. The paper reports under 10% overhead at modest CPU cost, and under 1% with an experimental balanced variant. The follow-up BuRR (SEA 2022) reaches "well below 1%" by bumping the few rows that do not fit into a fallback structure. A shorter band solves faster but needs more slack; a wider band packs tighter. The width w is the dial.

§7 · Why it works

Sparse random equations are solvable by one greedy pass

At about 1.22 variables per equation, a trivial peeling order always works above threshold. Remove the three-way split and you need 2.0 slots per key. Remove the seed retry and near-threshold builds fail. Remove the random fingerprint and the FPR is no longer 2-f.

Core insight: sparse random constraint systems with about 1.22 variables per equation are solvable by a trivial greedy order. A solved table plus a random fingerprint gives an exact 2-f false-positive rate with one XOR. Ablations:

  • Remove the 3-way split and arity 2 peels only up to c < 0.5, which means 2.0 slots per key.
  • Remove the retry with a new seed, and the failures near threshold (about 18% at 1.23 for n = 20000 in my demo) become hard errors.
  • Remove the fingerprint randomness, and the FPR is no longer 2-f; adversarial queries could pick a y whose XOR equals fp(y).
  • Remove the windows, and you are back at 1.22.
  • Ribbon: remove the band, and you get dense Gaussian elimination at O(n³).

§9 · Where it breaks

Construction failures, duplicates and seed-aware attackers

Near threshold, builds fail often, so the library retries up to 100 seeds. Duplicate keys form a 2-core that peeling cannot clear. An attacker who knows the seed can force a failure, so use a secret 64-bit seed. Updates mean a full rebuild.

  • Construction can fail. Retry with a new seed (at most 100 in the C library; about 1.1 tries expected). Close to the threshold, failures are common (my demo: 82% at 1.23, n = 20000).
  • Duplicates can prevent peeling, because two identical edges form a 2-core. The current C binary-fuse code detects and removes them on a failing round; older or other ports may just error. Deduplicate first.
  • Adversarial keys. An attacker who knows a fixed seed can pick keys that build a 2-core. Use a secret, random 64-bit seed per build. The filter is also not robust for queries: a false positive is deterministic for a given seed (see Naor–Yogev-style models).
  • Build memory. Peeling holds all key hashes plus counters. Sorting into segment buckets helps cache behaviour but not memory.
  • Size limits. The library's size is uint32_t. 8-bit fingerprints cap ε at 2-8, and 64-bit hashes are assumed (a 32-bit hash over 10⁸ keys collides).
  • Small n. The size factor rises sharply below about 10⁵ keys (1.2 or more), so XOR and fuse can be bigger than Bloom at high ε.
  • No updates. Any change means a rebuild. Dynamic filters have a provable Ω(n)-bit penalty (Kuszmaul–Walzer, STOC 2024).
  • Misconceptions. "XOR always beats Bloom" (not at large ε or tiny n). "Static is useless" (most big filters live in immutable files). "Ribbon is slow" (queries are about 20% slower in RocksDB's own numbers; construction is the cost).
§10 · In the wild

RocksDB's hybrid, CRLite's cascade and the library deviations

RocksDB uses Ribbon for compaction output and Bloom for flushes, with one filter per SST file. Firefox's CRLite uses a two-level Ribbon cascade rebuilt on a schedule. The fuse code sorts into segment buckets and uses mulhi, which the paper's textbook peeling does not.

  • RocksDB: hybrid by level. bloom_equivalent_bits_per_key keeps the same FPR as Bloom while spending about 30% less. One full filter per SST file.
  • Firefox CRLite / Clubcard: Ribbon in a two-level cascade. Filters are rebuilt on a schedule, so a static structure is natural.
  • xor_singleheader: 8, 16 and 32-bit variants, serialization and mmap (flat array + seed + segment parameters), pre-hashed uint64 keys.
  • Where the code departs from the paper: fuse construction sorts hashes into segment buckets (not in the textbook peeling), uses mulhi instead of %, and XOR-offsets within a segment instead of using independent hashes.
Research edge
§11 · Frontier

Deterministic, restart-free peeling is the new race

ZOR (2026) abandons under 1% of keys into a side structure instead of restarting, landing within 1% of the bound. Dynamic filters cost n·log ε⁻¹ + Ω(n) bits, a provable gap to static. Grafite and Memento extend the idea to range filters.

Verified against arXiv or abstract pages unless flagged.

  1. ZOR filters: Limasset, arXiv:2602.03525 (Feb 2026). Deterministic peeling. Instead of restarting on failure, it abandons under 1% of keys into a small side structure, landing within 1% of the information bound with fuse-like query speed (build is slower in the prototype).
  2. Fingerprint Filters Are Optimal: Kuszmaul, Liang, Zhou, FOCS 2025, arXiv:2510.18129. Any dynamic filter needs at least n·log ε⁻¹ + n·log e − o(n) bits, so fingerprinting (Carter et al. 1978) is tight for dynamic filters.
  3. Space Lower Bounds for Dynamic Filters and Value-Dynamic Retrieval: Kuszmaul & Walzer, STOC 2024, DOI 10.1145/3618260.3649649. Dynamic filters need n·log ε⁻¹ + Ω(n) bits: a provable gap to static.
  4. Tight Bounds and Phase Transitions for Incremental and Dynamic Retrieval: Kuszmaul et al., SODA 2025, arXiv:2410.10002.
  5. Grafite: Costa, Ferragina, Vinciguerra, SIGMOD 2024, arXiv:2311.15380. A range filter with O(1) query and FPR ≤ ℓ/2B−2 for any data and any query workload, robust to adversarial or correlated queries.
  6. Memento filter: Eslami & Dayan, SIGMOD 2025, arXiv:2408.05625. A dynamic range filter; in WiredTiger it doubles range-query throughput when 50% of queries are empty.
  7. Aleph filter: Dayan, Bercea, Pagh, arXiv:2404.04703 (VLDB 2024, per search results). An expandable filter with constant-time operations and memory-vs-FPR close to static filters if growth is predicted.
  8. Peeling close to the orientability threshold: Walzer, arXiv:2001.10500. Spatial coupling is the theory behind fuse-style windows.
  9. BuRR / Fast succinct retrieval and AMQ using Ribbon: Dillinger, Hübschle-Schneider, Sanders, Walzer, SEA 2022, arXiv:2109.01892. Space overhead well below 1%.
  10. Unverified by me, flagged: Diva (VLDB 2025), Zeno filter (SIGMOD 2026), and parallel BuRR construction (arXiv:2411.12365). They appear in search results, but I did not open them.
§11b · Open problems

Fast construction near the bound is still unsolved

Ribbon and ZOR reach about 1% overhead but pay in build time, while fuse builds fast at 8% or more over. Adversarially robust static filters, GPU peeling and learned filters with drift guarantees are all open.

  • Fast construction near the bound. Ribbon and ZOR reach about 1% overhead but pay in build time (RocksDB: about 4.4× Bloom's build CPU). Fuse is fast but at least 8% over. Nobody has both at all scales.
  • Deterministic, restart-free build with no side structure (ZOR still needs one).
  • Adversarial robustness. Static fuse and Ribbon filters give no guarantee against adaptive query adversaries. Adaptive or robust Bloom constructions (Naor–Yogev) cost extra and rely on one-way-function-like assumptions.
  • Range filters with worst-case guarantees at static-filter space. Grafite closes much of the gap; correlated and adaptive workloads are still contested.
  • External-memory, SIMD and GPU peeling. The peeling phase is inherently sequential and cache-hostile. I found no mature GPU XOR or fuse builder.
  • Learned filters (partitioned learned Bloom filters, NeurIPS 2024): the gains depend on the query distribution, and adversarial robustness and drift are unresolved.
§12 · Lineage

Bloom 1970, XOR 2019, binary fuse 2022, ZOR 2026

Carter's fingerprint bound (1978) → Botelho–Pagh–Ziviani peeling (2013) → XOR filters (Graf–Lemire 2019) → Ribbon (Dillinger–Walzer 2021) → binary fuse (2022) → ZOR (2026).

§14 · Question ladder

Test yourself

21 questions from mechanism to open research. Reveal, then mark ✓ or ✗; marks feed your progress ring.

Answer in your head first, then reveal and mark yourself honestly. Marks are saved in this browser and feed the progress ring.

Mechanism
1. In the 3-key trace, why is it safe to assign Ana's slot C0 after Ben's and Cy's?

Ana's slot C0 was touched by no other unpeeled key when she was peeled, so no later-assigned key writes it, and no earlier-assigned key reads it before it is set. Her other two cells, A0 and B0, are already final when she is assigned.

→ related card
2. Why does each cell get written at most once?

Each key is assigned exactly one cell: the one through which it was peeled. A cell is peeled through only one key, since it has degree 1 at that moment.

→ related card
3. In a Ribbon insert, what does c & -c compute and why do we shift?

It isolates the lowest set bit. Its bit-length minus one is the number j of trailing zeros. The reduced equation now starts at row i+j, so shifting the word right by j realigns coefficient bit 0 with that pivot.

→ related card
4. In binary_fuse8_contain, why XOR the in-segment offset instead of adding it?

XOR with a mask smaller than SegmentLength permutes positions inside the segment-aligned block and stays in-segment. Adding could cross into the next segment and break the window structure.

→ related card
Why
5. Why 3 hash positions and not 2 or 4?

Arity 2 peels only below load 0.5, which means 2.0 slots per key. Arity 4 raises the requirement to 1.295 slots per key without windows, and costs another memory read. Arity 3 minimizes slots per key for plain peeling.

→ related card
6. Why is the FPR exactly 2-f, and what must be true of the fingerprint hash?

The XOR of three cells is uniform on f bits and independent of fp(y), because the cells were set from other keys' independent random fingerprints. The fingerprint hash must behave like a random function independent of the positions.

→ related card
7. Why does a windowed hypergraph peel at lower density than a uniform one?

The end segments have lower degree, which seeds peeling. Once boundary keys peel, their neighbours drop to degree 1 in a wave (spatial coupling, threshold saturation), reaching beyond the uniform threshold.

→ related card
8. Why is Ribbon's query cache-friendlier than XOR's?

A window of w consecutive rows fits about one cache line, versus three random cache lines for XOR.

→ related card
Counterfactual
9. What if all keys had the same fingerprint? What if fingerprints were chosen non-randomly?

If all keys shared one fingerprint, the FPR would reach 100% for that fingerprint. Non-random fingerprints let queries correlated with them be accepted systematically. Solvability is unaffected in both cases.

→ related card
10. What if the array were 1.20n for plain XOR with n = 106?

At load 0.833 you are above 0.8185, so a 2-core of about Θ(n) keys remains with high probability, and construction fails on essentially every seed.

→ related card
11. What if w = 64 were w = 1024 in Ribbon?

Less slack would be needed, because the band is wider and packs tighter. But elimination cost per key grows, and the query window would span 16 cache lines.

→ related card
12. What if a duplicate key is inserted twice?

The two identical edges sit on the same 3 slots. Peeling cannot reduce them below degree 2, so the build fails on every seed unless duplicates are detected and removed. The current C binary-fuse code does that after a failing round.

→ related card
Adversarial
13. How would an attacker who knows the seed force a build failure?

Pick keys that all hash into the same few slots (at least 1.23 times the slot count), which guarantees a 2-core.

→ related card
14. How could an attacker find queries that are false positives?

With the filter or seed known, test candidate queries offline until about 2f of them yield a false positive. With a secret seed, the attacker only sees accept or reject, so each probe succeeds with probability 2-f. Once found, a false positive stays one, since the filter is not adaptive.

→ related card
15. How would you make build-time hash flooding harmless?

Use a per-build random secret 64-bit seed with a strong mixer, and reject and retry on failure.

→ related card
Connection
16. How does peeling relate to LDPC decoding and erasure codes?

Both peel sparse random graphs. The threshold of about 0.818 is the same object as the belief-propagation erasure-decoding threshold of LDPC codes, and spatial coupling is the same fix.

→ related card
17. How does this relate to cuckoo hashing's orientability threshold?

Orientability means each key can be assigned its own cell (threshold about 0.918). Peeling is a stricter, greedy-solvable subset of that.

→ related card
18. How do minimal perfect hash functions (BDZ, RecSplit, ShockHash) reuse these ideas?

BDZ builds an MPHF via peeling. RecSplit and ShockHash use brute-force and cuckoo-style seeds. They target about 1.44 to 1.5 bits per key for an MPHF.

→ related card
Open
19. Can a fast, restart-free construction reach under 1% overhead without a side structure?

Open. ZOR trades determinism for a side structure, and spatial coupling with parallelism are active directions.

→ related card
20. Is there an adversarially robust static filter at about 1.1× the information bound?

Open.

→ related card
21. Do learned filters beat fuse and Ribbon on realistic non-stationary workloads?

Open. The answer depends on drift and on adversarial queries.
