Static approximate-membership filters: XOR / binary fuse (peeling) vs Ribbon (banded elimination)

TL;DR. For a set that never changes, don't insert keys into a Bloom filter — solve for a table where the XOR of three cells equals each key's fingerprint. A greedy "peel the key that owns a private cell" order solves it almost always when there are ≥ ~1.22 cells per key; windows of consecutive segments (binary fuse) push that to ~1.13, and Ribbon's banded GF(2) elimination reaches <10% overhead with a tunable dial.

Why it matters. LSM-tree filters sit in RAM for hours; 3 bits/key saved on 10 billion keys is ~3.75 GB. RocksDB and Firefox's CRLite use this family in production.

Plain English first

Explain it simply

A bouncer has a guest list of a million names — too big to carry. Instead the bouncer carries a small cheat-sheet board of numbered slots. For a visitor, the bouncer turns the name into three slot numbers, adds up (XORs) the three numbers on the board, and compares the total with a short "secret code" derived from the name. Match → in. Everyone on the list always matches. A stranger matches only by luck — with an 8-bit code, 1 in 256.

The clever part is filling the board. For every guest we need "slot a + slot b + slot c = my code" at once. Trick: find a guest who owns one slot alone, set them aside on a stack, repeat. Once everyone is on the stack, fill the board in reverse: the last guest set aside gets their lonely slot adjusted so their sum works. It works almost every time with only ~1.23 slots per guest. Ribbon filters solve the same puzzle as a school-style system of equations where each equation touches only a short nearby stretch of slots, so a single pass solves it — with as little as ~5–10% spare room.

Everyday example

Three guests and a board of six slots in three pairs (A0 A1 | B0 B1 | C0 C1). Ana → A0, B0, C0, code 5. Ben → A0, B1, C1, code 3. Cy → A1, B0, C1, code 6. Slot C0 is touched only by Ana; A1 only by Cy; after those two are set aside, A0 only by Ben. Set aside Ana, Cy, Ben. Fill backwards: Ben first (A0 = 3), then Cy (A1 = 6), then Ana (C0 is set so the sum is 5, which is 6). Board: A0=3, A1=6, B0=0, B1=0, C0=6, C1=0. Check Ana: 3+0+6 → 5 ✓. A stranger hashing to A1, B1, C0 sums to 0 and is turned away unless their own code is 0.

Now the same thing, technically.

Real-world context

1 · Bare-minimum context

  • AMQ filter: "is x in S?" with no false negatives and false-positive rate ε. Minimum ≈ log₂(1/ε) bits/key (Carter et al. 1978; Pagh–Pagh–Rao 2005).
  • Bloom filter: k hash positions in a bit array; ≈ 1.44·log₂(1/ε) bits/key.
  • Fingerprint: f-bit hash of the key; chance a stranger collides = 2-f.
  • GF(2) linear algebra: XOR is addition mod 2; XOR-equation systems yield to Gaussian elimination.
  • Random hypergraph: each key = an edge over 3 slots. Peeling repeatedly removes degree-1 vertices; what is left is the 2-core.
  • Static: the whole key set is known up front; no later inserts/deletes.

1b · Real-world context

What it is

A way to store an immutable set so "might x be in it?" costs ~3 memory reads and ~9 bits per key at a 0.4% false-positive rate. Instead of inserting keys, you solve for a table whose cell XORs equal key fingerprints.

Why it exists

Bloom filters guard disk and network lookups but waste 44% over the information minimum and need scattered probes. If the set never changes, the table can be computed rather than grown: 23% overhead (XOR 2019), 13%/8% (binary fuse 2022), <10% with a dial (Ribbon 2021), <1% in experimental variants. Filters in an LSM tree live in RAM for hours, so each saved bit is multiplied by lifetime.

Where it's used

RocksDBRibbon for compaction output, Bloom for flushes (NewRibbonFilterPolicy). Blog: ~30% memory saved (≈7 vs 10 bits/key), ~4.4× build CPU (140 vs 32 ns/key), ~20% query CPU, break-even ≈ 1 h of filter lifetime.
Firefox CRLiteRevocation checking moved from Bloom cascades to "Clubcard", a partitioned two-level cascade of Ribbon filters; ~300 kB/day (4 MB snapshot every 45 days + deltas).
xor_singleheader (C)Reference xor + binary fuse 8/16/32-bit filters; serialize/mmap.
xorfilter (Go), xorf (Rust)Same families, PopulateBinaryFuse8 etc.
Analytics / networking / bioinformaticsNamed consumers of peeling-based filters in the ZOR abstract.
Not adopted (as far as I found)ClickHouse, DuckDB and Parquet use (split-block) Bloom filters; I found no xor/fuse there.

How it's used

#include "binaryfusefilter.h"            // FastFilter/xor_singleheader
binary_fuse8_t f;
binary_fuse8_allocate(n, &f);            // ~1.13*n bytes
binary_fuse8_populate(keys, n, &f);      // uint64_t keys[n]; false after 100 failed seeds
bool maybe = binary_fuse8_contain(x, &f);// 3 loads + XOR + compare; FPR ~ 1/256
binary_fuse8_free(&f);

// RocksDB (C++): Ribbon with Bloom-equivalent 10 bits/key; Bloom for flush
table_options.filter_policy.reset(rocksdb::NewRibbonFilterPolicy(10.0));
// bloom_before_level (since 6.24): Bloom on levels below the given one

Typical: 8-bit fingerprints (ε≈0.39%, ≈9 bits/key) or 16-bit (≈1.5·10⁻⁵, ≈18 bits/key); keys pre-hashed to 64 bits.

Use it when
  • Set built once, queried many times (SSTables, immutable segments, blocklists, k-mer sets)
  • RAM per key matters
  • Binary fuse for speed; Ribbon for tunable/smaller space
Skip it when
  • You need inserts/deletes (Bloom, cuckoo, quotient)
  • The build must stream or memory is tight (peeling holds all hashes)
  • Filter lifetime is short (RocksDB keeps Bloom for L0)

Who should care

Storage/DB engineers (LSM filters), infra (blocklists, certificate revocation), search and genomics engineers (membership over huge immutable sets), anyone paying RAM per key.

Technical deep dive

2 · The one-liner — and what it hides

"XOR filters are Bloom filters that are smaller and faster because you precompute a table where three cells XOR to the fingerprint." It hides:

  1. Why the table can always be computed — only if the 3-uniform hypergraph is peelable: a phase transition at ≥ 1.22 slots/key, not a heuristic.
  2. Why the FPR is exactly 2-f (and when it isn't).
  3. How binary fuse beats the threshold (1.22 → 1.13/1.08) with windows of consecutive segments — spatial coupling.
  4. That Ribbon drops hypergraphs entirely: banded linear algebra, a different space/time trade.
  5. What breaks: duplicates, build retries, adversarial keys, memory spike, 64-bit hash assumption, no updates.

3 · The problem

Bloom at ε=1%: ≈9.6 bits/key at optimal k, ~7 probes into a large bit array (cache misses). The minimum is log₂(100) ≈ 6.64 bits/key. At ε=2⁻⁸: Bloom ≈ 11.5 bits vs 8 minimum. On a 10-billion-key LSM, 3 bits/key = 3.75 GB of RAM. Static sets don't need incremental insertability, and that requirement is what costs Bloom its 44%.

4 · Mental model

A bulletin board of sticky notes. Each guest has three notes; the notes must XOR to the guest's code. Filling the board = solving every guest's equation at once. Peeling = repeatedly set aside a guest who owns a private note, then fill in reverse so that private note absorbs the slack.

Where the analogy breaks. The board has only ~1.23 slots per guest while each guest touches 3, so slots are heavily shared. Solvability is not a local guarantee; it is a global property of the random hypergraph (no dense core below ~82% load).

5 · The mechanism, traced

3-bit fingerprints, six slots. Positions (one per block): Ana → A0 B0 C0, fp 5 · Ben → A0 B1 C1, fp 3 · Cy → A1 B0 C1, fp 6. Step through:

Step 0 / 8 
peel stack (top first): Ben/A0, Cy/A1, Ana/C0      (all 3 peeled → 2-core empty → success)
assign in reverse:  A0 = 3^B1^C1 = 3 ;  A1 = 6^B0^C1 = 6 ;  C0 = 5^A0^B0 = 5^3^0 = 6
board: A0=3 A1=6 | B0=0 B1=0 | C0=6 C1=0     query y→(A1,B1,C0): 6^0^6 = 0 ≠ fp(y)=4 → reject

Why reverse order works. The vertex a key was peeled through was touched by no other unpeeled key at that moment. In reverse, anything assigned later was peeled earlier and writes only its own private vertex, so it never disturbs a key assigned before it. Each cell is written at most once.

Binary fuse query, as shipped

hash = murmur64(key + seed);   f = (uint8_t)(hash ^ (hash >> 32));
h0 = mulhi(hash, SegmentCountLength);                       // uniform over first SegmentCount segments
h1 = (h0 + SegmentLength)   ^ ((hash >> 18) & SegmentLengthMask); // next segment, random in-segment offset
h2 = (h0 + 2*SegmentLength) ^ ( hash        & SegmentLengthMask); // segment after that
return f == (F[h0] ^ F[h1] ^ F[h2]);

Segment length: power of two, 2^floor(ln n / ln 3.33 + 2.25) (arity 3). Array size factor: max(1.125, 0.875 + 0.25·ln(10⁶)/ln n). Build retries up to XOR_MAX_ITERATIONS = 100 seeds; hashes are first sorted into segment-order buckets for locality; the current C code detects and drops duplicates when a round fails (source: FastFilter/xor_singleheader).

Ribbon, traced

Each key becomes (start s, w-bit coefficient word c with bit 0 set, r-bit fingerprint b). Insert: if pivot row s is empty, store it. Otherwise XOR with the stored equation, shift out leading zeros (c ← c≫j, s ← s+j) and continue. c=0 with b=0: redundant. c=0 with b≠0: inconsistent → new seed. Back-substitute bottom-up: Z[i] = bi ⊕ ⨁j>0, ci[j]=1 Z[i+j]. Query XORs the Z rows picked by c's set bits — all inside one w-row window (64 rows × 8 bits = 64 B ≈ one cache line), versus three random cache lines for XOR.

6 · The math

(a) Information bound

A filter accepts a set A ⊇ S with |A| ≈ n + εu. Each stored state covers C(n+εu, n) of the C(u, n) possible key sets, so states needed ≈ (1/ε)n.

bits ≥ n · log₂(1/ε)→ in plain terms: each key pays for forgetting everything except an ε-sized neighbourhood.

(b) Why Bloom wastes 44%

Optimal Bloom has half its bits set; each bit carries <1 bit of information.

m / n = log₂e · log₂(1/ε) ≈ 1.44 · log₂(1/ε)→ in plain terms: a Bloom bit array is only 50% informative, and you pay for the rest.

(c) Why FPR = 2-f

For y ∉ S the three cells hold values set from other keys' independent random fingerprints, so their XOR is uniform on f bits and independent of fp(y).

Pr[ B[h₀]⊕B[h₁]⊕B[h₂] = fp(y) ] = 2-f ; bits/key = f · (slots/key) = 1.23f | ≈1.13f | ≈1.08f→ in plain terms: space = fingerprint width × slot overhead; the overhead is the whole game.

(d) The peeling threshold

m slots, n keys, c = n/m. Each slot has Poisson(3c) incident edges. Let q = probability an edge, seen from one endpoint, survives (is not removed via its other two endpoints). An endpoint keeps the edge alive iff it has ≥1 other surviving edge: probability 1 − e−3cq. Both other endpoints must do so:

q = (1 − e−3cq)² ⇒ c(q) = −ln(1−√q) / (3q)→ in plain terms: q=0 (everything peels) is always a solution; a nonzero solution (a 2-core) first appears at the minimum of c(q).

Numerically (my run): c* = 0.8185 for k=3 ⇒ 1/c* = 1.2218 slots/key (≈1.23 with slack); k=4: 0.7723 ⇒ 1.295; k=5: 0.7018 ⇒ 1.425. Arity 2 (graphs) has its core at c=0.5 ⇒ 2.0.

Orientability (every key gets its own cell) kicks in later, ≈0.918 ⇒ 1.089 for k=3 — quoted from literature, not re-derived here. Orientable ≠ peelable: a solution exists but greedy peeling can't find it; Gaussian elimination can (Ribbon uses a band to make that cheap).

(e) Fuse windows

Keys pick a start segment s and use segments s, s+1, s+2. End segments have lower degree, so peeling starts there and a wave moves inward — the spatial-coupling / threshold-saturation effect Walzer proved can lift the peeling threshold toward the orientability threshold (arXiv:2001.10500). Result: factor 1.125 (arity 3) or 1.075 (arity 4) at large n, rising for small n (formula above).

(f) Ribbon

⟨h(x), Z⟩ = b(x) over GF(2), h(x) = 0s · c · 0m−s−w→ in plain terms: each equation lives in a width-w band, so sorting by start makes the matrix a diagonal "ribbon" and elimination runs in near-linear time.

Dietzfelbinger–Walzer (arXiv:1907.04750): with m = n/(1−ε) columns and one random block of length w = O(log n / ε) per row, the matrix has full row rank whp and elimination costs O(n/ε²). Ribbon uses w=64; the paper reports <10% overhead at modest CPU cost and <1% for an experimental load-balanced variant; BuRR (SEA 2022) reaches "well below 1%" by bumping the few rows that don't fit into a fallback structure.

7 · Why it works

Core insight: a sparse random constraint system with ~1.22 variables per equation is solved by a trivial greedy order, and a solved table plus a random fingerprint gives exactly 2-f FPR with one XOR. Ablations:

  • Arity 2 instead of 3 → peels only below load 0.5 (2.0 slots/key).
  • No seed retry → near threshold (82% success at 1.23, n=20000 in my demo) becomes a hard error.
  • Non-random fingerprints → FPR no longer 2-f; queries correlated with the fingerprint function get through.
  • No windows → back to 1.22.
  • Ribbon without the band → dense elimination, O(n³).

9 · Where it breaks

  • Construction can fail. Retry with a new seed (≤100 in the C library). Near the threshold failures are common: my demo 82% at 1.23, n=20000.
  • Duplicates. Two identical edges form a 2-core. The current C binary-fuse code detects and removes them after a failing round; other ports may just error. Deduplicate.
  • Adversarial keys. Known seed + chosen keys ⇒ a forced 2-core. Use a secret random seed. Queries are not adversarially robust either: a found false positive stays one.
  • Build memory. Peeling holds all hashes + counters (≈24 B/key transient per implementation notes — unverified exactly).
  • Limits. C size is uint32_t; assumes 64-bit hashes; 8-bit fingerprints cap ε at 2-8.
  • Small n. The size factor rises sharply below ~10⁵; xor/fuse can lose to Bloom at large ε or tiny n.
  • No updates. Any change ⇒ rebuild; dynamic filters pay a provable Ω(n)-bit penalty (Kuszmaul–Walzer, STOC 2024).
Misconceptions. "XOR always beats Bloom" — not at large ε or tiny n. "Static is useless" — most big filters live in immutable files. "Ribbon is slow" — about +20% query CPU in RocksDB's own numbers; the cost is construction.

10 · In the wild

  • RocksDB: hybrid by level; bloom_equivalent_bits_per_key keeps Bloom's FPR while spending ~30% less; one full filter per SST file.
  • Firefox CRLite / Clubcard: Ribbon in a two-level cascade; filters are rebuilt on a schedule, so static fits.
  • xor_singleheader: 8/16/32-bit variants, flat array + seed + segment parameters (mmap-able), pre-hashed uint64 keys.
  • Deviations from the paper: fuse sorts hashes into segment buckets before peeling, uses mulhi instead of %, and XOR-offsets inside segments instead of independent hashes.

11b · Open problems

  • Fast build near the bound. Ribbon/ZOR reach ~1% overhead but pay in build time (RocksDB: ~4.4× Bloom's build CPU); fuse is fast but ≥8% over. Nobody has both at every scale.
  • Deterministic, restart-free build with no side structure (ZOR still needs one).
  • Adversarial robustness. Static fuse/Ribbon give no guarantee against adaptive query adversaries; robust Bloom constructions (Naor–Yogev) cost extra.
  • Range filters with worst-case guarantees at static-filter space (Grafite closes much; correlated/adaptive workloads remain contested).
  • External-memory, SIMD, GPU peeling. Peeling is sequential and cache-hostile; I found no mature GPU xor/fuse builder.
  • Learned filters. Gains depend on the query distribution; robustness and drift unresolved.

12 · Lineage

Bloom 1970 → Carter et al. 1978 (fingerprint filters, bound) → Bloomier filters (Chazelle et al. 2004) → Dietzfelbinger–Pagh 2008 (succinct retrieval/AMQ) → Botelho–Pagh–Ziviani 2013 (peeling for perfect hashing) → XOR filters (Graf–Lemire 2019/20) → Dietzfelbinger–Walzer 2019 (banded elimination) → Ribbon (Dillinger–Walzer 2021) / BuRR 2022 → Walzer 2020 (spatial coupling) → binary fuse (Graf–Lemire 2022) → ZOR (2026).

14 · Question ladder

Mechanism

1. In the trace, why is it safe to assign Ana's C0 after Ben's A0 and Cy's A1?

C0 was touched by no other unpeeled key when Ana was peeled, so no later-assigned key writes it; her other cells (A0, B0) are final by then.

2. Why does each cell get written at most once?

Each key is assigned only the one cell it was peeled through; a cell is peeled through only one key (degree 1 at that time).

3. In a Ribbon insert, what does c & -c compute and why shift?

It isolates the lowest set bit; its index is the trailing-zero count j. The reduced equation starts at row i+j, so shift right by j to realign bit 0 with that pivot.

4. In binary_fuse8_contain, why XOR the in-segment offset instead of adding it?

XOR with a mask < SegmentLength permutes positions inside the segment-aligned block and stays in-segment; adding could cross into the next segment and break the window structure.

Why

5. Why 3 hash positions, not 2 or 4?

Arity 2 peels only below load 0.5 (2.0 slots/key); arity 4 needs 1.295 slots/key without windows and costs another read. Arity 3 minimises slots/key for plain peeling.

6. Why is FPR exactly 2-f, and what must hold?

The three-cell XOR is uniform on f bits and independent of fp(y) because cells come from other keys' independent random fingerprints. The fingerprint hash must act like a random function independent of positions.

7. Why does a windowed hypergraph peel at lower density?

End segments have lower degree, seeding peeling; neighbours then drop to degree 1 in a wave (spatial coupling / threshold saturation).

8. Why is Ribbon's query more cache-friendly than XOR's?

A window of w consecutive rows ≈ one cache line, versus 3 random lines.

Counterfactual

9. All keys share one fingerprint? Non-random fingerprints?

Shared: every stranger with that fingerprint is a false positive (FPR 100% for them). Non-random: queries correlated with the function are accepted systematically. Solvability is unaffected either way.

10. Plain XOR with 1.20n slots, n=10⁶?

Load 0.833 > 0.8185: a Θ(n) 2-core remains whp, so essentially every seed fails.

11. Ribbon width 1024 instead of 64?

Needs less slack, but elimination costs more per key and a query window spans ~16 cache lines.

12. A duplicate key?

Two identical edges share the same 3 slots; peeling can't drop them below degree 2, so every seed fails — unless duplicates are detected and removed (current C binary-fuse code does this after a failing round).

Adversarial

13. Force a build failure knowing the seed?

Choose keys that all hash into the same few slots (more than ~0.82 per slot) ⇒ guaranteed 2-core. Needs the seed or a weak hash.

14. How could an attacker find false-positive queries?

With the filter or seed known, test candidates offline (~2f tries each). With a secret seed each probe succeeds with probability 2-f, and a found false positive stays one forever (filter is not adaptive).

15. Make build-time hash flooding harmless?

Per-build secret random 64-bit seed with a strong mixer; reject-and-retry.

Connection

16. Peeling vs LDPC decoding / erasure codes?

Both are peeling on sparse random (hyper)graphs; the 0.818 threshold is the same kind of object as the erasure-decoding threshold of LDPC codes, and spatial coupling is the same fix.

17. Relation to cuckoo hashing's orientability threshold?

Orientable = every key can get its own cell (≈0.918 for k=3); peelable is a stricter, greedy-solvable subset.

18. Minimal perfect hashing?

BDZ builds MPHFs via peeling; RecSplit/ShockHash use seed search / cuckoo-style tables to reach ≈1.44–1.5 bits/key.

Open

19. Fast, restart-free build below 1% overhead without a side structure?

Open; ZOR trades determinism for a side structure; spatial coupling and parallelism are active directions.

20. An adversarially robust static filter near 1.1× the bound?

Open.

21. Do learned filters beat fuse/Ribbon on realistic non-stationary workloads?

Open; depends on drift and adversarial queries.
