What it is

A Linux kernel interface (since 5.1, 2019) for asynchronous I/O. The app and kernel share two ring buffers in memory: the app drops request descriptors (SQEs) on the submission queue, the kernel posts results (CQEs) on the completion queue, and one io_uring_enter(2) call can submit many requests and wait for completions. [V] man7 io_uring(7). Cloudflare's framing: it is "a full-blown runtime for processing I/O requests", with its own worker threads and queues. [V] Cloudflare

Why it exists

  • Before: Linux aio (O_DIRECT only, copies, ≥2 syscalls per I/O) and epoll (readiness only, nothing for regular files), so apps bolted on thread pools. Details in section 3.
  • Storage apps port from libaio easily, but networking "required rethinking": swapping epoll for io_uring notifiers "does not lead to an outcome that fully takes advantage" of it; the win is a changed event-loop design. [V] liburing wiki "io_uring and networking in 2023"
  • Cost of not having it: a user-space thread pool (libuv-style) with context switches even for cached reads, or giving up deep queue depths from one thread.

Where it's used

Verified in the backfill pass; each card is one system and the role io_uring plays there.

Database · PostgreSQL 18

io_method = io_uring selects it for the new async I/O subsystem (alternatives worker, sync); needs a build with --with-liburing / -Dliburing. Default is worker: the PG 18 docs say "The default is worker". [V] PG 18 docs, fetched in this pass.

The release-announcement page, as fetched earlier, appeared to say sync; the versioned docs are the authoritative source. The announcement claims "up to 3x" in some scenarios for AIO overall, not io_uring specifically. announcement

Virtualization · QEMU

Block-layer AIO engine since QEMU 5.0, -drive aio=io_uring (others: threads, native); uses READV/WRITEV/FSYNC ops. [not independently re-verified] originally from the 2019 patch series

Database · TigerBeetle

Single thread alternates replica.tick() and io.run_for_ns(); every I/O is async, submitted through io_uring on Linux. [V] blog, linux.zig

Runtime · libuv (Node.js)

v1.45.0 handed some file ops (read/write/fsync/fdatasync/stat family) to io_uring, "8x throughput" in the commit message, falling back to the thread pool. Opt-in via UV_LOOP_USE_IO_URING_SQPOLL; from v1.49.0 the default reverted to the thread pool. [V] libuv docs (re-read in this pass: 1.45.0, 1.49.0 and the SQPOLL option confirmed). The "8x" figure is from the commit message via Phoronix, not re-verified.

Storage engine · RocksDB

Opt-in: PosixFileSystem async read via io_uring (ReadAsync/Poll) used by MultiGet and iterators; if not enabled, ReadAsync returns NotSupported. [unverified (single secondary source)] mirrored commit (the 2022 blog itself does not mention io_uring)

Async runtime · Glommio (Datadog)

Rust thread-per-core runtime built on io_uring with no helper threads; needs Linux 5.8+ and ≥512 KiB locked memory. [not independently re-verified] GitHub

Edge / network · Cloudflare

Not a "we run it" claim: they dissected the io-wq worker pool because socket I/O is their core workload, and recommend IORING_REGISTER_IOWQ_MAX_WORKERS (5.15) over lowering RLIMIT_NPROC. [V] blog

Counter-adopters · Google (ChromeOS, servers, Android)

Disabled it on ChromeOS and production servers and blocks it for Android apps via seccomp-bpf (2023); 60% of the past year's submissions exploited io_uring. [V] Google Security Blog, read directly; see section 9.

How it's used

Practitioners call liburing (the helper library "to setup and teardown io_uring instances" with a simplified interface) rather than raw syscalls; liburing is not tied to a kernel release but features need matching kernels. [V] liburing README. Core call sequence: io_uring_queue_init → io_uring_get_sqe → io_uring_prep_* → io_uring_submit (or io_uring_submit_and_wait) → io_uring_wait_cqe → io_uring_cqe_seen. [V] liburing wiki

Typical parameters: entries = power of two (e.g. 256); recommended networking flags COOP_TASKRUN (5.19+) and SINGLE_ISSUER + DEFER_TASKRUN (6.0/6.1+); SQPOLL only if a spare core is acceptable; multishot accept/recv with provided buffers (IOSQE_BUFFER_SELECT, watch IORING_CQE_F_MORE). [V] liburing wiki, io_uring_setup(2)

// Illustrative, not compiled: written from the documented call sequence. A compile check was attempted
// but no Linux/liburing toolchain was available (macOS host, Docker daemon down).
struct io_uring ring;
struct io_uring_params p = {0};
p.flags = IORING_SETUP_SINGLE_ISSUER | IORING_SETUP_DEFER_TASKRUN;  // kernel >= 6.1
io_uring_queue_init_params(256, &ring, &p);

struct io_uring_sqe *sqe = io_uring_get_sqe(&ring);
io_uring_prep_read(sqe, fd, buf, 4096, 0);   // fd, buffer, len, file offset
sqe->user_data = 42;                         // echoed back in the CQE

io_uring_submit_and_wait(&ring, 1);          // one syscall: submit + wait for 1 completion
struct io_uring_cqe *cqe;
io_uring_wait_cqe(&ring, &cqe);
// cqe->res = bytes read or -errno; cqe->user_data == 42
io_uring_cqe_seen(&ring, cqe);

Usual integration pattern: one ring per thread, batch SQEs per loop iteration, correlate with user_data, re-arm multishot requests when F_MORE is clear (TigerBeetle's loop above is the canonical shape). Full runnable program: section 13.

When to use it / when not

Use it

  • Many small ops can be batched.
  • File and network I/O share one loop.
  • You want deep queue depth from few threads (NVMe).
  • You can redesign the loop and require a recent kernel.

Search-level summaries and the liburing wiki agree on this shape. [V]

Skip it

  • Plain network server and you won't restructure around completions: stay on epoll (Alibaba Cloud's comparison reports io_uring throughput about 10% higher at 1000 connections, with CPU mitigations enabled [V] read in this pass; one vendor benchmark, no raw numbers), or libaio for O_DIRECT.
  • You need old-kernel portability.
  • Workload is untrusted/sandboxed (Google's stance, section 9).
  • You want cross-OS portability (Windows IoRing is a similar but separate API [not independently re-verified] windows-internals.com).
Signs you picked wrongGains of 1.06x-1.10x after a drop-in swap (section 2), iou-wrk-* thread pile-ups, or code full of kernel-version fallbacks.

Who should care

  • Database/storage engineers: deep NVMe queues, async buffer managers (PostgreSQL 18, RocksDB, TigerBeetle).
  • Runtime/library authors (Node/libuv, Rust async runtimes, Zig): completion-model API and cancellation semantics.
  • Infra/SRE: kernel version, RLIMIT_NPROC/pids.max, QEMU aio= choice.
  • Security/platform engineers: whether to allow it in containers; syscall-based monitoring is blind to SQE opcodes (section 9).
