Picture two notepads that the app and the kernel can both read and write. One holds requests (the submission queue), the other holds results (the completion queue). The app writes a request into a slot, and the kernel reads that slot from the same memory.

The old way. Linux aio copied 104 bytes for each I/O and took at least two syscalls. Buffered I/O behaved synchronously, so one slow read held up the loop.

Why it fails. A buffered file read blocks. Apps worked around that with thread pools, and each handoff costs at least two context switches, even on a page-cache hit.

The key idea. Put many requests in the submission queue, then call io_uring_enter once. The shared rings replace the copies, and one call covers the whole batch.

Inline first. The kernel tries each read right away without blocking. A read that hits the page cache finishes before the call returns, so its result is already in the completion queue.

Sockets wait cheaply. A socket with no data yet is parked on a poll list, and no thread sleeps on it. When data arrives, the kernel runs the request as task work and posts its result.

Files fall back. A buffered file read that cannot finish inline goes to an iou-wrk worker in the kernel. Only that slow path uses a helper thread.

The bill. The reads live inside the rings, so seccomp sees only the setup and io_uring_enter calls. Google disabled io_uring on ChromeOS and production servers; 60% of its kCTF Linux exploit submissions targeted it.

The numbers. A naive swap gains 1.06× in a buffer manager. The redesign reaches 2.05×, and sync POSIX ran 16.5K transactions per second against 376K with io_uring. Each card below takes one piece of this apart.
