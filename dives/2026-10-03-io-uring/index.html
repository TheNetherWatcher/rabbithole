io_uring: shared rings, zero-syscall I/O, and the security bill

io_uring gives Linux two shared rings: the app fills a submission queue, the kernel fills a completion queue, and one io_uring_enter can submit and reap many I/Os. The win is batching and concurrency, not a faster epoll: a naive swap gains only 1.06–1.10×. The price is a second syscall surface that seccomp cannot inspect.

Why it matters: it is now an opt-in I/O path in PostgreSQL 18, a read path in RocksDB, and the file path in several runtimes, and it is why security teams ask whether to allow it in containers at all.

Plain English
In everyday words

Two trays and one bell, not a walk per errand

A cook drops several order notes on a tray, rings one bell and keeps cooking. The helper does the quick ones at once, parks the slow ones and posts each result with its number. Many errands in flight from one thread.

Explain it simply

Picture a busy cook who needs things from a helpful pantry assistant. The old way: the cook walks over, asks for one thing, waits, walks back, then repeats for every single item. Most of the time goes into the walking back and forth, not the fetching. io_uring replaces that with two trays on a shared counter: an "orders" tray the cook drops notes into, and a "done" tray the assistant drops results into. The cook stacks up several notes, rings the bell once, and goes back to cooking.

When the bell rings, the assistant first does whatever is within arm's reach right away. Anything that has to wait (a parcel that has not arrived yet, a book in the basement) gets handled without the assistant standing around: either "I'll tap you when it shows up" or "a helper will go fetch it". Results land in the done tray, each with the number from the original note so the cook can match them up. The point: fewer interruptions and many errands in flight at once.

Everyday example

Sam is cooking dinner and writes three notes: (1) "read me the first page of the recipe card", (2) "tell me when the grocery parcel arrives", (3) "bring the big cookbook from the basement". Sam numbers them 1, 2, 3, drops them in the orders tray, and rings the bell once.

The assistant grabs the recipe card from the shelf right there and puts the page in the done tray before Sam has even looked up. For the parcel, nothing has arrived, so the assistant says "I'll flag it when the doorbell goes" and does not wait at the door. The basement book is far away, so a helper is sent. Later Sam glances at the done tray: slip 1 is there already, then slip 3 when the helper returns, then slip 2 when the parcel finally arrives. Sam matches each slip to its note by number. One bell, three errands, no waiting around, and results can come back in any order.

Now the same thing, technically.

Context
§1 · Prerequisites

Six ideas to know first

  • Syscall: a user-to-kernel switch; mitigations make entry costly.
  • Readiness vs completion: epoll says "can read", completion says "the read is done".
  • Page cache vs O_DIRECT: only O_DIRECT was truly async in Linux aio.
  • SPSC ring with acquire/release on the tail.
  • Little's law: in flight = throughput × latency.
  • Syscall = user→kernel mode switch. Cost = entry/exit + mitigations (post-Spectre/Meltdown), not the work itself. [paper §1]
  • Readiness vs completion: epoll says "fd can be read"; you still do the read. A completion API says "your read is done, here are the bytes".
  • Buffered I/O goes through the page cache; O_DIRECT bypasses it. Linux aio only did true async for O_DIRECT.
  • SPSC ring buffer: single-producer/single-consumer queue with head (consumer) and tail (producer) indexes; lock-free with proper memory ordering.
  • Acquire/release: producer releases (publishes) tail after writing the entry; consumer acquires tail before reading the entry. Entry visible iff tail visible.
  • Little's law: in-flight ops = throughput × latency. NVMe needs deep queues to hit rated IOPS.
§1b · Real-world context

Databases adopt it for storage; sockets are the harder half

PostgreSQL 18 offers io_method=io_uring (default is worker). RocksDB uses it on read paths, TigerBeetle routes all I/O through it, libuv moved file ops to it. Google disabled it on ChromeOS and production.

Tags: [V] seen in a fetched/searched source during the backfill pass; [K] not re-verified.

What it is

A Linux kernel interface (since 5.1, 2019) for asynchronous I/O. The app and kernel share two ring buffers in memory: the app drops request descriptors (SQEs) on the submission queue, the kernel posts results (CQEs) on the completion queue, and one io_uring_enter(2) call can submit many requests and wait for completions. [V] man7 io_uring(7). Cloudflare's framing: it is "a full-blown runtime for processing I/O requests", with its own worker threads and queues. [V] Cloudflare

Why it exists

  • Before: Linux aio (O_DIRECT only, copies, ≥2 syscalls per I/O) and epoll (readiness only, nothing for regular files), so apps bolted on thread pools. Details in section 3.
  • Storage apps port from libaio easily, but networking "required rethinking": swapping epoll for io_uring notifiers "does not lead to an outcome that fully takes advantage" of it; the win is a changed event-loop design. [V] liburing wiki "io_uring and networking in 2023"
  • Cost of not having it: a user-space thread pool (libuv-style) with context switches even for cached reads, or giving up deep queue depths from one thread.

How it's used

Practitioners call liburing (the helper library "to setup and teardown io_uring instances" with a simplified interface) rather than raw syscalls; liburing is not tied to a kernel release but features need matching kernels. [V] liburing README. Core call sequence: io_uring_queue_init → io_uring_get_sqe → io_uring_prep_* → io_uring_submit (or io_uring_submit_and_wait) → io_uring_wait_cqe → io_uring_cqe_seen. [V] liburing wiki

Typical parameters: entries = power of two (e.g. 256); recommended networking flags COOP_TASKRUN (5.19+) and SINGLE_ISSUER + DEFER_TASKRUN (6.0/6.1+); SQPOLL only if a spare core is acceptable; multishot accept/recv with provided buffers (IOSQE_BUFFER_SELECT, watch IORING_CQE_F_MORE). [V] liburing wiki, io_uring_setup(2)

// Illustrative, not compiled: written from the documented call sequence. A compile check was attempted
// but no Linux/liburing toolchain was available (macOS host, Docker daemon down).
struct io_uring ring;
struct io_uring_params p = {0};
p.flags = IORING_SETUP_SINGLE_ISSUER | IORING_SETUP_DEFER_TASKRUN;  // kernel >= 6.1
io_uring_queue_init_params(256, &ring, &p);

struct io_uring_sqe *sqe = io_uring_get_sqe(&ring);
io_uring_prep_read(sqe, fd, buf, 4096, 0);   // fd, buffer, len, file offset
sqe->user_data = 42;                         // echoed back in the CQE

io_uring_submit_and_wait(&ring, 1);          // one syscall: submit + wait for 1 completion
struct io_uring_cqe *cqe;
io_uring_wait_cqe(&ring, &cqe);
// cqe->res = bytes read or -errno; cqe->user_data == 42
io_uring_cqe_seen(&ring, cqe);

Usual integration pattern: one ring per thread, batch SQEs per loop iteration, correlate with user_data, re-arm multishot requests when F_MORE is clear (TigerBeetle's loop above is the canonical shape). Full runnable program: section 13.

When to use it / when not

Use it

  • Many small ops can be batched.
  • File and network I/O share one loop.
  • You want deep queue depth from few threads (NVMe).
  • You can redesign the loop and require a recent kernel.

Search-level summaries and the liburing wiki agree on this shape. [V]

Skip it

  • Plain network server and you won't restructure around completions: stay on epoll (Alibaba Cloud's comparison reports io_uring throughput about 10% higher at 1000 connections, with CPU mitigations enabled [V] read in this pass; one vendor benchmark, no raw numbers), or libaio for O_DIRECT.
  • You need old-kernel portability.
  • Workload is untrusted/sandboxed (Google's stance, section 9).
  • You want cross-OS portability (Windows IoRing is a similar but separate API [not independently re-verified] windows-internals.com).
Signs you picked wrongGains of 1.06x-1.10x after a drop-in swap (section 2), iou-wrk-* thread pile-ups, or code full of kernel-version fallbacks.

Who should care

  • Database/storage engineers: deep NVMe queues, async buffer managers (PostgreSQL 18, RocksDB, TigerBeetle).
  • Runtime/library authors (Node/libuv, Rust async runtimes, Zig): completion-model API and cancellation semantics.
  • Infra/SRE: kernel version, RLIMIT_NPROC/pids.max, QEMU aio= choice.
  • Security/platform engineers: whether to allow it in containers; syscall-based monitoring is blind to SQE opcodes (section 9).
Technical deep dive
§2 · The one-liner

“Async I/O through shared rings” hides five things

Most ops finish inline, not async. "No syscalls" needs SQPOLL, which burns a core. A naive swap gains only 1.06–1.10×; the redesign adds 2.05–2.31×. It is a second syscall surface that seccomp cannot see.

"io_uring is async I/O via two shared ring buffers, so you skip syscalls."

Hides:

  1. Most ops are not async: the kernel first tries the op inline, non-blocking in submit context. Async is the fallback, and for buffered file I/O the fallback is a thread pool (io-wq), not hardware async.
  2. "No syscalls" is only true with SQPOLL (burns a core); otherwise one io_uring_enter per batch. Win = amortization.
  3. Naive port gains about nothing (measured: 1.06x buffer mgr, 1.10x shuffle). Gains come from batching + registered resources + task-work control + redesigned architecture.
  4. It is a second syscall interface: ops live in SQEs, invisible to seccomp/syscall audit. Google disabled it on ChromeOS/prod.
  5. Zero-copy isn't free: ownership of buffers/cancellation is the hard part; ZC send loses to memcpy for small payloads [K].

Jasny et al. compare a naive swap with a redesigned io_uring path in a buffer manager and a network shuffle. The naive swap barely moves; the redesign does the work.

§3 · The problem

Linux aio copies 104 bytes and needs two syscalls per I/O

Linux aio was async only for O_DIRECT, copied 104 bytes per I/O and took at least two syscalls, so apps bolted on thread pools. The paper's 4K random reads: 608K IOPS for aio, 1.2M for io_uring without polling, 1.7M with it.

Before: Linux aio (io_submit/io_getevents).

  • Async only for O_DIRECT; buffered "behaves in a synchronous manner". [V] paper §1
  • Submit can still block (metadata fetch, device request slots exhausted) → apps still ran thread pools.
  • Copies: 64 B (iocb) + 8 B pointer on submit, 32 B (io_event) on completion → 104 B copied for "zero-copy" I/O. [V]
  • Completion ring exposed but "hard (impossible?) to use correctly". [V]
  • ≥2 syscalls per I/O (submit + getevents): "post spectre/meltdown ... a serious slowdown". [V]
  • Devices <10 µs latency, millions of IOPS: slow non-deterministic submit, bad single-core scaling.
  • epoll: readiness only; regular files always "ready" → no file I/O help; pair with thread pool. Thread pool for buffered I/O = ≥2 context switches even on page-cache hit. [V] paper §9.2

Axboe tried extending aio (2010 and again) → more entry points, worse API → started fresh. Goals: easy to use/hard to misuse, extensible, efficient, scalable; "no memory copies for either submissions or completion events, and no memory indirections" [V] §3-4. Merged 5.1 (Jan 2019 merge, May 2019 release).

Headline numbers from paper §9: 4K random reads — aio 608K IOPS, io_uring 1.2M (no polling), 1.7M (polling). Authors' own caveat: "these values don't carry a lot of absolute meaning" (unfair: aio has no polling).

§4 · Mental model

A restaurant order window: one bell for a stack of orders

Kitchen and diner share two belts: orders in (SQ), plates out (CQ). The diner stacks 32 slips and rings once. The cook does quick orders on the spot and parks slow ones. The analogy breaks where belts carry indexes and buffers stay yours.

Restaurant order windowKitchen (kernel) and diner (app) share two conveyor belts: orders in (SQ), plates out (CQ). The diner stacks 32 order slips then rings the bell once. The cook grabs whatever's quick (inline), parks slow orders on a side-queue (poll waitlist) or hands them to a prep crew (io-wq).

Breaks where:

The paper's picture of the same idea: the database and the kernel exchange requests through two rings in shared memory, and the submit call crosses the boundary once.

  • The belt carries indexes to slips, not slips (SQ array indirection).
  • The cook may not be asynchronous at all: simple orders finish while you're ringing the bell; the CQE is already there on return.
  • The prep crew = real kernel threads in your process (since 5.12), counted against RLIMIT_NPROC.
  • Once the cook has read a slip, you may reuse the slot, but the kernel may still be using your buffers.
§5 · Mechanism, traced

One read from SQE to CQE, usually with no thread

One io_uring_enter submits the batch and the kernel tries the read inline. A socket with no data sleeps on a poll list; a buffered file falls back to an iou-wrk worker. Results come back as CQEs read from shared memory.

Seven-step walkthrough inside.

5.1 Memory layout

mmap(fd, IORING_OFF_SQ_RING   = 0x0)         SQ ring: head tail ring_mask ring_entries flags dropped array[]
mmap(fd, IORING_OFF_CQ_RING   = 0x8000000)   CQ ring: head tail ring_mask ring_entries overflow cqes[]   (single mmap w/ SQ since 5.4)
mmap(fd, IORING_OFF_SQES      = 0x10000000)  sqes[ entries ] each 64 B

(IORING_OFF_PBUF_RING = 0x80000000, 5.19.) Offsets inside rings come from io_uring_params.sq_off / cq_off returned by io_uring_setup.

SQE (64 B) [V] field order; offsets reconstructed:

 0 opcode u8 | 1 flags u8 | 2 ioprio u16 | 4 fd s32
 8 off/addr2 u64 | 16 addr u64 | 24 len u32 | 28 op-flags u32
32 user_data u64   <- echoed in CQE, your correlation id
40 buf_index/buf_group u16 | 42 personality u16 | 44 splice_fd_in/file_index u32
48 addr3 u64 + pad   (SQE128, 5.19: 128 B for NVMe passthrough cmd)

CQE (16 B): user_data u64 | res s32 (bytes or -errno) | flags u32 (F_BUFFER, F_MORE, F_NOTIF; CQE32 = 32 B).

SQ ring holds indexes into array[], which index sqes[]: kernel does head = READ_ONCE(sq_array[cached_sq_head++ & mask]); sqe = &sq_sqes[head] (with array_index_nospec). CQ indexes cqes[] directly. Indirection lets apps embed SQEs in own structures and submit non-contiguously. IORING_SETUP_NO_SQARRAY (6.6) drops it.

CQ defaults to 2× SQ entries (CQSIZE overrides); sizes → power of 2.

5.2 One read(fd, buf, 4096) end to end

Step through the trace below (a socket read with no data yet, then the buffered-file variant). The ring pointers move as the app and kernel hand off.

app:   sqe = &sqes[tail & mask];  fill(opcode=READ, fd, addr=buf, len=4096, user_data=0xA1)
       array[tail & mask] = tail & mask
       store_release(sq.tail, tail+1)            # publish
       io_uring_enter(fd, to_submit=1, min_complete=1, GETEVENTS)   # 1 syscall for N sqes

kernel io_uring_enter -> io_submit_sqes (uring_lock)
   per SQE: io_alloc_req -> io_get_sqe -> io_submit_sqe -> io_init_req
   non-linked -> io_queue_sqe:
        issue_flags = NONBLOCK | COMPLETE_DEFER
        io_issue_sqe()  ----- inline attempt in *submitter's context* ---->
             page-cache hit / O_DIRECT w/ NOWAIT / socket w/ data  => completes, CQE posted
        ret == -EAGAIN ?

             APOLL_READY   became ready meanwhile: queue as task_work, retry

Key facts [V] from source:

  • Non-blocking ops complete inside the submit call; the CQE is already in the ring on return (paper §9.2).
  • IOSQE_ASYNC skips the inline attempt → straight to io-wq.
  • Completions from poll/io-wq come back via task_work on the submitting task. Plain TWA_SIGNAL = IPI that interrupts userspace.
  • __io_submit_flush_completions batches CQE posting.
Reality check"Async" for buffered file I/O = a kernel thread pool doing blocking syscalls (iou-wrk-* threads), like libuv's pool, just in-kernel and cheaper. Real async: O_DIRECT/NVMe with NOWAIT, sockets/pipes via poll.

Jasny et al. draw the three execution paths: inline completion, the poll set for sockets, and the worker fallback for blocking work.

5.3 io-wq details [V]

  • Two pools: bound (regular files/bdev; sized from SQ ring) and unbound (sockets, char devs; max = RLIMIT_NPROC).
  • Per-task, per-NUMA pools; workers are threads of the submitting task (5.12 NATIVE_WORKERS), idle timeout 5 s.
  • Hashed work serializes buffered writes to the same inode.
  • Control: IORING_REGISTER_IOWQ_MAX_WORKERS (5.15). Hitting RLIMIT_NPROC/cgroup pids.max → the ring may burn CPU retrying thread creation (Cloudflare "missing manuals").

5.4 SQPOLL

A per-ring kernel thread polls the SQ tail. Zero syscalls while awake.

thread idle > sq_thread_idle (default 1 s):
   atomic_or(sq.flags, NEED_WAKEUP); smp_mb__after_atomic(); recheck sq entries; sleep
app after tail store:
   full barrier;  if (load(sq.flags) & NEED_WAKEUP) io_uring_enter(SQ_WAKEUP)

The full barrier pairs with the thread's post-flag barrier: a classic Dekker-style store→load race. Without it the app sees no flag while the thread sees no entry → lost wakeup. Unprivileged since 5.13. Costs a core; Jasny et al. measure ~30 µs wake latency from sleep.

§6 · The math

Batching divides the syscall cost; queue depth sets IOPS

Cost per op is cs/B + co, so batching only hides the entry cost. Little's law gives IOPS = QD / latency: 100 µs reads need QD ≈ 100 for 1M IOPS. Sync POSIX ran 16.5K tx/s against 376K with io_uring, mostly from queue depth.

Two sliders inside.

Amortization

Let cs = enter syscall cost, co = per-op in-kernel work, B = ops per enter.

cost/op = cs / B + co→ in plain terms: batching divides the fixed cost. Jasny et al. measure 5-6× fewer cycles/op at B ≥ 16 [V] arXiv 2512.04859. The limit B→∞ gives co: you can't beat it, which is why SQPOLL/polling matter only when cs/B is still visible.

Little's law for queue depth

IOPS = QD / latency→ in plain terms: 100 µs NVMe read, 1M IOPS ⇒ QD = 100. Sync I/O has QD=1 per thread ⇒ 10K IOPS/thread. Jasny's synchronous POSIX baseline 16.5K tx/s vs 376K tx/s with io_uring (buffer manager, 1 thread) is mostly QD, not syscall cost. Batching isn't the only win; concurrency in one thread is.

Ring index arithmetic

head, tail are free-running u32. used = tail − head (mod 232), free = N − used, slot = idx & (N−1) (N power of 2).

used = (tail − head) mod 232; free = N − used; slot = idx & (N−1)→ in plain terms: Why free-running instead of wrapping at N: full vs empty are distinguishable (used==N vs 0) with no spare slot or flag; all N slots are usable. Correct across u32 overflow because of modular subtraction.

Memory-ordering contract (SQ)

App: write SQE; store_release(tail). Kernel: load_acquire(tail); read SQE. The release→acquire edge ⇒ SQE writes happen-before kernel reads. The kernel consumes with smp_store_release(sq.head) (seen in io_commit_sqring [V]); the app load_acquire(head) before reusing a slot. CQ mirrored. Without release on tail, the CPU/compiler could expose tail before the entry bytes ⇒ the kernel reads a garbage SQE. (CQ-side acquire/release pairings are inferred from paper + liburing, not read from source.)

CQ overflow bound

Pending requests can exceed SQ size (SQE consumed ⇒ slot reusable, request still in flight). In-flight P ≤ SQ_entries + inflight_async; CQ = 2×SQ by default doesn't bound P. Hence NODROP (5.5): overflow CQEs are held in a kernel list, flushed on next enter(GETEVENTS); a purely userspace CQ poller can stall forever.

§7 · Why it works

Remove any one piece and it falls back to aio or a thread pool

The core move is turning the syscall into data. Shared rings replace copies; inline-first avoids thread handoffs; the poll path avoids a thread per socket; io-wq catches the rest. Without user_data out-of-order completions cannot be matched.

Core insight: turn syscall into data. A syscall = control transfer + argument marshalling. Move marshalling to shared memory (SQE), make control transfer batched or removable (SQPOLL), and make completion a memory read (CQE).

Ablate each piece:

  • Remove shared rings → back to aio's copies/≥2 syscalls.
  • Remove inline-first attempt → every op pays a context switch to a worker even on page-cache hit (the thread-pool problem).
  • Remove poll-arm path → sockets need a worker thread per blocked op (thousands of threads) or you are back to epoll+read.
  • Remove io-wq fallback → buffered file I/O blocks io_uring_enter (submit stalls for disk), breaking the "submit never blocks" promise.
  • Remove registration → per-op atomic refcount + page pin; Jasny: registered buffers are part of the 2× gain.
  • Remove DEFER_TASKRUN → IPIs interrupt the app mid-batch, break batching, add jitter.
  • Remove the user_data indirection → can't match out-of-order completions.
§8 · Knobs & alternatives

Batch size, SQPOLL and polling trade cores for latency

You choose SQ depth, batch size, and whether to burn a core on SQPOLL or IOPOLL. Alternatives: epoll with threads (about 10% behind at 1,000 connections, one vendor benchmark), libaio for O_DIRECT, SPDK at about 2× the cores.

Knobs: SQ depth; CQ size; batch size B; SQPOLL (core vs latency); IOPOLL (poll NVMe CQ; needs O_DIRECT; reaps via GETEVENTS or SQPOLL thread); COOP vs DEFER_TASKRUN; registered files/bufs; IOWQ_MAX_WORKERS; passthrough; multishot + buffer rings.

Alternatives:

  • epoll + threads: simple, portable; no file I/O. Network gain of io_uring over tuned epoll ≈ ~10% @1000 conns (Alibaba blog, read in this pass; single vendor benchmark), single-digit–20% typical [K], big only with ZC/large batches.
  • libaio: O_DIRECT only; competitive for tuned Seastar/Scylla (Scylla engineers reported no big win [K, unverified]; Seastar/Scylla details not re-verified).
  • SPDK: userspace NVMe polling; "io_uring within ~10% of SPDK but ~2× the cores" (SYSTOR 2022, outside the 2y window) [V] via agent.
  • Windows IoRing: "almost identical" design, far fewer opcodes. IOCP: completion-based but a syscall per submit. kqueue (BSD/macOS): readiness only. TigerBeetle/Qt wrap them behind one API.
§9 · Where it breaks

A second syscall surface that seccomp cannot see

Google's kCTF: 60% of 42 Linux kernel exploit submissions targeted io_uring, so it was disabled on ChromeOS and production and blocked for Android apps. Seccomp sees only setup and enter calls, not the SQE opcodes.

Security (the big one)

  • Google kCTF/VRP post (14 Jun 2023): "60% of the submissions exploited the io_uring component" (of 42 Linux kernel exploit submissions), "~1 million USD for io_uring alone". Disabled on ChromeOS, production servers; Android seccomp-blocks it for apps. Stance: safe only for trusted components. [V] read directly in this pass
  • Bug classes = object-lifetime between ring-owned resources and user-visible mappings/fds, plus new opcodes reusing old fields:
    • CVE-2021-41073: PROVIDE_BUFFERS puts a kernel io_buffer* in req->rw.addr; loop_rw_iter treats it as a user ptr; later io_put_kbuf frees attacker-adjacent memory (type confusion). 5.10–5.14.6.
    • CVE-2022-2602: race between registered files in flight and unix-socket GC → UAF.
    • CVE-2023-2598: OOB physical-page access in fixed-buffer registration (folio/compound page coalescing), 6.3-rc1→6.4-rc1, full LPE.
    • CVE-2024-0582: pbuf ring register → mmap → unregister leaves a mapping to freed pages. (NVD says "memory leak"; mechanism from write-ups, confirm.)
  • Monitoring blind spot: seccomp sees only io_uring_setup/enter/register, never the SQE opcodes. ARMO "Curing" rootkit PoC (2025) ran C2 + file ops via io_uring; Falco blind, Tetragon default policies miss, MS Defender didn't detect [V] ARMO. Ops run from io-wq/task_work context also dodge sys_enter_* tracing.
  • Mitigations: kernel.io_uring_disabled sysctl (0 allow / 1 only io_uring_group or CAP_SYS_ADMIN, existing rings keep working / 2 -EPERM for all; 6.6 [K]); Docker default seccomp blocks it; containerd 2.0 removed from RuntimeDefault [search-only].
Gotcha: seccomp sees three syscalls, not the opsEverything an SQE does (OPENAT, READ, SEND, CONNECT) happens behind io_uring_enter. A syscall-keyed audit or EDR policy never sees it.

Correctness / perf pitfalls

  • Completions are unordered. fsync can complete before the write is issued unless linked (man page quote). IOSQE_IO_DRAIN = full barrier, expensive.
  • Cancel: ASYNC_CANCEL yields 2 CQEs, order unspecified; in-flight disk I/O "typically cannot be canceled" (stray DMA risk). Tokio's drop-cancels-future model collides: a dropped future ≠ a stopped kernel write into your buffer → owned-buffer APIs (without.boats).
  • io-wq thread explosion vs RLIMIT_NPROC/pids.max.
  • Multishot: the ring of provided buffers runs dry ⇒ -ENOBUFS, multishot terminates [K]; absent F_MORE ⇒ re-arm.
  • SEND_ZC: pin + extra notif CQE costs more than memcpy for small sends (~<10 KB) [K].
  • io-wq/SQPOLL threads are real tasks ⇒ coredump/ptrace/freezer regressions [search-only].
  • Kernel-version fragmentation: 5.19→6.0→6.1→6.6→6.15… portable code needs fallbacks; nginx cited regressions + tuning cost, never merged.
Misconception"io_uring = faster epoll." Jasny et al.: swapping interfaces naively → 1.06× / 1.10×.
§10 · In the wild

Engines use it where the win is, and deviate from the paper

RocksDB uses it only on read paths. libuv moved file ops to it, then reverted the default to the thread pool in v1.49. Jasny et al. report +14% for PostgreSQL after applying their guidelines. Glommio runs thread-per-core on io_uring.

RocksDB

io_uring on read paths only (MultiGet, iterator prefetch), thread-local rings, SINGLE_ISSUER|DEFER_TASKRUN; ~24% over pread on raw disk ([unverified (single secondary source)]; the 2022 RocksDB blog does not mention io_uring; the opt-in claim is likewise unverified). Not writes/compaction.

TigerBeetle

Single thread alternating tick() and io.run_for_ns(); all I/O via io_uring (kqueue/IOCP behind abstraction); a mid-2026 newsletter reports +8% from re-entering the kernel after each completion callback to pipeline IO and CPU (secondary).

Seastar / Scylla

io_uring reactor backend exists; long-default linux-aio+epoll [K] (not independently re-verified).

libuv / Node

io_uring for file ops only; network stays epoll; ref issue #1947 (+38% seq read, tighter variance in thread); later restricted for security [K].

QEMU

(not independently re-verified) 1.2M (no poll) / 1.7M (poll) 4K IOPS vs Linux AIO cliff ~608K (FOSDEM 2020); 2025 series makes io_uring the event loop (aio_add_sqe).

PostgreSQL 18

io_method=io_uring (default worker, per the PG 18 docs [V]); guidelines from the Jasny paper → +14%.

Glommio / tokio-uring / nginx

Glommio (thread-per-core, io_uring-native; not independently re-verified), tokio-uring (stale since 0.5.0, May 2024), nginx (not merged).

10M IOPS/core

Axboe, Ryzen 5950X, 2× Optane P5800X, 512B polled random reads, fixed files/bufs: a per-IO software overhead microbenchmark, not app throughput. [V] Phoronix

§11 · Frontier

The frontier moves to zero-copy receive and BPF-run rings

Zero-copy receive, merged in Linux 6.15, hands NIC buffers to user space; one core saturated 200G in the demo. A BPF struct_ops series could replace the enter loop, with merge status only secondhand. Restrictions plus a cBPF filter cannot inspect arguments.

§11b · Open problems

Sandboxing io_uring without disabling it is still unsolved

Filters see opcodes but not safe arguments, and pointers live in shared memory (TOCTOU). Disk I/O cannot be cancelled, so a cancel can DMA into reused pages. Buffered file I/O stays on a thread pool until every filesystem has NOWAIT paths.

  1. Sandboxing. Disable-for-untrusted is the current answer. seccomp can't see opcodes; attack surface grows per opcode/registration type (zcrx, uring_cmd). The task-restriction/cBPF filter is the live attempt; coarse (no arg inspection). Hard because opcodes carry pointers/flags nested in shared memory the filter can't TOCTOU-safely inspect. [reasoning mine]
  2. Cancellation of in-flight block I/O. Needs hardware-side cancel to avoid stray DMA into reused pages. Axboe on LKML: file/bdev I/O can't be cancelled.
  3. Truly async buffered I/O. Page-cache miss alloc, block allocation, journalling, fsync still punt to io-wq; needs NOWAIT through every FS path. Async-buffered-read patches (2020: preadv 1m13s vs io_uring 12.0 s/82% CPU vs patched 9.3 s/52% CPU) fixed reads only partially.
  4. Resource accounting. io-wq per-task×NUMA pools vs RLIMIT_NPROC/pids.max; no clean per-ring CPU accounting.
  5. Security observability. EDR keyed on syscalls is blind; LSM/KRSI hooks proposed, not default.
  6. API complexity vs adoption. Pestka et al.; Jasny et al. say gains need redesign. Open: can a higher-level library give 80% of the win without redesign? (tokio-uring's stall suggests cancellation semantics are the blocker.)
  7. Cross-OS standard. Windows IoRing is similar but narrower; BSDs/macOS have no completion API.
§12 · Lineage

Linux aio (2002) failed on copies; io_uring shipped in 5.1 (2019)

Linux aio was O_DIRECT-only and copy-heavy, while Windows IOCP was completion-based from the 1990s. io_uring then gained fixed resources and multishot (5.19), DEFER_TASKRUN (6.0–6.1), NVMe passthrough, zero-copy receive (6.15) and BPF rings targeted for 7.1.

POSIX aio / glibc thread-emulated aio → Linux aio (2002, O_DIRECT) → Windows IOCP (1990s, completion model) → io_uring 5.1 (2019) → fixed resources, multishot, buffer rings (5.19–6.0) → DEFER_TASKRUN/SINGLE_ISSUER (6.0–6.1) → NVMe passthrough (5.19–6.0) → zcrx (6.15, 2025) → BPF-in-ring (7.1 target, 2026). Peers: Windows IoRing (Win11), SPDK.

Key papers: Axboe "Efficient IO with io_uring" (2019, v0.4); Joshi FAST'24; Jasny VLDB'26.

§13 · Hands-on

A 30-line program shows the syscall count and the inline/punt split

Read 64 blocks per round, count io_uring_enter calls with strace, then drop caches to watch iou-wrk threads appear. Predict first. Needs Linux 5.19+ and liburing. The author did not compile it; run it on your kernel.

See the syscall count collapse and the inline/punt split. Needs Linux ≥5.19, liburing-dev, strace.

// Not compiled/run by the author (no Linux/liburing available when checked). cc -O2 t.c -luring -o t
#include <liburing.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#define N 4096
int main(int argc, char **argv) {
    int sqpoll = argc > 2 && !strcmp(argv[2], "sqpoll");
    int fd = open(argv[1], O_RDONLY /* | O_DIRECT for true async */);
    struct io_uring r; struct io_uring_params p = {0};
    if (sqpoll) { p.flags = IORING_SETUP_SQPOLL; p.sq_thread_idle = 2000; }
    io_uring_queue_init_params(256, &r, &p);
    static char buf[N][4096];
    for (int round = 0; round < 100; round++) {
        for (int i = 0; i < 64; i++) {
            struct io_uring_sqe *s = io_uring_get_sqe(&r);
            io_uring_prep_read(s, fd, buf[i], 4096, (__u64)i * 4096);
            s->user_data = i;
        }
        io_uring_submit(&r);              // 1 enter per 64 reads (0 w/ SQPOLL awake)
        for (int i = 0; i < 64; i++) {
            struct io_uring_cqe *c;
            io_uring_wait_cqe(&r, &c);
            io_uring_cqe_seen(&r, c);
        }
    }
    printf("done\n");
}

Run:

dd if=/dev/urandom of=f bs=1M count=64; strace -f -c -e trace=io_uring_enter,pread64 ./t f   # vs: ... ./t f sqpoll

Predict then check:

  1. Enter count ≈ 100–200 (not 6400). Why not exactly 100? (wait_cqe enters when CQ is empty.)
  2. With a page-cache-warm file: most CQEs are already present on return from submit ⇒ wait_cqe doesn't enter (inline completion).
  3. Drop caches (echo 3 > /proc/sys/vm/drop_caches), rerun, ps -L / top -H during the run: see iou-wrk-* threads ⇒ buffered punt to io-wq.
  4. Switch open to O_DIRECT (aligned buffers needed: use posix_memalign) → threads vanish on NVMe.
  5. sqpoll: strace shows ~0 enters; top -H shows an iou-sqp-* thread at 100% CPU.
§14 · Question ladder

Test yourself

24 questions from mechanism to open research. Reveal, then mark ✓ or ✗; marks feed your progress ring.

Answer in your head first, then reveal and mark yourself honestly. Marks are saved in this browser and feed the progress ring.

Mechanism
1. What exactly happens, step by step, from io_uring_submit() for a socket read with no data yet?

SQE written, tail released; enter → io_submit_sqes → io_queue_sqe → inline io_issue_sqe with NONBLOCK → socket returns -EAGAIN → io_queue_async copies SQE → io_arm_poll_handler → APOLL_OK: request sleeps on socket waitqueue (no thread). Data arrives → wakeup → io_poll_task_func (task_work) rechecks with vfs_poll, reissues, posts CQE.

→ related card
2. Why does the SQ ring hold indexes into array[] rather than SQEs, and what did 6.6 change?

Lets apps submit non-contiguous SQEs / embed SQEs in own structs. NO_SQARRAY (6.6) removes the extra load and the indirection when apps don't need it.

→ related card
3. How does the kernel know the app has freed an SQE slot, and why is that safe with in-flight requests?

Kernel smp_store_release(sq.head) after consuming (io_commit_sqring); app acquires head. Safe because the kernel copies the SQE into the request (io_req_sqe_copy, FEAT_SUBMIT_STABLE 5.5) when it will need it later; user buffers aren't copied — you must keep those alive.

→ related card
4. What does CQE_F_MORE mean for multishot recv and SEND_ZC, and how do the two differ?

MORE on multishot: request still armed, more CQEs will come; absence ⇒ re-arm. MORE on SEND_ZC: a second F_NOTIF CQE follows meaning "buffer reusable"; the first CQE carries bytes sent.

→ related card
5. Why must SQPOLL's NEED_WAKEUP flow have a full barrier on both sides?

Store-load ordering (Dekker): app stores tail then loads flag; thread stores flag then loads tail. Without a full barrier both can read stale values → app sees no flag, thread sees no entries → sleeps forever with work pending.

→ related card
6. What is task_work, and why does DEFER_TASKRUN require SINGLE_ISSUER?

task_work = a callback run in the context of a specific task at kernel→user transition (or an explicit point). DEFER_TASKRUN runs it only within io_uring_enter(GETEVENTS) on the ring's work_llist; only the submitter task may reap, hence single issuer.

→ related card
Why
7. Why try inline non-blocking first rather than always queue?

Most ops (page-cache hit, ready socket, NOWAIT O_DIRECT) finish immediately; queueing costs ≥2 context switches. Inline = no handoff, CQE ready on return.

→ related card
8. Why two io-wq pools (bound/unbound)?

Bound ops (regular files/bdev) have bounded concurrency tied to the device queue; unbound (sockets) can block indefinitely; mixing would let slow sockets starve disk work or force an arbitrary cap.

→ related card
9. Why are free-running indexes better than wrapping indexes?

Full vs empty distinguishable without a wasted slot; all N usable; modular subtraction handles u32 wrap.

→ related card
10. Why do provided buffer rings make multishot recv scale better than epoll+read for idle connections?

Provided buffers are picked at data arrival, so idle connections hold no buffer; epoll+read typically needs a buffer per connection (or read-after-ready, which still needs a buffer at that time but costs a syscall each).

→ related card
Counterfactual
11. If CQ were exactly SQ size and no NODROP, what breaks?

A burst of completions exceeds CQ while the app is busy ⇒ completions dropped (pre-5.5) or must be stored; with NODROP they pile in kernel memory until the app enters; extreme case: lost/stalled completions.

→ related card
12. If io-wq workers were kernel threads (pre-5.12) not process threads, what changes for cgroups/creds/ptrace?

Kernel threads: separate creds/cgroup/ptrace invisibility, harder accounting, no RLIMIT_NPROC coupling; 5.12 made them process threads: inherit cgroup/creds, visible to ptrace/coredump (and regressions).

→ related card
13. If SEND_ZC had no notification CQE, what could go wrong?

App reuses/frees the buffer while the NIC still DMAs from it ⇒ corrupted data on the wire or use-after-free of page contents.

→ related card
14. If the kernel read your SQE lazily (after returning) without copying it, what bug appears?

App reuses the slot, kernel executes the new SQE (or a half-written one) ⇒ wrong op/args. Hence copy-on-defer.

→ related card
Adversarial
15. How would you hide file exfiltration from a seccomp+Falco setup using io_uring?

Do exfil via SQEs: OPENAT, READ, SEND/CONNECT ops; seccomp sees only enter; Falco hooks syscalls → blind (ARMO Curing).

→ related card
16. Where is the TOCTOU surface when the kernel reads shared-memory SQEs?

Kernel reads SQE fields from user-writable memory (after READ_ONCE); an app thread can mutate the SQE or pointed-to structs concurrently. A per-opcode filter that inspects args at filter time may see different values than at execution; the kernel mitigates by copying the SQE before use, but pointer targets (iovecs, msghdr) remain user memory.

→ related card
17. How could a registered-buffer bug give physical-memory access (cf. CVE-2023-2598)?

Fixed-buffer registration coalesces pages into compound-page folios; wrong arithmetic computes a buffer range/length past the folio ⇒ read/write to adjacent physical pages through the registered buffer ⇒ kernel memory R/W ⇒ LPE.

→ related card
18. How would you DoS a host using only unprivileged io_uring and RLIMIT_NPROC?

Queue many blocking unbound ops (e.g., reads on a socket/pipe that never gets data) across many ring-submitting threads: each can spawn io-wq workers up to RLIMIT_NPROC (per-user), starving the user/container of threads; with pids.max, workers burn CPU retrying creation.

→ related card
Connection
19. Compare io_uring's SQ/CQ with NVMe's submission/completion queues. What does passthrough remove?

Same producer/consumer queue pair idea; io_uring has an extra software layer (block layer, page cache, FS). Passthrough (URING_CMD + /dev/ng*) skips block layer/FS so the NVMe SQE goes nearly straight to the device queue; you give up caching, FS semantics, LBA mgmt (16–40% IOPS gain in FAST'24).

→ related card
20. How does completion-based I/O change Rust's Future cancellation model?

Rust futures are cancelled by drop; with readiness that's safe. With completion, the kernel may still write into your buffer after drop ⇒ UB. Fix: ownership transfer of buffers (tokio-uring style APIs) or cancel-and-wait; cost: ergonomics, no &mut [u8] APIs.

→ related card
21. How is Little's law behind both NVMe queue depth and why sync I/O is slow?

IOPS = QD/latency: the device has ~µs–100 µs latency, so to reach 1M IOPS you need ~100 in flight. Sync I/O has QD=1/thread; io_uring/NVMe queues allow deep QD from one thread.

→ related card
Open
22. Can a sandbox filter io_uring per-op without TOCTOU and without disabling it?

Open. Needs filtering at the semantic level (opcode + stable args) with a TOCTOU-safe copy; the current cBPF filter doesn't inspect args. Alternative: capability-style per-ring restrictions (existing REGISTER_RESTRICTIONS) — coarse.

→ related card
23. Can buffered file I/O ever be truly async on Linux without per-filesystem NOWAIT work?

Open. Requires NOWAIT support for allocation, journalling, writeback throttling in each FS; or accept the thread pool as the implementation (what io-wq is).

→ related card
24. Should the ring be BPF-programmable, or does that grow the attack surface faster than it removes syscalls?

Open. BPF removes syscalls and enables custom completion logic but adds a verified-code attack surface and interaction with cancellation; the history of BPF verifier bugs argues caution; the unprivileged cBPF filter is the conservative variant.

→ related card
