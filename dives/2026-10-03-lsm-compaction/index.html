LSM-tree compaction: leveling vs tiering vs lazy leveling

TL;DR. Databases built on log-structured merge trees turn random writes into cheap sequential ones, then pay later by re-merging sorted files in the background. How eagerly they merge sets write amplification, read cost and disk space. Leveling merges eagerly (fast reads, tight space, heavy rewriting); tiering merges lazily (cheap writes, many runs, more space); lazy leveling mixes both and keeps most of each win.

Why it matters. The same dial explains write stalls, p99 spikes, SSD wear, disk-full-during-compaction, and even resurrected deleted rows.

0b. Plain English first

Explain it simply. Imagine a librarian who receives new books all day. Shelving each book in exactly the right alphabetical spot costs a walk across the library every time. So instead the librarian drops new books on a "recent" cart. When the cart is full, the whole cart is sorted once and shelved as a neat batch. Over time, you have many sorted batches, and finding a book means checking every batch. So the librarian periodically merges batches into bigger sorted batches. That merging is compaction.

The big question is how eagerly to merge. Merge constantly and finding a book is easy (few batches) but the librarian re-handles the same books over and over. Merge lazily and shelving is cheap but searching means checking many batches, and old, replaced copies pile up. Every database built this way (RocksDB, Cassandra, and others) is choosing a point on that dial.

Everyday example. A shop logs sales. Each day's 100 sales get sorted and stored as a "daily pile". Rule A (eager): when a new daily pile arrives, immediately merge it into the one big "history pile". Finding a sale means checking one pile, but every day you re-copy the entire history. Rule B (lazy): keep the daily piles; once you have 10, merge them into one "ten-day pile"; once you have 10 of those, merge into a "hundred-day pile". Copying is far less, but looking up a sale means checking up to ~10 piles per tier. Rule C (hybrid): lazy for the small recent tiers, eager for the single giant bottom pile, so old stuff stays tidy while recent writes stay cheap.

Bridge: now the same thing, technically.

1. Bare-minimum context

  • Memtable: in-memory sorted buffer absorbing writes; flushed to disk as an immutable sorted file (SSTable / "run") when full. Writes are also appended to a WAL for durability.
  • Run: one immutable sorted file (or set of files). Reads must consult every run that might contain the key.
  • Level: a group of runs; level i holds roughly T× the data of level i−1 (T = size ratio).
  • Bloom filter: per-run probabilistic membership test, false-positive rate p; lets point lookups skip runs.
  • Amplification trio: write amp (bytes written to disk per user byte), read amp (runs/pages touched per lookup), space amp (bytes on disk per live byte). Compaction trades among them.
  • DAM model: cost = number of page I/Os. All the closed-form results below use it.

Primary sources: O'Neil 1996, Monkey SIGMOD'17, Dostoevsky SIGMOD'18.

Use LSM / leveling when

  • Read-heavy but on LSM: leveled for tight space and few runs
  • Universal/tiered when write amp dominates and 2× temp space is OK
  • FIFO for TTL logs/metrics

Skip / pick a B-tree when

  • Read latency predictability beats write throughput
  • Tail latency is critical (stalls are LSM-specific)
  • You want little compaction tuning (InnoDB, Postgres, LMDB)
  • Signs you chose wrong: L0 count climbing, stalls, disk 2× spikes

What it is. A log-structured merge tree stores data as immutable sorted runs and compaction is the background process that merges runs to bound read cost, discard overwritten/deleted data, and reclaim space. The compaction policy (when, which runs, how much) is the single biggest tuning lever in an LSM engine.

Why it exists. B-trees update pages in place: a random write per update, which is slow on spinning disks and wears SSDs. LSM turns random writes into sequential ones (one memtable flush) and pays later, in background merges. Facebook's MyRocks post reports an instance 3.5× smaller than uncompressed InnoDB and 2× smaller than compressed InnoDB, with "orders of magnitude less" data written (MyRocks); the CIDR'17 abstract says RocksDB uses less than half the storage InnoDB uses (Dong et al.).

Where it's used (each checked against a primary or official page unless tagged): - RocksDB at Facebook/Meta: MyRocks (MySQL engine). - Cassandra / ScyllaDB: the compaction overview docs say STCS is the default strategy (check your version); LCS "is optimized for read heavy workloads"; TWCS is for TTL'd, mostly immutable time-series. Cassandra 5.0 adds UCS (CEP-26) and its docs say it is "recommended for most workloads"; UCS default is scaling_parameters = T4, with the fan factor f = 2 + |w| (w<0 leveled L_f, w>0 tiered T_f). ScyllaDB's Incremental Compaction uses ~1 GB fragments (sstable_size_in_mb=1000) freed as they finish, cutting ~200 GB of STCS temporary space to ~2 GB and reaching ~90–93% disk use vs the ~50% STCS rule of thumb; steady-state space amp stays "relatively high" like STCS. - CockroachDB Pebble: Go RocksDB descendant; the CRDB docs call a read amplification below 10 healthy. L0 sublevels and the ">10 visible, >20 stalls" operator rule come from netdata guides (secondary). - TiKV/TiDB: two RocksDB instances per node (data and Raft log); Titan (key-value separation) is on by default for new clusters since v7.6.0. - SlateDB (object-storage LSM): pluggable compaction scheduler, only size-tiered shipped; distributed compaction via a shared .compactions file (RFC-0025, v0.14.1+); "trivial move" off by default. Its scaling figures are the project's own claims. - YugabyteDB ("highly customized" RocksDB), Flink (EmbeddedRocksDBStateBackend), Bigtable (memtable→SSTable minor compaction, major compaction merges all SSTables), LevelDB as Chrome's IndexedDB backend (Wikipedia, secondary), ClickHouse MergeTree (parts merged in background; "no memtable" is an inference from the docs' silence). Kafka Streams default store RocksDB and HBase minor/major compaction: weak evidence (unverified).

When to use / not. Use leveled for read-heavy or space-sensitive workloads on SSD (worst case ≈1.111 with dynamic level bytes per Dong et al.). Use tiered/universal for write-heavy ingestion where write amp dominates and you can afford 2× temporary space and more runs per read. Use FIFO for TTL'd caches/metrics (write amp ≈ 1). Pick a B-tree when read latency predictability matters more than write throughput, tail latency is critical (compaction/stalls are LSM-specific), or you want less operational tuning (InnoDB, Postgres, LMDB).

Who should care. Backend/infra engineers running RocksDB-backed stores; Cassandra/Scylla operators choosing strategies; anyone debugging p99 spikes, write stalls, disk-full-during-compaction, or SSD wear.

Technical deep dive

2. The one-liner and what it hides

"Leveling = fast reads, slow writes; tiering = fast writes, slow reads."

It hides: 1. The tradeoff is not symmetric across levels: space amp is set by the last level, update cost accumulates over all levels. Hence hybrids (lazy leveling). 2. Bloom filter memory must be allocated non-uniformly (Monkey), or lookup cost silently grows with the number of levels. 3. The formulas are worst-case DAM bounds; real write amp is shaped by partial compaction, compression, skew, and the SSD's own write amp (multiplicative). 4. Compaction is also where deletes become real, so it is a correctness hazard, not just a performance knob (tombstones, snapshots, gc_grace). 5. Compaction competes with foreground I/O: the "optimal" policy on paper can be a tail-latency disaster (write stalls).

3. The problem

A random 4 KB update to a B-tree touches a leaf page: ~1 random read + 1 random write, with write amp up to page-size / entry-size from rewriting whole pages (illustrative arithmetic: 4096 / 100 ≈ 40×; not a measured figure). An LSM instead batches: buffer B·P entries, write once sequentially. But now a key's versions can be in the memtable and in any run. Without merging, runs grow without bound and lookup cost grows with them; obsolete versions and tombstones never die. Compaction bounds that, at the price of rewriting data. Question: how many times should each byte be rewritten, and how many runs may a lookup face?

4. Mental model

Analogy: laundry. Wash small loads often (leveling: always merge into the one big pile, clothes are always sorted but you rewash the same shirts constantly) or let loads accumulate in baskets and wash baskets together (tiering).

Where it breaks: laundry has no cost for finding a shirt; here, a lookup must probe every basket (run) unless a Bloom filter says "not here." And deleting a shirt means writing a "delete marker" that must travel to the bottom of the pile before the shirt's space is reclaimed.

LEVELING (1 run per level; level i capacity T^(i+1)):
 flush1: L0=[1]
 flush2: merge into L0 -> [2]                         (rewrote 1)
 flush3: merge -> [3]  (3 > cap? cap(L0)=3, no)       (rewrote 2)
 flush4: merge -> [4] > cap 3 -> push down: L1=[4]    (rewrote 3)
 flush5: L0=[1]; flush6: [2]; flush7: [3]; flush8: [4] -> merge into L1 -> [8] (rewrote 4+4)
 each level re-merges its resident data up to ~(T-1)/2 times on average before overflowing

TIERING (up to T runs per level; merge all when T arrive):
 flush1: L0=[1]; flush2: L0=[1,1]; flush3: L0=[1,1,1] -> T runs -> merge -> L1=[3]  (wrote 3)
 flush4..6: same -> L1=[3,3]; flush7..9 -> L1=[3,3,3] -> merge -> L2=[9]            (wrote 9)
 each entry is written ~once per level; a lookup may face up to T-1 runs per level

Real code path in RocksDB (leveled): compaction picker scores each level (L0: max(num_files / level0_file_num_compaction_trigger, total_size / max_bytes_for_level_base); L1+: size / target), compacts the highest score ≥ 1, picks the file with least overlap ratio in the next level (kMinOverlappingRatio), merges the file with its overlapping next-level files, optionally split into subcompactions by key range across threads (wiki). Merging drops shadowed versions and, at the bottom level, tombstones.

6. The math

Notation (Monkey/Dostoevsky): N entries, B entries/page, P buffer pages, T size ratio, L levels, M filter bits, p_i Bloom FPR at level i, φ write/read cost ratio (SSD asymmetry), μ scan-vs-seek factor, s scan selectivity.

Levels (Eq.1): the last level holds ≈ N(T−1)/T entries, so

L = ⌈ log_T( N·E / M_buffer · (T−1)/T ) ⌉

→ in plain terms: each level is T× bigger, so you need log base T of (data/buffer) levels. Bigger T = fewer levels (T→T_lim collapses to 1 level = a sorted array).

O'Neil's origin of leveling cost (Thm 3.1): with K disk components of ratios r_i = S_i/S_{i−1}, merge I/O is minimized when all r_i are equal; H = (2R/Sp)·(K(1+r) − ½). → each byte is read and written about (1+r) times per level, which is where leveling's ~T-per-level cost comes from.

Update cost (Monkey Eq.10): - Leveling: W = (L/B)·((T−1)/2)·(1+φ) - Tiering: W = (L/B)·((T−1)/T)·(1+φ)

→ under leveling each entry is merged ≈ (T−1)/2 times per level (it sits in a level while arrivals merge into it, then moves on); under tiering ≈ once per level. Why not simpler? Because the same amount of merge work happens per level in aggregate (bigger levels merge exponentially more data, exponentially less often), so the cost per entry per level is set only by how many times a level's resident data is re-merged.

Zero-result lookup (Eq.3): R = Σp_i (leveling, ≤1 run/level) or (T−1)·Σp_i (tiering). The filter FPR is p = e^(−(bits/entry)·ln²2). Monkey's optimization (Lagrange): minimize R subject to total filter memory fixed → optimal p_i ∝ entries at level i, i.e. p_i = T·p_{i−1}: give the small levels tiny FPR, the huge last level a large one. Because probing any run costs one I/O regardless of its size, memory buys more I/O avoided on small levels. Result: with enough memory R = O(e^(−M/N)), independent of L, versus O(L·e^(−M/N)) for uniform allocation. → uniform 10 bits/entry costs R ≈ L·0.008; Monkey's allocation removes the L factor.

Dostoevsky's table (worst case, Section 3):

Tiering Leveling Lazy leveling
Update W O(L/B) O(L·T/B) O((L+T)/B)
Zero-result lookup R O(T·e^(−M/N)) O(e^(−M/N)) O(e^(−M/N))
Existing-key lookup V O(1 + T·e^(−M/N)) O(1) O(1)
Short range O(T·L) O(L) O(1 + (L−1)·T)
Long range O(T·s/B) O(s/B) O(s/B)

→ lazy leveling = tiering on levels 1…L−1, leveling at level L. It keeps leveling's lookup/space cost but cuts update cost from L·T to L+T, paying only on short scans.

Fluid LSM-tree generalizes: K = max runs at levels 1…L−1, Z = max runs at level L. Leveling K=Z=1; tiering K=Z=T−1; lazy K=T−1, Z=1. - Eq.12: W = φ/(μB)·((T−1)/(K+1)·(L−1) + (T−1)/(Z+1)) - Eq.13: excess space = Z − 1 + 1/T (T=10, 10 bits/entry: leveling 0.1, tiering 8.1) Sanity: K=Z=1 gives (T−1)/2·L; K=Z=T−1 gives (T−1)/T·L (matches Monkey Eq.10).

Monkey exact forms (rendered pages checked): per-level FPR leveling Eq.15 p_i = R/T^(L−i) · T^(L−1)/(T^L−1) · (T−1); tiering Eq.16 p_i = R/T^(L−i) · T^(L−1)/(T^L−1) (a factor (T−1) lower). For large L (≈5+): p_i ≈ R/T^(L−i+1)·(T−1) (leveling), R/T^(L−i+1) (tiering). Zero-result cost Eq.7: R = R_filtered + R_unfiltered, R_filtered = [T^(T/(T−1))/(T−1)] · e^(−(M_filters/N)·ln²2) · T^(L_unfiltered) for leveling (without the 1/(T−1) for tiering); R_unfiltered = L_unfiltered (leveling) or L_unfiltered·(T−1) (tiering). Eq.8: M_threshold = N/ln²2 · ln T/(T−1), and L_unfiltered = 0 if M_filters ≥ M_threshold. Dostoevsky Eq.7 gives the lazy-leveling threshold maximum 1.62 bits/entry at T=3 (and says the Fluid LSM generalization keeps 1.62). The "no strategy wins everywhere" statement elsewhere is a paraphrase of Sarkar et al., not a quote.

7. Why it works

Key insight: lookup and space cost are determined by the shape of the last level (it holds ~(T−1)/T of the data); update cost is determined by how often data is re-merged across all levels. Those are different levels, so you can pick different policies for each. Ablation: - Remove the size-ratio geometry (equal-sized levels) → O'Neil's theorem says merge I/O is no longer minimal. - Remove Bloom filters → every run is probed; tiering lookups cost T·L I/Os. - Uniform filters instead of Monkey's → lookup cost grows with L. - Remove tombstone dropping at the bottom level → deleted data is never freed. - Remove dynamic level sizing in RocksDB → space amp worse (static mode: Dong et al. §3.1 say space amp "would be larger than 2" when the last level is only slightly bigger than the previous level's target); with it ≈ 1.11 at T=10 because ~90% of data sits in the last level (CIDR'17).

9. Where it breaks

  • Write stalls: not a bug but deliberate backpressure when L0 file count or pending-compaction bytes exceed thresholds. Raising triggers moves the cliff later and deeper. Per SILK (ATC'19): tail latency comes from client writes, flushes and compactions fighting for I/O bandwidth; the abstract claims "up to two orders of magnitude lower 99th percentile latencies than RocksDB and TRIAD" by giving internal ops spare bandwidth when load is low, prioritizing flushes and lower-level compactions, and preempting compactions. SILK was a RocksDB prototype; I found no upstream merge (unverified), though RocksDB does have an auto-tuned rate limiter and IO priorities (search).
  • L0 read amp: the wiki says "we have to pick up all the L0 files because they usually are overlapping" and the tuning guide says point lookups "must consult all files in level 0"; range-scan read amp ≈ number_of_level0_files + number_of_non_empty_levels. Mitigations: intra-L0 compaction (bounded by max_compaction_bytes), subcompactions; Pebble's sublevels (secondary).
  • Write-stall conditions (RocksDB Write-Stalls wiki): memtables ≥ max_write_buffer_number; L0 files reach slowdown/stop triggers; pending compaction bytes reach soft/hard limits. Stalls apply DB-wide though triggers are per column family.
  • Space spikes: universal compaction can need up to 2× disk during a full compaction; "leveling = 1.1× space" is a steady-state figure, snapshots/iterators pin old files.
  • Delete problem (Lethe, SIGMOD'20): no bound on how long a tombstone takes to reach the last level, so physical deletion (GDPR!) is unbounded. FADE (age-prioritized compaction) and KiWi (page-level secondary range deletes) reported 1.17–1.4× read throughput, 2.1–9.8× lower space amp, 4–25% more write amp (arXiv abstract; the FADE/KiWi names are the paper's, not shown in my fetch).
  • Write amp stacks (no primary quote obtained; follows from the definition of device WA = flash writes incl. GC ÷ host writes): total flash writes = app bytes × LSM WA (10–50× typical) × device WAF; compaction's large sequential rewrites keep device WAF low (1–2) on an uncrowded drive, worse when shared/near-full (unverified).
  • Correctness hazards: compaction is the only place data is deliberately discarded. Incidents: PingCAP's RocksDB DeleteRange corruption post (Medium returned 403; per search snippet: data corrupted, cluster panicked, details unverified); CockroachDB Advisory 48860 ("permanent data corruption or loss in rare cases" from range deletions concurrent with replica GC; "irrecoverable using regular node failover", needs backup restore; fixed in v19.1.9, v19.2.7, v20.1.0). Cassandra zombie data: if repair doesn't finish within gc_grace_seconds (default 864000 s = 10 days), a replica can purge a tombstone while another still holds the live row, which then resurrects.

  • Compaction storms (many shards/column families compacting after bulk load/restart) (unverified, from memory): mitigated by rate limiters, jitter, max_background_jobs.

  • Range deletes are the riskiest compaction feature. RocksDB fragments range tombstones per SST so they don't overlap and can be binary-searched, rewrites them across files during compaction, keeps sequence numbers for snapshots, and drops them at the bottom level (blog). Pebble truncates them to file bounds and needs atomic compaction groups (adjacent files sharing a boundary user key must be compacted together) so a tombstone can't wrongly cover data that moved down alone (doc). Pebble range keys: unverified.

Misconceptions: "stalls mean mis-tuning" (often it's sustained ingest > compaction bandwidth); "more threads is better" (SILK: scheduling beats parallelism); "deleting frees space now" (only after the tombstone hits the last level); "tombstone purge after gc_grace is safe" (only if repair completed).

10. In the wild

  • RocksDB: leveled default; score-based picker; dynamic level bytes default since v8.4; subcompactions; universal and FIFO styles. The tuning guide's worked example computes "1 + 2 + 10 + 10 + 10 = 33" write amp and space amp 1.14; the Leveled-Compaction wiki (Intra-L0 section) calls leveled write amp "often larger than 10"; "10–30× in practice" is my range from these sources, not one measurement.
  • Universal (tiered): write amp often 2–7× (unverified); wiki trigger order: data age (hard requirement) → space-amp (full compaction) → sorted-run count respecting size_ratio → run count without it; "temporarily double the disk space" during a full compaction.
  • Cassandra: STCS default; UCS (5.0) unifies tiered/leveled with scaling parameter W and density-based sharding.
  • ScyllaDB ICS: ~1 GB fragments freed incrementally (see section 1b). I could not find a "space amplification goal 1–2" in the primary post, so that claim was dropped.
  • Pebble: CRDB docs only say read amp <10 is healthy; the sublevel >10/>20 thresholds and admission.l0_sub_level_count_overload_threshold = 20 come from netdata guides (secondary).
  • TiKV: RocksDB + Titan for large values.

Stateless compaction service decoupled from the LSM instance; up to 8× throughput, up to 98% lower p99 vs conventional LSM-KVS (RocksDB prototype, Kvrocks and Nebula). 9. O³-LSM (Lin et al.), SIGMOD 2026 (2603.05439). Extends compaction offload to memtable and flush offload over disaggregated memory; up to 4.5× write throughput, 76% lower p99. 10. SlateDB (object-storage LSM): pluggable scheduler (only size-tiered shipped), distributed compaction via shared .compactions file, subcompactions on the roadmap; scaling numbers are the project's own claims (design, roadmap). Not a paper.

Key-value separation 11. Scavenger: Space-Time Trade-offs for KV-Separated LSM-trees (Zhang et al.), ICDE 2024; arXiv upload Aug 2025 (2508.13909). I/O-efficient GC plus space-aware compaction (compensated size); better than BlobDB, Titan, TerarkDB. Extension Scavenger+ in IEEE TC 2025 (2508.13935). Venue discrepancy resolved: late arXiv upload of an ICDE 2024 paper (IEEE Xplore record seen via search; dblp not reachable).

Survey 12. Rethinking LSM-tree based Key-Value Stores: A Survey (Lv et al.), arXiv Jul 2025, no venue (2507.09642). Five years of work on compaction, stalls, and read amplification (100+ papers per search snippet).

Adjacent, fetched but not compaction-policy: Mnemosyne (SIGMOD 2025, Bloom-filter memory tuning), dLSM (VLDB Journal 2024, disaggregated memory), LSM-OPD (2508.11862, scans on compressed data), Nezha (2603.09122, ICDE 2026, KV separation + Raft).

Pattern: compaction is becoming adaptive/learned (CAMAL, EcoTune, ArceKV, AXE), stalls are attacked structurally (DiaLSM), compaction cost by kernel and offload tricks (RESYSTANCE, CaaS-LSM, O³-LSM), and KV-separation co-designs GC with compaction (Scavenger).

Still unverified (search snippets only, not cited above): D2Comp and DFlush (DPU offload), multi-threaded compaction pipelining, GPComp/gLSM (GPU), the EDBT 2025 write-amplification benchmark paper. No ZNS-specific compaction paper found.

11b. Open problems

  • No dominant strategy. Sarkar et al., VLDB'21 decompose any compaction strategy into four primitives (trigger, data layout, granularity, data-movement policy), benchmark 10 strategies, and report 12 observations and 7 takeaways. That no strategy wins every metric is my paraphrase of their findings, not an abstract quote.
  • Granularity done wrong. Spooky (Dayan, Weiss, Dashevsky, Pan, Bortnikov, Twitto; PVLDB 15(11) 2022) argues partial-compaction granularity is often implemented incorrectly (venue/authors from search; abstract not read).
  • Tuning under workload shift. Policy changes require rewriting data, so transition cost is hard and rarely modeled. Work: Endure/K-LSM (2311.10005, Huynh, Chaudhari, Terzi, Athanassoulis; first at PVLDB 2022 (from memory)), RusKey RL tuner (2308.07013, SIGMOD 2024 (search)), and the 2024–26 papers above.
  • Scheduling theory. No clean optimal result trading tail latency vs write amp vs space; picking is heuristic. bLSM's spring-and-gear scheduler (Sears & Ramakrishnan, SIGMOD 2012) and SILK are partial answers.
  • Deletes/TTL. Bounded-latency physical deletes remain mostly research (Lethe), not default.
  • Cloud/object storage. Request pricing shifts the optimum; SlateDB only ships size-tiered; offloaded compaction (CaaS-LSM, O³-LSM) is an open design space.
  • KV separation cuts write amp but moves cost to GC and range scans.

Why hard: any change to the layout is paid for in rewritten data, workloads drift, and foreground/background I/O interact non-linearly.

12. Lineage

B-tree → O'Neil et al., LSM-tree (1996) (rolling merge, leveling) → Bigtable/LevelDB (2006–11) → bLSM (SIGMOD'12, scheduling) → Monkey (2017) (filter allocation) → Dostoevsky (2018) (lazy leveling, Fluid LSM) → WiscKey/Titan (KV separation) → SILK (2019), Lethe (2020), design-space benchmark (2021), Spooky (2022) → learned/adaptive and offloaded compaction (2024–26).

14. Question ladder

Mechanism

1. Walk a flush through leveling at T=3 until it overflows into L1: how many bytes are rewritten

Per the section-5 trace: arrivals 2, 3, 4 each rewrite the resident L0 data (1, 2, 3 units) = 6 units of resident data rewritten, plus 4 flush writes; the size-4 run (> cap 3) then moves down to L1. Resident data is re-merged each arrival, which is the (T−1)/2 factor.

2. Why does tiering write each entry about once per level while leveling writes it ≈(T−1)/2 times

Tiering merges only when T runs accumulate, then writes the result once into the next level; leveling re-merges the arriving run with the resident level data on every arrival, so resident data is rewritten on average (T−1)/2 times before overflowing.

3. What does RocksDB's L0 score formula compute and why two terms

L0 score = max(num_files/trigger, total_size/max_bytes_for_level_base): file count matters because overlapping L0 files drive read amp; size matters for byte-based backlog.

4. What does kMinOverlappingRatio choose and why does it lower write amp

Picks the file whose overlap with next-level files is smallest relative to its own size: least rewrite of the lower level per byte moved down.

5. What exactly makes a tombstone droppable

Compaction reaches the bottommost level (nothing deeper can hold older versions) and no snapshot needs it.

Why

6. Why must Bloom FPR grow geometrically with level size under Monkey

Probing any run costs one I/O regardless of size; Lagrange optimization of Σp_i under a memory constraint gives p_i ∝ entries at level i, i.e. p_i = T·p_{i−1}.

7. Why does lazy leveling use leveling only at the last level

The last level holds ~(T−1)/T of data, so it controls space amp and lookup cost; upper levels (little data) only affect update/scan costs, where tiering is cheaper.

8. Why is space amp ≈1.11 with dynamic level bytes at T=10

With dynamic level bytes the last level is sized to its actual data and each level above is 1/T of the one below, so total = last × (1 + 1/T + 1/T² + …) = last × T/(T−1) = 1.111× at T=10 (the last level ≈ 90% of all data).

9. Why do equal size ratios minimize merge I/O (O'Neil Thm 3.1)

Merge I/O per level is proportional to (1+r_i); with a fixed product of ratios (fixed total size) the sum is minimized by equalizing ratios (convexity).

Counterfactual

10. What if T→T_lim (one huge level)? What if T=2

T→T_lim: L→1, a sorted array: reads optimal, each insert rewrites everything. T=2: tiering and leveling coincide.

11. What if Bloom filters were free and perfect? Does tiering still lose

Perfect filters make zero-result lookups free for both; tiering still pays on existing-key lookups and scans (up to T runs/level) but wins on writes.

12. What if the SSD had no write-amp penalty (WAF=1)? Does the optimal policy change

WAF multiplies: policy ranking by LSM WA is unchanged, but the absolute endurance budget and cost balance (φ) shift, favoring lower-WA policies on worn/shared SSDs.

13. What if compaction ran strictly at lower priority than foreground I/O? What happens to debt

Debt accumulates, L0 files/pending bytes hit stall thresholds and writes stall hard anyway: the cliff just moves.

Adversarial

14. Craft a workload that maximizes L0 overlap and read amp

Random keys across the whole range with bursts of flushes faster than L0→L1 compaction: every L0 file spans the whole key space.

15. How would an attacker (or buggy client) trigger a write-stall cascade

Burst writes beyond sustained compaction bandwidth, or bulk load that builds pending-compaction debt past 64 GB/256 GB.

16. Construct a Cassandra delete→resurrection scenario with a missed repair

Delete row; a replica is down/unrepaired past gc_grace; healthy replicas compact the tombstone away; the down replica returns still holding the row; repair treats it as live.

17. How can long-running iterators/snapshots defeat the space-amp bound

Pinned snapshots/iterators keep obsolete SSTs alive; compaction can't drop versions they might read.

Connection

18. How does this relate to external merge sort and to garbage-collected heaps (generational GC)

Compaction is multiway merge sort run incrementally; levels with ratio T are generational GC with promotion.

19. How is SSD FTL garbage collection a nested LSM

The FTL writes log-structured pages and compacts blocks: stacked WA multiplies with the LSM's.

20. How does key-value separation reshape the policy math

Values aren't rewritten during compaction, so keys-only merges shrink W; but GC must reclaim value logs and range scans lose locality.
