Nanite-style virtualized geometry: cluster DAG, crack-free LOD, micro-triangle rasterization

TL;DR. Chop a mesh into 128-triangle clusters, build a DAG of ever-coarser clusters whose group borders are locked so neighbours always meet exactly, and let the GPU pick the cut where projected error ≈ 1 pixel. Triangle count then tracks screen pixels, not scene size. Why it matters: film-quality assets in real time with no LOD authoring, no popping, and no per-object CPU draw calls — at the price of overdraw, masked-material, animation and portability problems.

Plain English first

Explain it simply

Think of a map app. Zoomed out, a city is a grey blob; zoomed in, you see every house. The app does not keep one giant picture and shrink it. It keeps the city cut into small tiles, and for every tile it keeps cruder versions too. You only load the tiles you can see, at just the sharpness your screen can show. Nanite does this for 3D models. A statue with a million tiny triangles is chopped into patches of 128 triangles. Each patch has coarser stand-ins. Every frame the GPU asks, per patch: "if I used the coarse version, would anyone notice?" If not, it uses the coarse one. The key trick: neighbouring patches always agree on the exact points along their shared edges, so a coarse patch next to a fine patch fits like a jigsaw piece, with no gaps.

Everyday example

A game has a stone dragon statue made of about 1,000,000 triangles. Stand 2 metres away: the statue fills the screen, so you need nearly all the detail; the game draws the fine patches facing you and skips the back of the statue. Walk 200 metres away: the statue is a 30-pixel smudge, so each patch is swapped for its coarsest stand-in — a few hundred triangles in total — and nobody can tell. Walk back slowly: patches in the middle get sharper one at a time, and no seam ever opens because the borders between patches never moved.

Now the same thing, technically.

Real-world context

What it is

A rendering pipeline (Unreal Engine 5's Nanite, plus open clones) that stores each mesh as a hierarchy of triangle clusters at many detail levels, picks the right cut through that hierarchy on the GPU every frame so error stays ≲1 pixel, and rasterizes the result with a mix of hardware and compute-shader rasterization.

Why it exists

Classic LOD has three costs: tools/artists author LOD chains per asset; objects pop at switches; the CPU submits a draw call per object, capping scene complexity. Million-triangle scans and sculpts were unusable. Nanite makes triangle count scale with pixels on screen and moves culling, LOD and draw building to the GPU.

How it's used

In Unreal: tick Enable Nanite Support on a Static Mesh; global r.Nanite 0/1; streaming pool r.Nanite.Streaming.StreamingPoolSize; buffer cvars r.Nanite.MaxCandidateClusters (12 B each) and r.Nanite.MaxVisibleClusters (16 B each) verified. In your own engine, meshoptimizer does the build side (signatures from memory of the public header; check your version):

// 1. cluster a mesh into <=128-tri meshlets
size_t maxm = meshopt_buildMeshletsBound(index_count, 128, 128);
std::vector<meshopt_Meshlet> ml(maxm);
std::vector<unsigned> mv(maxm * 128);
std::vector<unsigned char> mt(maxm * 128 * 3);
size_t n = meshopt_buildMeshlets(ml.data(), mv.data(), mt.data(),
    indices, index_count, &pos[0].x, vcount, sizeof(Vec3),
    /*max_vertices*/128, /*max_triangles*/128, /*cone_weight*/0.f);

// 2. simplify a merged group with its border locked
float err = 0;
size_t out = meshopt_simplify(dst, group_idx, group_idx_count,
    &pos[0].x, vcount, sizeof(Vec3),
    group_idx_count / 2, /*target_error*/1e9f,
    meshopt_SimplifyLockBorder | meshopt_SimplifySparse, &err);
// err is relative to mesh extent; scale with meshopt_simplifyScale()

Use it / skip it

Use it
  • Opaque, mostly static, high-poly geometry (scans, sculpts, CAD, rock/architecture kits)
  • Many instances of heavy assets
  • You want zero LOD authoring and no popping
Skip it
  • Translucency; forward/mobile renderers
  • Small low-poly meshes (one blog-grade test: classic LOD wins under ~2M tris/mesh)
  • Heavily masked foliage, big WPO animation (§9)

Who should care

Engine and graphics programmers; technical artists choosing import settings; 3D-vision people building Gaussian-splat LOD, which is borrowing the same DAG idea (§11).

Technical deep dive

1 · Bare-minimum context

  • Rasterization: GPU turns triangles into pixels; shades pixels in 2×2 quads.
  • LOD: cheaper mesh versions at distance; classic = a few per object.
  • Meshlet / cluster: small fixed-size triangle batch (128 here).
  • Quadric error metric: Garland & Heckbert's edge-collapse cost (CMU).
  • Visibility buffer: store "which triangle" per pixel, shade later once.
  • HZB: mip pyramid of farthest depth, for conservative occlusion tests.

2 · The one-liner — and what it hides

"Nanite renders unlimited triangles by streaming and LOD-ing 128-triangle clusters at pixel scale." It hides:

  1. How independently simplified neighbours meet without cracks.
  2. How the GPU picks a consistent cut with no neighbour communication.
  3. Why a DAG, not a tree, and why borders alternate.
  4. Why a software rasterizer beats hardware for tiny triangles.
  5. What it costs: overdraw, masks, animation, ray tracing, streaming.

3 · The problem

  • Source asset: 1M–1B triangles. Screen: 1080p = 2.07M pixels. Needed detail ≲ 1 triangle/pixel → ≲ 2M visible triangles ≈ 16k clusters, independent of source size.
  • Discrete LOD: popping, per-asset authoring, per-object draw calls and CPU culling.
  • Hardware raster shades 2×2 quads: a one-pixel triangle still costs ≥4 lanes → ≥75% wasted.
  • Constraint: LOD decisions must be local (per cluster, parallel) yet globally watertight.

4 · Mental model

A zoomable map in tiles with pinned borders: fine and coarse tiles share the same border points, so any mix interlocks.

Where the analogy breaks. Pins make tile borders un-simplifiable: a border stays dense forever unless the next level draws its tile borders elsewhere. So the map is re-tiled at every zoom level with different cuts — that's why it's a DAG, not a tree.

5 · The mechanism, traced

Offline build (per mesh)

level 0: T triangles → graph-partition on shared edges → clusters of ≤128 tris
repeat:
  group    : merge 8–32 adjacent clusters                    [secondary: UE constants]
  lock     : edges shared with a DIFFERENT group → both vertices locked
  simplify : QEM collapse inside the group to ~50% triangles (borders untouched)
  record   : group error  = max(raw error, max child error)     # monotone
             group bounds = hull(children bounds, own bounds)   # nested
  split    : re-cluster simplified group into new ≤128-tri clusters ("parents")
  next level re-partitions the NEW clusters → old borders now interior
until one root cluster remains

Each cluster ends up with (self error, self bounds) and (parent error, parent bounds); all clusters in a group share the same pair.

Then the survivor passes frustum + HZB occlusion; big triangles go to the hardware rasterizer, tiny ones to a compute rasterizer, both writing a 64-bit value to the visibility buffer by atomic max (depth in high bits). A later pass reads (clusterID, triangleID), fetches the triangle, interpolates, shades once per pixel with materials binned by tile. GPU traversal: persistent threads pull BVH nodes from a lock-free queue; "not small enough" nodes push children back secondary.

Conflict. Visibility buffer: sources agree on 64 bits/pixel, ~30-bit depth, 7-bit in-cluster triangle ID (128 = 27), cluster ID in the rest. One says 27-bit cluster ID; another a 25-bit ID in a 32-bit word plus a 32-bit depth word. I could not confirm against the slides. conflict

6 · The math

QEM collapse cost

Plane p=(a,b,c,d), a²+b²+c²=1; point v=(x,y,z,1). Squared distance (pᵀv)² = vᵀ(ppᵀ)v. Per-vertex Q = Σ ppᵀ (4×4 symmetric). Collapsing 1,2 → v̄ costs

Δ(v̄) = v̄ᵀ (Q₁ + Q₂) v̄ , v̄ solves [q11 q12 q13 q14; q12 q22 q23 q24; q13 q23 q33 q34; 0 0 0 1] v̄ = (0,0,0,1)ᵀ

each vertex remembers "how far from my old surface planes may I drift"; adding matrices adds errors without storing planes, so a collapse is O(1) after setup.

Screen-space error

Image-plane half-height at distance d is d·tan(φ/2) world units = H/2 px, so:

proj(e,d) = e · H / ( 2 · d · tan(φ/2) ), d = max(‖cam − c‖ − r, ε)

error shrinks with distance and grows with resolution; using the nearest point of the bounding sphere makes it conservative (never optimistic).

Selection rule

draw c ⇔ proj(e_self, d_self) ≤ τ < proj(e_parent, d_parent), τ ≈ 1 px

"I'm fine enough, and my coarser parent isn't." Exactly one cluster per leaf-to-root path satisfies this.

Why monotone?

If e_parent ≥ e_self and bounds_parent ⊇ bounds_self, then d_parent ≤ d_self, so proj is non-decreasing going up any path → one τ-crossing per path; siblings share the parent's numbers → all agree. No neighbour talk.

Size accounting

Σ triangles = T(1 + ½ + ¼ + …) = 2T ; levels ≈ log₂(T/128) ; T = 10⁹ → ≈ 23

the whole DAG costs only about twice the original mesh. Epic: 14.4 B per input triangle; 1.5M-tri example 19.64 MB vs 148.95 MB for a 4-LOD static mesh verified.

7 · Why it works

  • Watertight: locked border vertices are identical at every level; a fine group beside a coarse one shares exact vertices. No stitching, no skirts.
  • Local decision: monotone error + nested bounds + group-shared numbers → per-cluster parallel choice, no sync.
  • Constant work per pixel: ≈1 triangle/pixel regardless of source size.
  • Two-pass occlusion culling secondary: pass 1 draws clusters visible last frame vs last frame's HZB; build new HZB from that depth; pass 2 re-tests what pass 1 culled against the new HZB and draws the wrongly culled. Conservative-correct, no CPU readback.
  • Software raster: one wave per cluster, 64-bit atomic write to the visibility buffer, no quad waste; reported up to ~3× hardware for pixel-sized triangles secondary.

8 · Design knobs & alternatives

  • Cluster size 128 (7-bit triangle ID, wave multiple). meshoptimizer user report: 256v/128t beat 64v/64t because rasterization cost dominated verified.
  • Group size 8–32 clusters secondary: bigger = better simplification, more streaming coupling.
  • τ ≈ 1 px: bigger = faster, shimmers more; visual stability leans on temporal AA.
  • Position precision 2P grid, ≤21 bits/axis: size vs stairstepping secondary.
  • Streaming pages 128 KB (32 KB root) secondary.
  • Alternatives: discrete LOD; view-dependent progressive meshes (not parallel per cluster); Quick-VDR clustered progressive meshes (2004); mesh shaders without a DAG; voxels/impostors for aggregates.

9 · Where it breaks

Overdraw / thin geometry. Layered or holey meshes lose few triangles to simplification and need many depth layers before occlusion bites; one article claims up to 2× worse than expected (80.lv, blog-grade).
Aggregates (leaves, grass, hair): disconnected parts do not collapse into a plane. Epic's answer in the UE 5.8 docs: Assemblies, Voxels, Skinning verified.
WPO / animation. Static cluster bounds; displaced vertices can be wrongly culled (needs max-WPO-distance); animation invalidates cached virtual-shadow-map pages. secondary
Masked materials need extra raster bins and per-pixel alpha test in the raster loop.
No translucency; deferred-only → no forward VR, no mobile out of the box. secondary
Ray tracing: clusters don't map to hardware BLAS directly; cluster acceleration structures (RTX Mega Geometry, 2025) are the hardware response verified.
Streaming: undersized pool thrashes; pop-in under fast cameras; SSD effectively required. Subpixel shimmer relies on TSR/TAA.
Misconceptions. "Free LODs": cost moves to material shading, shadows, memory. "Always faster": measured results mixed — one forum test: Nanite ~1.5 ms slower than an overdraw-optimized LOD scene; another: RTX 3090 55–58 FPS vs 47–49 secondary.

11b · Open problems

  • Aggregate LOD: no accepted coarser representation that preserves coverage, colour and shading; voxels are Epic's first production answer, still new.
  • Deforming geometry: bounds/DAG assume rigid shapes; skinned Nanite is experimental (5.5+) secondary. Hard because error bounds must hold for every pose.
  • Ray tracing: per-frame cluster BVH builds at ~1 px LOD; LOD consistency between primary and secondary rays.
  • Portability: 64-bit image atomics and persistent threads limit it to desktop-class GPUs; WebGPU/mobile ports are partial secondary.
  • Perceptual error: QEM attribute weights are heuristic.
  • Splats vs meshes: no locked borders in 3DGS; blending hides seams; principled analogue unsettled.

12 · Lineage

Progressive meshes / view-dependent simplification (Hoppe, 1996–97) → Quadric error metrics (Garland & Heckbert, SIGGRAPH 1997) → clustered hierarchy of progressive meshes, Quick-VDR (Yoon et al., 2004) secondary → meshlets + mesh shaders (~2018) → Nanite (Karis, SIGGRAPH Advances 2021) → open clones (meshoptimizer, Bevy) → GPU-driven materials (GDC 2024) → cluster ray tracing (2025) → Gaussian-splat cluster LOD (2025). Cignoni et al.'s "Batched Multi-Triangulation" (2005) is a frequently cited precursor I did not retrieve.

13 · Hands-on (≤30 min)

cluster_dag_1d.py (same folder): a 1-D polyline stands in for the mesh; clusters of 8 segments, groups of 4, group simplified to half with endpoints locked, offsets alternate by level, monotone error + nested bounds. It picks cuts for random cameras and checks the selected clusters tile the curve exactly.

$ python3 cluster_dag_1d.py

monotone err + nested bounds : tiling failures 0 / 3000
ablate monotone rules        : tiling failures 50 / 3000
cut cam=-500 tau=0.5 : 256 clusters, per level {0: 256}
cut cam=-500 tau=4   : 128 clusters, per level {0: 8, 1: 116, 2: 4}
cut cam=-500 tau=20  :  16 clusters, per level {4: 16}

Try: set off = 0 always (never move borders) and watch the root error/cluster counts; or break only the bounds hull to see which half of the ablation does the damage. Caveat: 1-D toy, error measured vertically; it shows the consistency argument, not Nanite's quality or speed.
