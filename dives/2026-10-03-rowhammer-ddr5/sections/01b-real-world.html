What it is, in one paragraph. Rowhammer is a read-disturbance phenomenon in DRAM. Repeatedly activating ("hammering") one row electrically disturbs physically adjacent rows, leaking their charge fast enough to flip bits before the next refresh. It was first shown by Kim et al. (ISCA 2014): disturbance errors appeared in 110 of 129 DDR3 modules, with as few as 139K reads to a row, in every module made in 2012–2013 (paper). It is a scaling defect. It gets worse as cells shrink, so no single vendor can fix it.

Why it exists, and why it is a problem. DRAM density doubles by shrinking cells and packing them tighter. Smaller cells hold less charge, which means a smaller noise margin. A tighter pitch means stronger capacitive and electromagnetic coupling between neighbours. So each generation needs fewer hammers to flip a bit. The defect breaks the most basic guarantee software assumes: that writing memory you don't own cannot change it. Before Rowhammer, memory integrity was taken for granted. Now it is an active, unsolved hardware-security problem.

Where it shows up in real systems:

Cloud multi-tenant serversThe canonical threat model: your VM hammers to flip a neighbour tenant's page-table entry.
BrowsersRowhammer.js triggered flips from JavaScript. No native code needed.
Android / mobileDrammer flipped bits deterministically on phones via the contiguous ION allocator.
AMD ZenZenHammer (USENIX Sec 2024) reached AMD and the first DDR5 flip.
NVIDIA GPUsGPUHammer (USENIX Sec 2025) flipped GDDR6 on an RTX A6000, dropping an ML model's accuracy from about 80% to 0.1%.
SK Hynix DDR5Phoenix (S&P 2026, CVE-2025-6202) got root on a default DDR5 desktop in minutes.

How a practitioner touches it (defensive side). You don't "call" Rowhammer. You observe it and configure around it:

# Watch corrected/uncorrected ECC errors per DIMM (rising CE = marginal cells / pressure)
sudo systemctl enable --now rasdaemon
sudo ras-mc-ctl --error-count
sudo ras-mc-ctl --summary
edac-util -v

Server BIOS exposes a refresh-rate multiplier (1×, 2×, or 4× tREFI). The 2015 industry reflex was to force 2×. Memtest86 ships a Rowhammer test (test 13). JEDEC's modern answer is firmware and controller settings for RFM and, in future, PRAC.

Care about it if

  • You run multi-tenant hardware, a browser engine, or a mobile platform
  • You serve an ML inference service on shared GPUs
  • You design DRAM or memory controllers, or you certify hardware

You can mostly ignore it if

  • It is a single-user, physically secured, non-adversarial box
  • No untrusted code runs on the same DRAM as your secrets
  • The attacker needs to run code on the same DRAM as the victim

Who should care. Cloud and infrastructure security, DRAM and memory-controller designers, browser and OS sandbox authors, ML-serving infrastructure, and hardware-security researchers.
