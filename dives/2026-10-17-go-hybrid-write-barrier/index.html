Go's hybrid write barrier: why stacks are never re-scanned

Go's collector marks while your program runs, so it must hear about pointer changes. Go 1.7 could not trust stacks (no barrier on stack writes), so it froze the world and re-scanned them: 10s to 100s of ms. The hybrid barrier shades the overwritten pointer, and the new one while a stack is unscanned, so a scanned stack stays black.

Why it matters: the stop-the-world pause stopped growing with goroutine count; the design doc's target was under 50 µs. The cost moved to a barrier on every pointer store during marking and to mark assists.

The whole idea in 8 scrolls

How Go's garbage collector stopped re-reading every stack while the world was frozen

A garbage collector has to find everything a program can still reach, and Go does it while the program runs. It tags objects white (not seen), grey (seen, contents not yet read) and black (fully read). Whatever is still white at the end is freed. Goroutine stacks count as roots.

The Go 1.5 way. Every time the program stores a pointer into the heap, a small write barrier shades the new pointer so a black object can never hold a white one. But stack writes get no barrier, because they are the most common operation in any program.

The catch (Go 1.7). A scanned stack turns black, but as soon as its goroutine runs it can pick up a white pointer, so it is grey again. The collector had to stop the world and re-scan every stack that ran. The design doc says that took 10s to 100s of milliseconds with many goroutines.

The new idea (Go 1.8). Also shade the pointer being overwritten. Now if a scanned stack loads C and the heap link to C is cut, the cut itself shades C. The stack can no longer hide anything the collector hasn't seen.

The other half. If a stack is not yet scanned, it may hold the only pointer to C, and it can store C into an already-black object. So while the current stack is grey, the new pointer gets shaded too. (Simulated: either shade alone loses C in one of the two races.)

The payoff. After a stack is scanned, everything on it was shaded and the deletion shade stops it hiding more. It stays black for the rest of the cycle. No re-scan list, no stop-the-world re-scan.

What actually ships. The runtime does not call a function per store. The compiler tests a flag, and when marking is on it writes the old and new pointer into a 512-entry per-P buffer, flushed in batches. It records both unconditionally, which the design doc says costs about twice the conditional form.

The trade. A tiny worst-case pause, paid for by a barrier that runs on every pointer store during the mark phase, and a pacer that keeps marking near 25% of CPU and bills allocating goroutines when it falls behind.

In everyday words

An inspector, a shop that stays open, and a shout-it-out rule

An inspector tags boxes while clerks keep moving them. A clerk can lift an unseen box off a shelf and clear the shelf, and the box gets binned. The fix is a rule: shout the name of any box you take off or put on a shelf.

Check each clerk's pockets once, and never again.

Imagine a warehouse that has to throw away anything nobody can reach anymore, but it can't close while it counts. So an inspector walks the aisles with tags: white means "haven't seen this box yet", grey means "seen it, haven't looked inside", black means "seen it and everything it points to". When the walk ends, every box still tagged white gets thrown out.

The trouble is that clerks keep moving boxes while the inspector works. A clerk can lift a white box off a shelf the inspector is about to skip, hold it, and clear the shelf. The inspector then finishes the walk, never sees that box, and bins it while the clerk is still carrying it. Go's garbage collector has this exact problem, and the fix is a house rule: whenever a clerk takes a box off a shelf or puts one onto a shelf, they call out its name and the inspector tags it. The clerk's own hands and pockets are too busy to police, so the inspector checks them once. The clever part of Go's rule is that after that one check, the pockets never need checking again.

Everyday example

Priya is a clerk. Shelf B holds box C. The inspector has already checked Priya's pockets (empty) and has just tagged shelf B as "to look inside". Priya takes C from shelf B into her hands, then clears the slot on the shelf. She calls out "C" as she clears the slot, so the inspector tags it. The inspector looks inside shelf B (now empty) and moves on, but C is already tagged and is kept. Without the call-out, C would still be white at the end, and the box in Priya's hands would be binned.

Before Go 1.8 the call-out rule was weaker, so the inspector had to close the shop at the end and re-check every clerk's pockets one last time. With 100,000 clerks that took long enough for customers to notice. The new rule removes the re-check.

Context
§1 · Prerequisites

Six things to know first

  • Tri-color marking: white unseen, grey queued, black scanned.
  • Strong invariant: no black object points to a white one.
  • Write barrier: code around heap pointer stores. Stack writes get none.
  • Tracing GC: an object is live if a chain of pointers leads to it from a root (goroutine stacks, globals, registers). Everything else is freed. Go GC guide.
  • Concurrent marking: the collector traces while the program (the mutator) keeps running and rewiring pointers, so the graph changes under the tracer.
  • Tri-color abstraction: white = unvisited, grey = visited but its pointers not yet scanned (on the work queue), black = visited and scanned. White objects left at the end are garbage.
  • Strong invariant: no black object points to a white object. If it holds, finishing the grey queue marks everything reachable. Design doc 17503.
  • Write barrier: a few instructions the compiler wraps around pointer stores into the heap, so the collector hears about the change. Stack writes get none, because they are far too frequent.
  • Stop-the-world (STW): every goroutine pauses. Go keeps two short STW phases per cycle (sweep termination and mark termination).
§1b · Real-world context

Every Go binary runs it; you steer it with GOGC and GOMEMLIMIT

Kubernetes, etcd, Docker, Prometheus and Terraform are all Go, so they all run this collector. You never call the barrier. You set GOGC, GOMEMLIMIT (Go 1.19) and read GODEBUG=gctrace=1.

What it is

A small piece of compiler-emitted code that runs on every heap pointer store while a GC mark phase is active. It records the old pointer being overwritten and the new pointer being written, so the concurrent collector can never miss an object that the program moves around. It is why Go's GC pauses are measured in tens to hundreds of microseconds instead of milliseconds.

Why it exists

Go 1.5 (2015) shipped a concurrent collector, and by 1.7 the one remaining unbounded pause was the stop-the-world re-scan of goroutine stacks at the end of marking, which the design doc says could take 10s to 100s of ms with many goroutines. Go makes goroutines cheap enough to run 105 or more, so the pause scaled with a number users control. The hybrid barrier (proposal #17503, Go 1.8) removed it.

Where it runs

Every Go binary carries this runtime. I did not check any of these projects' GC settings, only that they are written in Go and so run this collector:

Kubernetes, etcd
Control-plane servers where a GC pause shows up as API latency or a missed leader heartbeat.
Docker / moby, containerd
Daemon processes that hold many goroutines per container.
Prometheus
Large pointer-rich in-memory indexes, so GC CPU is a real cost.
Terraform, Hugo, CockroachDB
Go programs whose heaps grow to many GB.

How you touch it

You never call the barrier. You steer the collector that turns it on and off:

GOGC=100                  # heap goal = live + (live + roots) * GOGC/100   (default 100)
GOMEMLIMIT=3500MiB        # soft total-memory limit, Go 1.19+
GODEBUG=gctrace=1         # one line per GC cycle on stderr

// in code
debug.SetGCPercent(200)
debug.SetMemoryLimit(3500 << 20)

A real gctrace line (my machine, gcdemo.go, 14 P):

gc 1 @0.003s 2%: 0.035+0.30+0.061 ms clock, 0.49+0.14/0.34/0+0.86 ms cpu, 3->4->0 MB, 4 MB goal, 0 MB stacks, 0 MB globals, 14 P
         ^wall%   ^STW sweep-term + concurrent mark + STW mark-term     ^heap at start->end->live   ^goal

The first and last numbers in the clock triple are the two STW pauses. The middle one is the concurrent mark, and it is the phase during which the barrier is on.

When to care, when not

Tune GOGC / GOMEMLIMIT when a profile shows runtime.gcAssistAlloc, GC CPU above ~25%, or you run in a container with a hard memory limit.
Don't touch it when pauses are already sub-millisecond and memory is not tight. The barrier itself is not tunable, and the alternatives (Java ZGC, Shenandoah) are different runtimes, not flags.

Who should care

Backend and infra engineers running latency-sensitive Go services (p99), SREs sizing memory in containers, and anyone writing unsafe or cgo code that stores pointers behind the compiler's back, since that bypasses the barrier.

§2 · The one-liner

"Shade the old and new pointer" hides five questions

The sentence skips: why stacks need no barrier, why two shades, why the shipped code is not the pseudocode, why the barrier is mostly off, and why assists now cost more tail latency than the barrier.

"Go's write barrier shades the old and new pointer on every heap store during marking, so the collector can run concurrently."

What that sentence hides:

  1. Stacks have no barrier at all. So how can the collector trust a stack it scanned a millisecond ago?
  2. The two shades fix two different races. Each alone is broken, in a different place.
  3. The shipped code is not the textbook pseudocode. It buffers pointers and records both unconditionally.
  4. The barrier is off most of the time. It exists only during the mark phase, and the pacer decides when that is.
  5. The barrier is not the latency risk anymore. Mark assists, charged to whoever allocates, are.
§3 · The problem

A stop-the-world rescan was the last unbounded pause

Guess first Stack writes have no write barrier. Under Go 1.7's insertion-only barrier, what happens to a stack after the GC scans it and the goroutine runs again?

It reverts to grey. A scanned stack is black only until its goroutine runs and can pick up a white pointer, so Go 1.7 re-scanned every dirty stack in a stop-the-world step.

Go 1.7 marked concurrently but treated stacks as permanently grey, then re-scanned every dirty one with the world stopped. The design doc says 10s to 100s of ms with many goroutines, and it grew with goroutine count.

10s–100s msworst-case STW stack re-scan per GC cycle in Go 1.7, per the design doc. Hybrid barrier target: under 50 µs.

Go 1.5 (2015) made marking concurrent with a Dijkstra insertion barrier: on *slot = ptr, shade ptr. That keeps the strong invariant for the heap: no black heap object ever points to a white one.

Stacks are the catch. The compiler emits no barrier for stack writes (a local assignment is the most common operation in a program), so a stack can pick up a white pointer silently. Go 1.7 handled this by treating stacks as permanently grey: scanning a stack colors it black, but the moment its goroutine runs again it can hold a white pointer, so it is grey again. Marking therefore cannot finish until every stack touched since its scan is scanned again, with the world stopped, because a running goroutine could re-dirty it.

Go 1.7 mark terminationCost
Stacks to re-scanevery goroutine that ran since its stack was scanned
Pause length"10s to 100s of ms" with many goroutines (design doc 17503)
Scales withgoroutine count and stack depth, both set by the application

So the pause was unbounded in exactly the quantity Go encourages you to make large. Proposal 17503 (Clements and Hudson, 2016-10-21) set out to delete the re-scan. Its preliminary experiments put worst-case STW under 50 µs.

Why not put a barrier on stack writes? Because a barrier is a load, a compare and a possible call. Putting that on every local pointer assignment would tax all code, all the time, to protect a rare race. The design goal was the opposite: keep stack writes free and make the heap barrier smart enough that a scanned stack is provably safe.

§4 · Mental model

A stocktake in a shop that stays open

Boxes are objects, a clerk's hands are a stack, and shouting is the barrier. It breaks because the inspector runs on other CPUs (a race, not a conversation), shouting over-tags, and allocators also get drafted into counting.

A stocktake in an open shop. Boxes are objects, shelves are heap objects, a clerk's hands are a goroutine stack. White, grey and black are tags. Whenever a clerk takes a box off a shelf or sets one on a shelf, they shout its name and the inspector tags it. The inspector checks a clerk's hands once; after that the clerk can't hide anything.

Where it breaks.

  • The real inspector is a set of GC worker goroutines on other CPUs, so "shouting" is a memory write racing with their reads, not a conversation. That race is why the shipped barrier never checks the color of the holder (see the mechanism).
  • Shouting over-tags. A box that is thrown away a moment after being tagged still survives this cycle (floating garbage).
  • Clerks can also be forced to help count (mark assist), and the analogy has no equivalent of that tax on allocators.

§5 · The mechanism, traced

Replaying one race shows what each shade is for

Guess first A scanned (black) stack loads C from B, then B's pointer to C is set to nil. Which barrier alone saves C?

Deletion alone. The nil store looks harmless to an insertion barrier (it shades only the new value, nil), so C is lost. The deletion shade catches the overwritten C. Source: this dive's barrier_sim.py, race S1.

A simulator replays three races under five barriers. Insertion alone loses an object behind a black stack; deletion alone loses one behind a grey stack; the hybrid keeps both. The real runtime buffers 512 pointers per P and records both always.

What the compiler and runtime actually do

// compiler, for every heap pointer store  *slot = ptr
if runtime.writeBarrier.enabled {          // CMPL runtime.writeBarrier, $0
    buf := gcWriteBarrier2()               // reserves 2 slots (16 B) in this P's wbBuf
    buf[0] = ptr                           // new value  (Dijkstra half)
    buf[1] = *slot                         // old value  (Yuasa half)
}
*slot = ptr

// runtime (mwbbuf.go): per-P buffer, wbBufEntries = 512 pointers = 4 KiB
// fast path = bump a pointer; when full -> wbBufFlush() on the system stack:
//   for each entry: drop nil / tiny values, mark the object, push to the GC work queue

Three differences from the textbook pseudocode, all visible in mbarrier.go and mwbbuf.go:

  1. Buffered, not immediate. shade does not mark on the spot. Pointers go into a 512-entry per-P buffer and are marked in batches. Entry points gcWriteBarrier1/2/3 reserve 8, 16 or 24 bytes; up to 8 pointers per call (wbMaxEntriesPerCall).
  2. Unconditional. The comment keeps the conditional pseudocode (if current stack is grey: shade(ptr)) as the proof, but the code path records both pointers every time. The comment gives the reason for not even conditioning on the holder's color: a mutator store followed by a mark-bit load can reorder against the GC's mark-bit store and slot load, and avoiding that needs an expensive memory barrier. So it always greys the pointer. Design doc 17503 lists this "unconditional" shape as a safe, easier-to-reason-about variant that costs about twice as much for most of the mark phase.
  3. Buffers drain before termination. gcMarkDone runs a "ragged barrier" with forEachP, flushing every P's buffer and work cache before it may declare marking done.

Stacks, scanned once

markroot(i):
    gp := stack of goroutine i
    suspendG(gp)                 // or park self in _Gwaiting (waitReasonGarbageCollectionScan)
    scanstack(gp)                // shade every pointer found, set gp.gcscandone
    // never scanned again this cycle: no rescan list, no STW rescan

newobject during mark:  gcmarknewobject()   // allocate black

Allocate-black is a precondition the design doc names. Go already allocated black, so the hybrid barrier changed nothing there. Whether a goroutine's stack created mid-cycle is born black is something I did not verify (it lives in proc.go, which I did not read).

§6 · The math

Two conditions to lose an object, and pacing as arithmetic

Guess first Live heap after the last cycle is 100 MB, stacks 2 MB, globals 1 MB, GOGC = 100. What is the heap goal?

150 MB
100 MB400 MB

203 MB = 100 + (100 + 2 + 1) × 100/100. Roots count toward the goal since Go 1.18, per the GC guide and mgcpacer.go.

An object is lost only if a black object gains a pointer to it and every grey path to it is cut. Each shade breaks one condition. The pacer sets a heap goal from live heap, roots and GOGC, and assists bill allocation by scan work remaining.

1 · When is an object lost?

An object x is freed wrongly only if two things both happen during marking:

(1) the mutator stores a pointer to white x into a black object
(2) every path from a grey object to x through white objects is destroyed before the GC follows it→ in plain terms: a black object will never be looked at again, so a pointer hidden there is invisible, and removing the last "grey-protected" path means nobody else will find it either.

That is the classic two-condition result for concurrent tracing. A barrier only has to break one condition:

  • Dijkstra insertion shade(ptr) breaks (1): a black object never gains a white pointer. This is the strong invariant.
  • Yuasa deletion shade(*slot) breaks (2): whatever was reachable when marking began stays reachable-or-shaded (snapshot-at-the-beginning).

2 · The weak invariant the hybrid actually keeps

every white object pointed to by a black object is reachable from some grey object through a chain of white objects→ in plain terms: a black object may point at a white one, but only if a grey object still has a path to that white one. The collector will find it when it gets to the grey object.

The design doc is explicit that the hybrid barrier does not keep the strong invariant: a black goroutine may store a white pointer into a black heap object without shading it. What it keeps is this weaker, "grey-protected" form, which is enough because Yuasa shading protects the chain.

3 · Why the insertion half may stop once the stack is black

Right after scanstack, the stack points only to objects the scan shaded. For a scanned stack to hide an object y in a black heap object it must first hold a pointer to y that the GC has not seen. It can only acquire one by (a) loading it from the heap, which needs the heap slot to be overwritten later or y to be grey-protected, and Yuasa covers the overwrite; or (b) allocating it, which is black. So shade(ptr) adds nothing for a black stack. For a grey stack it is required (race S2).

4 · The pacer's arithmetic

The barrier only runs while the collector is marking, and the pacer decides when that starts. From mgcpacer.go:

heapGoal = heapMarked + (heapMarked + lastStackScan + globalsScan) × GOGC / 100→ in plain terms: after a cycle, let the heap grow by GOGC percent of (live heap + roots) before the next one finishes. Since Go 1.18 stacks and globals count, so a program with a huge number of goroutines gets a bigger goal.

Worked example: heapMarked = 100 MB, stacks 2 MB, globals 1 MB, GOGC = 100: goal = 100 + (100 + 2 + 1) × 1 = 203 MB. The goal is clamped to at least a minimum heap of 4 MiB × GOGC/100.

trigger = clamp(goal − runway, minTrigger, maxTrigger)
minTrigger ≥ heapMarked + (goal − heapMarked) × 45/64    maxTrigger ≈ heapMarked + (goal − heapMarked) × 61/64→ in plain terms: start marking early enough that the expected work finishes by the goal, but never earlier than ~70% or later than ~95% of the way from live heap to goal (for small heaps). The earlier it starts, the longer the barrier is on.

With the example above, the trigger lies between about 100 + 103 × 0.70 ≈ 172 MB and 100 + 103 × 0.95 ≈ 198 MB. runway is the pacer's estimate of how much the program allocates during the mark.

5 · Mark assist

assistWorkPerByte = scanWorkRemaining / (heapGoal − heapLive)→ in plain terms: if marking has 40 MB of scanning left and only 20 MB of room before the goal, each byte you allocate must be paid for with 2 bytes of scanning.

An allocating goroutine's debt gcAssistBytes goes negative as it allocates; it must do assistWorkPerByte × debt scan work, but never less than gcOverAssistWork = 64 KiB per assist, so it builds credit instead of assisting on every allocation. Background workers target gcBackgroundUtilization = 25% of CPU; assists cover whatever gap remains. On GOMAXPROCS = 8 that is exactly 2 dedicated mark workers.

The ratio is published with separate atomic stores, so a reader can briefly see a skewed pair (a source comment says so).

§7 · Why it works

A scanned stack is shaded once and then cannot hide anything

After a stack scan, everything on it is shaded, and the deletion shade blocks anything new from being smuggled in. Remove either shade and a race loses an object; remove "scan once" and the stop-the-world rescan returns.

Core insight: a stack only needs a barrier-protected hand-off at the moment it is scanned. After that, the deletion shade keeps it from smuggling anything out of the heap, and everything already on it was shaded by the scan. So a scanned stack is permanently safe for the rest of the cycle and the re-scan list disappears.

Ablation: remove each piece and see what breaks (rows are the simulator's results):

RemoveWhat breaks

The price is a barrier that is more conservative than the minimum: because it records both pointers regardless of colors, it marks objects that a precise barrier would skip, and some of them die during the cycle anyway (floating garbage, reclaimed next cycle).

§8 · Design knobs & alternatives

GOGC and GOMEMLIMIT move the trade; the barrier stays fixed

Doubling GOGC roughly doubles heap overhead and halves GC CPU. GOMEMLIMIT caps GC near 50% CPU to avoid thrash. Other runtimes pay on loads (ZGC) or add SATB (Shenandoah, G1) because they move objects.

§9 · Where it breaks

Real bugs, assist stalls and the unsafe escape hatch

Guess first Is the write barrier's work done on every pointer store into the heap, in every Go program, all the time?

Only during marking. The compiler emits a cheap flag test (runtime.writeBarrier) before the call; the buffered work runs only when the flag is set.

Barrier-correctness bugs were rare and are fixed (wasm #30873, #22987). Today's pain is mark assist tail latency, floating garbage, and corruption from cgo or unsafe that bypasses the compiler's barrier.

Real bugs (all historical; no open barrier-correctness bug surfaced in my search)

  • Wasm deletion barrier greyed the wrong object (#30873, #30872; fixed 2019, backported to 1.11/1.12): a reachable object could go unmarked. Lost-object bug in the exact class this dive is about.
  • Preemption inside barrier code (#22987, fixed 2017): a preemption inside heapBits.bits could lose a pointer and overflow the per-P buffer. Fixed with go:nosplit.
  • Crashes in gcWriteBarrier/wbBufFlush (#14149, #15293, #42249): maintainers attributed them to heap corruption from cgo or unsafe; the barrier is where a bad pointer first gets dereferenced.

Costs

  • Mark assist latency is the main user complaint now. No assist credit exists at cycle start, so allocating goroutines pay early. Field reports include hundreds of ms stalls with 1–2 ms STW pauses (#16293) and one anecdotal ~10× latency during GC in runtime.gcAssistAlloc (a mailing-list thread). Pacer meta-issue: #42430.
  • Barrier overhead (#22460): usually small because the barrier is off, but a few percent in some programs such as the compiler. A buffered fast path was about 4× faster on amd64 for the single-pointer case, about 2% on GC-heavy apps. #20005 (open) is about the code size of the enabled-flag check.
  • Floating garbage: over-shading keeps some dying objects for one more cycle.
  • Stack scanning still costs CPU, just not pause time. It also feeds the pacer (lastStackScan).
Misconceptions. (1) "Stacks are rescanned at the end." Not since the hybrid barrier. (2) "The write barrier is always on." It is checked on every heap store but only executes during marking. (3) "GC latency means STW pauses." STW is now tens of µs; assists charged to allocating goroutines are the larger tail.
unsafe / cgo. A pointer written through unsafe arithmetic or from C bypasses the compiler's barrier. If marking is running, the object it points to can be freed. Use GODEBUG=cgocheck and the race/asan builds.
§10 · In the wild

The runtime buffers, records both, and allocates black

Shipped code differs from the pseudocode: a 512-entry per-P buffer, unconditional recording justified by memory ordering, a two-register fast path, checkmark mode, and allocate-black. Non-moving runtimes need only a marking barrier.

Where the shipped runtime departs from the paper-and-pseudocode version:

  • Buffered shading. 512-entry per-P wbBuf; next and end are uintptr so updating them needs no barrier of its own.
  • Unconditional recording of old and new pointers, justified by memory-ordering cost (see mbarrier.go).
  • Fast path saves two registers. gcWriteBarrier1/2/3 set a reserve size and jump to one shared body that only saves R12 and R13 on amd64; the slow path (flush) saves every general register.
  • Checkmark mode. A debug mode re-marks the heap and shades every buffer entry to verify nothing was missed.
  • Stack scan as a root job. markroot → suspendG → scanstack (self-scans move the goroutine to _Gwaiting), with gcscandone making it once-per-cycle.
  • Allocate-black via gcmarknewobject during _GCmark and _GCmarktermination.

§11 · Frontier

The barrier is settled; the work moved to locality and pacing

Guess first Green Tea GC became the default in Go 1.26. What part of the collector does it change?

Marking and scanning. The Go 1.26 notes say it improves marking and scanning of small objects through locality and CPU scalability; Google expects 10–40% less GC CPU. The write barrier design is unchanged by it, as far as I found.

I found no new Go write-barrier paper in 2024–26. Green Tea GC became the default in Go 1.26 (10–40% less GC CPU expected), after a Go 1.25 experiment. Java's G1 reworked its own barriers in 2025.

Plain statement: the barrier design is settled. It has been the same hybrid shape since Go 1.8 (2017), and I found no 2024–2026 paper proposing a new Go write barrier (four extended searches, several dead ends). The active work moved to how the marking is ordered and how the pacer reasons, plus neighboring runtimes' barriers.

§11b · Open problems

Assist latency and the 25% budget are still unsettled

Every fix for assist tail latency trades CPU, memory or allocation latency for another. How the fixed 25% worker budget behaves with a million goroutines is unresearched, and Green Tea's effect on barrier cost is unreported.

  • Assist tail latency. Assists tax whoever allocates when marking falls behind, and no credit exists at cycle start. Fixing it means starting marking earlier (more CPU, more time with the barrier on) or slowing allocation (latency) or growing the heap (memory). The obvious fix just moves the cost. I found no recent Go-team statement; "open" here is inferred from the long-running issues (#16293, #42430).
  • The 25% worker budget at huge goroutine counts. How the fixed CPU share interacts with 106 goroutines' stack-scan work: I found no discussion. Treat as unresearched.
  • Barrier code size and check cost. #20005 (open): the enabled-flag test uses an absolute address and accounts for a large share of barrier instructions; per-G shadows were proposed. Whether it shipped is unconfirmed.
  • Does Green Tea change barrier cost? The sources I found do not say.
  • Generational or compacting Go. Go stays non-moving and non-generational; whether that stays optimal for pointer-heavy heaps is contested. I did not research the current proposals, so no position is attributed here.

Why it stays hard: every lever (start earlier, assist harder, grow the heap, buffer more) trades latency, CPU or memory against another one, and the workload decides which hurts.

§12 · Lineage

1978 insertion, 1990 deletion, 2017 hybrid

Dijkstra's insertion barrier (1978) and Yuasa's deletion barrier (1990) meet in Go 1.8 (2017), echoing the double barrier in IBM's Metronome. Then a buffered barrier, a pacer rewrite, GOMEMLIMIT, and Green Tea.

  1. 1978 · Dijkstra et al., on-the-fly GC: insertion barrier, tri-color invariant. (title and venue from memory, not fetched)
  2. 1990 · Yuasa, real-time GC: deletion barrier, snapshot-at-the-beginning. (same caveat)
  3. 2007 · Metronome (IBM real-time Java): a "double write barrier" the design doc equates to Go's hybrid.
  4. 2015 · Go 1.5: concurrent tri-color collector, Hudson's post.
  5. 2016–17 · Go 1.7 coarsened Dijkstra + permagrey stacks → proposal 17503 → hybrid barrier in Go 1.8.
  6. Later · Buffered barrier (#22460), pacer redesign (#44167), GOMEMLIMIT (1.19, 2022).
  7. 2025–26 · Green Tea: page-oriented marking, default in Go 1.26.
§13 · Hands-on

Break the barrier in a simulator, then count goroutines

Run barrier_sim.py and delete a shade to watch an object get lost. Run gcdemo.go with 1,000 to 500,000 goroutines: on my machine the worst STW pause stayed near 100 µs.

Experiment 1 · Replay the races (2 min)

python3 barrier_sim.py

Prints the barrier × race table and the S1 trace. Then break it: in heap_store, delete the line self.shade(old, "deletion") from the hybrid branch and rerun. S1 starts losing C. Add a fourth scenario where a new object is allocated white during marking and stored into a black object: you will need allocate-black to make it pass.

Experiment 2 · Watch STW stay flat as goroutines grow (5 min)

go run gcdemo.go -g 1000
go run gcdemo.go -g 100000
go run gcdemo.go -g 500000
GODEBUG=gctrace=1 go run gcdemo.go -g 100000 2>&1 | grep '^gc ' | head

goroutines=100000 GCs=9 max STW pause=133us total STW=0.4ms
goroutines=500000 GCs=9 max STW pause=104us total STW=0.4ms

The worst pause stays around 100 µs from 1,000 to 500,000 goroutines. That is the headline of the design doc, observed. Caveat: the goroutines are idle and the heap is small, so this shows the absence of a goroutine-count-scaling STW, not that your service is pause-free. §14 · Question ladder

Test yourself

20 questions from mechanism to open research. Reveal, then mark ✓ or ✗; marks feed your progress ring.

Answer in your head first, then reveal and mark yourself honestly. Marks are saved in this browser and feed the progress ring.

Mechanism
1. In race S1 (black stack, nil store), what does the barrier do on B.f = nil, step by step?

The compiler tests runtime.writeBarrier; enabled, it reserves slots in the P's buffer and records the old value (C) and new value (nil). Nil is dropped at flush; C is marked grey and queued. C survives even though the heap no longer reaches it.

→ related card
2. When is a goroutine's stack scanned, and what happens to it afterwards?

As a root job (markroot): the goroutine is suspended (or parks itself in _Gwaiting), scanstack shades every pointer found and sets gcscandone. It is not scanned again this cycle.

→ related card
3. What does gcMarkDone do with the write-barrier buffers, and why?

It runs a ragged barrier with forEachP, flushing each P's buffer and work cache. Pointers still in a buffer are unmarked, so termination before flushing could miss reachable objects.

→ related card
4. How does a mark assist decide how much to scan?

assistWorkPerByte = scanWorkRemaining / (heapGoal − heapLive). The goroutine's negative gcAssistBytes debt is multiplied by it, with a floor of 64 KiB of scan work per assist so it builds credit.

→ related card
Why
5. Why shade the old pointer instead of only the new one?

A black stack can load a white pointer from the heap and then unlink it. An insertion barrier ignores the overwrite. Shading the old value keeps it reachable-or-shaded (race S1).

→ related card
6. Why is the insertion shade only needed while the stack is grey?

A freshly scanned stack points only to shaded objects, and the deletion shade stops it hiding others. A grey stack may hold the only pointer to an object and store it into a black object (race S2).

→ related card
7. Why not put a barrier on stack writes instead?

Stack pointer writes are the most frequent operation in a program. A barrier there would tax all code to protect a rare race; the design keeps stack writes free and makes the heap barrier sufficient.

→ related card
8. Why does the shipped barrier record both pointers regardless of the holder's color?

Checking the holder's mark bit races with the GC's own mark-bit store; on x86 the result can be r1==r2==0 without an expensive memory barrier. Always greying the pointer avoids the barrier (mbarrier.go comment).

→ related card
Counterfactual
9. What if Go allocated white during marking?

A new object could be stored into a black object and never be seen. The hybrid barrier requires allocate-black (design doc), which Go already did via gcmarknewobject.

→ related card
10. What if the pacer started marking at 99% of the goal instead of ~70–95%?

The barrier would be on for less time but there is little runway: scan work must finish before the goal, so assist ratios spike and allocating goroutines pay latency, or the heap overshoots.

→ related card
11. What if GOGC were 200 on a service with 1 GB live heap?

The goal is roughly 3× live instead of 2×, so cycles are about half as frequent, GC CPU roughly halves, and peak heap overhead roughly doubles (GC guide).

→ related card
12. What changes if you remove the 25% background-worker target?

Marking would be paced only by assists, so allocating goroutines would do all the work when behind, concentrating latency in the application's own request path.

→ related card
Adversarial
13. How could you cause a use-after-free in Go despite the barrier?

Store a pointer through unsafe arithmetic or from C during marking: the compiler emitted no barrier, so the object can stay white and be freed. Checks: GODEBUG=cgocheck, race and asan builds.

→ related card
14. How would you make a service suffer mark-assist latency on purpose?

Allocate heavily while marking runs and the pacer is behind: assists bill each allocation. A sharp change in live heap size is a known trigger (pacer issues #42430, #44167).

→ related card
15. What would a bug that greyed the wrong object cause?

A reachable object left white and freed: memory corruption. It happened in the wasm deletion barrier (#30872/#30873, fixed 2019).

→ related card
Connection
16. How is this like OS copy-on-write or page-table dirty bits?

All three track mutation lazily: a barrier or fault records "this changed" so a background process can catch up later. The stack scan once-and-done mirrors scanning a snapshot.

→ related card
17. Why do ZGC and Shenandoah need load-side barriers while Go does not?

They move live objects concurrently, so a loaded pointer might be stale. Go never moves heap objects, so it only needs to guard marking.

→ related card
18. How does Green Tea relate to the barrier?

It changes the order and granularity of marking (by page, for locality), not the invariant. The barrier still guards correctness; I found no report of how Green Tea changes barrier cost.

→ related card
Open
19. Can assist tail latency be eliminated without more CPU or memory?

Not by a known method: starting earlier costs barrier-on time and CPU, assisting harder moves latency into the request path, a bigger heap costs memory. The trade is workload dependent.

→ related card
20. Would a generational Go collector pay for the barrier it would need?

Contested and not researched here: a generational collector needs a remembered-set barrier on top of the marking barrier. Whether pointer-heavy Go heaps repay that cost is unsettled in my sources.

→ related card
