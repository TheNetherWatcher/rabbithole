A garbage collector has to find everything a program can still reach, and Go does it while the program runs. It tags objects white (not seen), grey (seen, contents not yet read) and black (fully read). Whatever is still white at the end is freed. Goroutine stacks count as roots.

The Go 1.5 way. Every time the program stores a pointer into the heap, a small write barrier shades the new pointer so a black object can never hold a white one. But stack writes get no barrier, because they are the most common operation in any program.

The catch (Go 1.7). A scanned stack turns black, but as soon as its goroutine runs it can pick up a white pointer, so it is grey again. The collector had to stop the world and re-scan every stack that ran. The design doc says that took 10s to 100s of milliseconds with many goroutines.

The new idea (Go 1.8). Also shade the pointer being overwritten. Now if a scanned stack loads C and the heap link to C is cut, the cut itself shades C. The stack can no longer hide anything the collector hasn't seen.

The other half. If a stack is not yet scanned, it may hold the only pointer to C, and it can store C into an already-black object. So while the current stack is grey, the new pointer gets shaded too. (Simulated: either shade alone loses C in one of the two races.)

The payoff. After a stack is scanned, everything on it was shaded and the deletion shade stops it hiding more. It stays black for the rest of the cycle. No re-scan list, no stop-the-world re-scan.

What actually ships. The runtime does not call a function per store. The compiler tests a flag, and when marking is on it writes the old and new pointer into a 512-entry per-P buffer, flushed in batches. It records both unconditionally, which the design doc says costs about twice the conditional form.

The trade. A tiny worst-case pause, paid for by a barrier that runs on every pointer store during the mark phase, and a pacer that keeps marking near 25% of CPU and bills allocating goroutines when it falls behind.
