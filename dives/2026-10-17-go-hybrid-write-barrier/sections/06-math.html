1 · When is an object lost?

An object x is freed wrongly only if two things both happen during marking:

(1) the mutator stores a pointer to white x into a black object
(2) every path from a grey object to x through white objects is destroyed before the GC follows it→ in plain terms: a black object will never be looked at again, so a pointer hidden there is invisible, and removing the last "grey-protected" path means nobody else will find it either.

That is the classic two-condition result for concurrent tracing. A barrier only has to break one condition:

  • Dijkstra insertion shade(ptr) breaks (1): a black object never gains a white pointer. This is the strong invariant.
  • Yuasa deletion shade(*slot) breaks (2): whatever was reachable when marking began stays reachable-or-shaded (snapshot-at-the-beginning).

2 · The weak invariant the hybrid actually keeps

every white object pointed to by a black object is reachable from some grey object through a chain of white objects→ in plain terms: a black object may point at a white one, but only if a grey object still has a path to that white one. The collector will find it when it gets to the grey object.

The design doc is explicit that the hybrid barrier does not keep the strong invariant: a black goroutine may store a white pointer into a black heap object without shading it. What it keeps is this weaker, "grey-protected" form, which is enough because Yuasa shading protects the chain.

3 · Why the insertion half may stop once the stack is black

Right after scanstack, the stack points only to objects the scan shaded. For a scanned stack to hide an object y in a black heap object it must first hold a pointer to y that the GC has not seen. It can only acquire one by (a) loading it from the heap, which needs the heap slot to be overwritten later or y to be grey-protected, and Yuasa covers the overwrite; or (b) allocating it, which is black. So shade(ptr) adds nothing for a black stack. For a grey stack it is required (race S2).

4 · The pacer's arithmetic

The barrier only runs while the collector is marking, and the pacer decides when that starts. From mgcpacer.go:

heapGoal = heapMarked + (heapMarked + lastStackScan + globalsScan) × GOGC / 100→ in plain terms: after a cycle, let the heap grow by GOGC percent of (live heap + roots) before the next one finishes. Since Go 1.18 stacks and globals count, so a program with a huge number of goroutines gets a bigger goal.

Worked example: heapMarked = 100 MB, stacks 2 MB, globals 1 MB, GOGC = 100: goal = 100 + (100 + 2 + 1) × 1 = 203 MB. The goal is clamped to at least a minimum heap of 4 MiB × GOGC/100.

trigger = clamp(goal − runway, minTrigger, maxTrigger)
minTrigger ≥ heapMarked + (goal − heapMarked) × 45/64    maxTrigger ≈ heapMarked + (goal − heapMarked) × 61/64→ in plain terms: start marking early enough that the expected work finishes by the goal, but never earlier than ~70% or later than ~95% of the way from live heap to goal (for small heaps). The earlier it starts, the longer the barrier is on.

With the example above, the trigger lies between about 100 + 103 × 0.70 ≈ 172 MB and 100 + 103 × 0.95 ≈ 198 MB. runway is the pacer's estimate of how much the program allocates during the mark.

5 · Mark assist

assistWorkPerByte = scanWorkRemaining / (heapGoal − heapLive)→ in plain terms: if marking has 40 MB of scanning left and only 20 MB of room before the goal, each byte you allocate must be paid for with 2 bytes of scanning.

An allocating goroutine's debt gcAssistBytes goes negative as it allocates; it must do assistWorkPerByte × debt scan work, but never less than gcOverAssistWork = 64 KiB per assist, so it builds credit instead of assisting on every allocation. Background workers target gcBackgroundUtilization = 25% of CPU; assists cover whatever gap remains. On GOMAXPROCS = 8 that is exactly 2 dedicated mark workers.

The ratio is published with separate atomic stores, so a reader can briefly see a skewed pair (a source comment says so).
