The simulator in this folder (barrier_sim.py) replays one hand-scheduled race. Below is scenario S1: a goroutine's stack is already scanned and empty; it loads C out of B, then unlinks it from the heap. Toggle the deletion shade off to see the bug.

Read the table as the whole design. Insertion alone fails S1 (a black stack hides things), which is exactly why Go 1.7 needed to rescan stacks. Deletion alone fails S2 (a grey stack is not a consistent snapshot). The hybrid passes both.

What the compiler and runtime actually do

// compiler, for every heap pointer store  *slot = ptr
if runtime.writeBarrier.enabled {          // CMPL runtime.writeBarrier, $0
    buf := gcWriteBarrier2()               // reserves 2 slots (16 B) in this P's wbBuf
    buf[0] = ptr                           // new value  (Dijkstra half)
    buf[1] = *slot                         // old value  (Yuasa half)
}
*slot = ptr

// runtime (mwbbuf.go): per-P buffer, wbBufEntries = 512 pointers = 4 KiB
// fast path = bump a pointer; when full -> wbBufFlush() on the system stack:
//   for each entry: drop nil / tiny values, mark the object, push to the GC work queue

Three differences from the textbook pseudocode, all visible in mbarrier.go and mwbbuf.go:

  1. Buffered, not immediate. shade does not mark on the spot. Pointers go into a 512-entry per-P buffer and are marked in batches. Entry points gcWriteBarrier1/2/3 reserve 8, 16 or 24 bytes; up to 8 pointers per call (wbMaxEntriesPerCall).
  2. Unconditional. The comment keeps the conditional pseudocode (if current stack is grey: shade(ptr)) as the proof, but the code path records both pointers every time. The comment gives the reason for not even conditioning on the holder's color: a mutator store followed by a mark-bit load can reorder against the GC's mark-bit store and slot load, and avoiding that needs an expensive memory barrier. So it always greys the pointer. Design doc 17503 lists this "unconditional" shape as a safe, easier-to-reason-about variant that costs about twice as much for most of the mark phase.
  3. Buffers drain before termination. gcMarkDone runs a "ragged barrier" with forEachP, flushing every P's buffer and work cache before it may declare marking done.

Stacks, scanned once

markroot(i):
    gp := stack of goroutine i
    suspendG(gp)                 // or park self in _Gwaiting (waitReasonGarbageCollectionScan)
    scanstack(gp)                // shade every pointer found, set gp.gcscandone
    // never scanned again this cycle: no rescan list, no STW rescan

newobject during mark:  gcmarknewobject()   // allocate black

Allocate-black is a precondition the design doc names. Go already allocated black, so the hybrid barrier changed nothing there. Whether a goroutine's stack created mid-cycle is born black is something I did not verify (it lives in proc.go, which I did not read).
