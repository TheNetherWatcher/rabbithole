Core insight: a stack only needs a barrier-protected hand-off at the moment it is scanned. After that, the deletion shade keeps it from smuggling anything out of the heap, and everything already on it was shaded by the scan. So a scanned stack is permanently safe for the rest of the cycle and the re-scan list disappears.

Ablation: remove each piece and see what breaks (rows are the simulator's results):

RemoveWhat breaks
shade(*slot) (deletion)S1: a black stack loads C and unlinks it; C is freed while held. Go 1.7 papered over this by rescanning stacks in STW.
shade(ptr) while the stack is greyS2: a grey stack stores its only pointer into a black object and drops it; the object is lost.
"scan the stack once"Back to Go 1.7: STW rescan of every goroutine that ran, 10s–100s of ms.
Allocate-black during markA fresh object would be white and could be stored into a black object unseen. Design doc lists allocate-black as a requirement; Go already did it (gcmarknewobject).
Draining wbBuf before terminationPointers sitting in a buffer are not yet marked, so mark termination could finish with work still hidden in a per-P buffer. gcMarkDone flushes with forEachP first.

The price is a barrier that is more conservative than the minimum: because it records both pointers regardless of colors, it marks objects that a precise barrier would skip, and some of them die during the cycle anyway (floating garbage, reclaimed next cycle).
