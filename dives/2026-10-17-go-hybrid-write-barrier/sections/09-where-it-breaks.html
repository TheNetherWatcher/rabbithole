Real bugs (all historical; no open barrier-correctness bug surfaced in my search)

  • Wasm deletion barrier greyed the wrong object (#30873, #30872; fixed 2019, backported to 1.11/1.12): a reachable object could go unmarked. Lost-object bug in the exact class this dive is about.
  • Preemption inside barrier code (#22987, fixed 2017): a preemption inside heapBits.bits could lose a pointer and overflow the per-P buffer. Fixed with go:nosplit.
  • Crashes in gcWriteBarrier/wbBufFlush (#14149, #15293, #42249): maintainers attributed them to heap corruption from cgo or unsafe; the barrier is where a bad pointer first gets dereferenced.

Costs

  • Mark assist latency is the main user complaint now. No assist credit exists at cycle start, so allocating goroutines pay early. Field reports include hundreds of ms stalls with 1–2 ms STW pauses (#16293) and one anecdotal ~10× latency during GC in runtime.gcAssistAlloc (a mailing-list thread). Pacer meta-issue: #42430.
  • Barrier overhead (#22460): usually small because the barrier is off, but a few percent in some programs such as the compiler. A buffered fast path was about 4× faster on amd64 for the single-pointer case, about 2% on GC-heavy apps. #20005 (open) is about the code size of the enabled-flag check.
  • Floating garbage: over-shading keeps some dying objects for one more cycle.
  • Stack scanning still costs CPU, just not pause time. It also feeds the pacer (lastStackScan).
Misconceptions. (1) "Stacks are rescanned at the end." Not since the hybrid barrier. (2) "The write barrier is always on." It is checked on every heap store but only executes during marking. (3) "GC latency means STW pauses." STW is now tens of µs; assists charged to allocating goroutines are the larger tail.
unsafe / cgo. A pointer written through unsafe arithmetic or from C bypasses the compiler's barrier. If marking is running, the object it points to can be freed. Use GODEBUG=cgocheck and the race/asan builds.
