Start with o.x, a property read in JavaScript. V8 gives each object a hidden class, called a Map, that records its layout. Two objects built the same way share one Map, M2: x first, then y.

The naive way. Without a shape tag, every read searches the object's keys. That is several dependent loads, tens of nanoseconds per access, for every object. A JavaScript program does billions of these.

The key idea. Each place in the code that reads o.x keeps one slot, its inline cache. The slot remembers the last Map it saw. It starts empty, marked UNINITIALIZED.

First call. The slot is empty, so the read misses. The runtime looks up x in M2 once, finds it at offset +12, and stores (M2, +12) in the slot. The slot is now monomorphic: one Map, one answer.

Next call hits. The object's Map is M2 again, so the read is one compare and one load at +12. No search. This is the path that makes property access cheap.

Hot code bets. Once the function is hot, the optimizing compiler reads the slot and emits a CheckMaps against M2 plus one load. It also records that the code depends on M2 staying stable. The check guards the bet; it does not prove it.

The bet loses. An object with Map M3, built as {y, x}, fails the check. The engine deopts back to the interpreter, and the slot goes polymorphic, holding both M2 and M3. The deopt path is what makes the aggressive guard safe.

The trade-off. Each extra Map costs one more check, so the read gets slower as shapes pile up. Past 4 Maps the site turns megamorphic and uses a global stub cache. The state only moves forward; a site never goes back to monomorphic.

The numbers. One read site, one run. A monomorphic read takes 0.99 ns and four shapes take 4.06 ns, about 4× more. The cards below take each piece in turn.
