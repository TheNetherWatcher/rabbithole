V8 hidden classes (Maps) and inline caches: shapes, speculation, deopt

V8 gives every object a hidden class (a Map) that records its layout, and every property read site an inline cache that remembers the last Map it saw. When the Map matches, a read is one compare and one load. Optimized code bets that the Map stays the same, checks it with one compare, and deoptimizes back to the interpreter when the bet loses.

Why it matters: property access is the most common operation in JavaScript, and the same guards that make it fast have been the source of serious browser exploits (CVE-2020-6418, CVE-2020-16009, CVE-2025-2135).

4-seat tables
In everyday words

Objects carry a shape tag, and each read remembers it

JavaScript objects can gain and lose fields at any time, so a naive engine searches for x on every read. V8 tags each object with its layout (its hidden class, or Map) and each read site keeps a sticky note of the last tag it saw.

When the tag matches, the read is one fixed-offset load.

Explain it simply. JavaScript lets you make an object like {x: 1, y: 2} and add or remove fields whenever you like. That freedom is a problem for speed: to read p.x, a naive engine must search the object for a field called "x" every single time, like flipping through a stack of papers looking for the one labelled "x".

V8 (the engine in Chrome and Node.js) cheats with two tricks. First, every object carries a small tag that says "I'm laid out like this" (the hidden class, V8 calls it a Map). All objects built the same way share one tag. Second, each place in your code that reads p.x keeps a sticky note (the inline cache): "last time, objects with tag #7 had x in the first slot." Next time, the engine glances at the object's tag; if it says #7, it grabs the first slot without searching. If the tag is different, it falls back to searching and updates its note. The faster tiers of the engine go further: they bet the note will stay true, compile code that assumes it, and bail out to slow code if the bet loses.

Everyday example

A waiter in a restaurant gets order slips. Slips from the tablet app are all printed in the same layout: table number in the top-left. After a few of them the waiter stops reading the header and just looks top-left. One day a handwritten slip shows up with the table number elsewhere. The waiter notices the layout is different (tag mismatch), stops, reads the slip properly, and mentally files "layouts A and B exist". If slips arrive in dozens of random layouts, the waiter gives up and reads every slip carefully. A very eager waiter (the optimizing compiler) might even pre-write the table number onto a ticket without looking, betting the layout holds; if the bet loses, the ticket is torn up and the waiter starts again.

Context
§1 · Prerequisites

Six things to know first

  • Map: V8's hidden class, the layout descriptor shared by objects built alike.
  • Inline cache: a per-site memo keyed on Map.
  • Tiers: Ignition, Sparkplug, Maglev, TurboFan.

Six in total, each defined inside.

  • JS objects are dynamic. Semantically they are string-to-value maps, and the engine must make that fast anyway.
  • Prototype chain. A property miss on the object continues up the [[Prototype]] chain.
  • V8 tiers. Ignition (interpreter) → Sparkplug (baseline) → Maglev (mid) → TurboFan (top). (v8.dev/blog/maglev)
  • Smi. A small integer stored inline in a tagged word (low tag bit 0); heap objects are tagged pointers. With pointer compression a tagged value is 32 bits.
  • Feedback vector. A per-function array on the heap where each operation site (property load, call, +) records what it saw.
  • JIT speculation. Compile for the types you observed, guard with cheap checks, deoptimize when a guard fails.
§1b · Real-world context

Every Chrome tab, Node server and Electron app runs it

Chrome, Node.js, Deno, Electron apps and Cloudflare Workers all run V8. You never call it; you choose stable object shapes. Watch for --trace-deopt spam or LoadIC_Megamorphic in a profile.

What it is. A Map is V8's hidden class: an immutable-ish descriptor of an object's layout (which named properties, in what order, at which offsets, with which representations) plus its prototype and elements kind. An inline cache (IC) is a per-site memo keyed on Map that turns "find property x" into "compare Map, load at fixed offset".

Why it exists. The origin is the Self language (Ungar and Smith, 1980s), which invented maps to make prototype-based objects as compact as class-based ones. Hölzle, Chambers and Ungar's polymorphic inline caches (ECOOP '91) extended single-entry ICs to several entries per site: median 11% speedup on their Self programs, 27% with type feedback for recompilation, and about 2× fewer non-inlined sends (Self bibliography). Without it, every o.x is a hash probe or linear scan: slow and memory-hungry, because property names are stored per object.

Where it's used.

  • Chrome / Chromium: every web page's JS runs on V8.
  • Node.js, Deno: server-side JS on V8. Node's performance advice is basically "keep shapes stable".
  • Electron apps (VS Code, Slack): V8 inside.
  • Cloudflare Workers (workerd): V8 isolates.
  • SpiderMonkey (Firefox): the same idea, called Shapes, with ICs expressed in CacheIR. JavaScriptCore (Safari): Structures plus polymorphic ICs, tiers LLInt → Baseline → DFG → FTL. (Speculation in JSC)

How it's used. Nothing to call: it's automatic. What you touch are inspection flags and coding habits.

node --allow-natives-syntax --trace-opt --trace-deopt --trace-ic app.js
// d8 / node --allow-natives-syntax
%HasFastProperties(o)   // false => dictionary mode
%HaveSameMap(a, b)      // do two objects share a Map?
%DebugPrint(o)          // dumps Map, descriptors, elements kind

Habits: initialize all fields in the constructor in the same order; do not delete (set undefined or use a Map); keep arrays homogeneous and packed; keep hot call sites at 4 shapes or fewer.

When to use it, and when not. You don't opt in; you decide whether to design for it. It's worth caring about on hot paths (parsers, ECS loops, serializers, framework internals). It's not worth contorting cold code. Signs you picked wrong: --trace-deopt spam, %HasFastProperties false on hot objects, or a profile full of LoadIC_Megamorphic.

Who should care. Node and backend engineers on hot paths, framework and library authors, performance engineers, and security engineers. The JIT's shape assumptions are the richest browser-exploit surface.

Technical deep dive
§2 · The one-liner

"Fixed-offset loads" hides five moving parts

Maps form a transition tree keyed by property name and order, so {x,y} and {y,x} differ. The IC is a one-way state machine: mono, poly, mega. Optimized code bets on it and needs deopt. Every removed guard is a security assumption.

"V8 gives objects hidden classes so property access is a fixed-offset load."

It hides five things:

  1. Maps form a transition tree keyed by property name and order. {x,y} and {y,x} get different Maps.
  2. The IC is a monotonic state machine (uninitialized → monomorphic → polymorphic, up to 4 Maps → megamorphic) with a process-wide stub cache as the fallback.
  3. Optimizing tiers don't just use the IC. They bet on it (CheckMaps plus dependencies) and need deoptimization for when the bet loses.
  4. Field representation (Smi, Double, HeapObject, Tagged) is part of the shape and can change in place.
  5. Every guard the compiler removes is a security assumption. A modelling bug turns into type confusion.
§3 · The problem

Without shapes, every o.x is a search and every object repeats its keys

A naive property read is a hash probe or scan with several dependent loads, tens of nanoseconds, and each object stores its own key names. Self measured a point at 10 machine words without maps and 3 with. V8 needs about one load.

Semantically, o.x means: walk the object's property table (a hash map or sorted array), compare strings (interned, so pointer compares), and if the name is missing, climb the prototype chain. That is tens of nanoseconds with several dependent loads, per access, and every object repeats its key names. Self measured a "Cartesian point" at 10 machine words without maps and 3 with. A JS app does billions of accesses, and V8 needs about one load for each.

The fix is to give each shape a tag, so that a site which has seen that tag before can skip the search. The cost of the tag check and the fallbacks is modelled in the math card.

§4 · Mental model

A Map is a struct discovered at runtime

Map is the struct definition, the object is an instance, and the inline cache is a JIT-style switch(map) at each site. Unlike C structs, Maps mutate and get abandoned, and the switch gets baked into machine code, so invalidation is the hard part.

A Map is a struct definition discovered at runtime. An object is a struct instance: a map*, a properties*, an elements*, then the in-object fields. An IC is a JIT-style switch (map) at each site.

The header is a few pointer-sized words. A field that fits in the object sits right after it, and the spare slots are slack reserved for fields added later. Anything past that goes through the properties pointer.

Where the analogy breaks: C structs are fixed at compile time. Maps are discovered as the program runs, can mutate (field generalization, deprecation), and can be abandoned for dictionary mode. And the "switch" can be baked into machine code, which makes invalidation a first-class problem.

§5 · Mechanism, traced

One getX call, from cold miss to a deopt

A literal {x,y} follows Map transitions M0 → M1 → M2. The first call misses and stores a handler; the second is a compare and a load. A call with {y,x} fails CheckMaps, deopts, and the IC goes polymorphic.

6-step trace and an IC shape simulator inside.

Code:

function getX(o) { return o.x; }
getX({x: 1, y: 2});

Object creation. The literal {x:1,y:2} starts from a root Map M0 (empty, with in-object slack) and follows transitions: M0 --x--> M1 --y--> M2. M2's DescriptorArray is shared with M1 and M0 through the ownership rules: [x: field, in-object #0, Smi] [y: field, in-object #1, Smi].

Trace the two literals through the tree. The Map records the sequence of property additions, not the set of names, so the same keys in another order take a different branch and end at a different Map.

Layout (pointer compression, 4-byte tagged values):

offset  0   map        -> M2
offset  4   properties -> empty_fixed_array   (out-of-object overflow)
offset  8   elements   -> empty_fixed_array
offset 12   x          Smi(1)   (encoded 0b10)
offset 16   y          Smi(2)

Without compression, words are 8 bytes and x sits at offset 24. This is my derivation from the JSObject layout; check it with %DebugPrint.

Ignition and the IC, first call. The bytecode LdaNamedProperty a0, [name x], [slot 3] consults feedback_vector[3]. It is UNINITIALIZED, so the runtime LoadIC::Load does the real lookup in M2's descriptors, finds x at in-object index 0, builds a handler, and stores (weak M2, handler) in the slot. The handler is typically a Smi bit-packed with KindBits | IsInobjectBits | IsDoubleBits | FieldIndexBits (handler-configuration.h).

Second call (monomorphic hit). The slot holds M2. Load o.map, compare, decode the handler, load the field at index*word. No lookup.

Hot, then optimized (Maglev or TurboFan). The compiler reads slot 3 while building the graph. Monomorphic M2 with a field handler means it emits:

cmp  dword [rax + 0], M2_compressed
jne  deopt_entry
mov  r10d, [rax + 12]

(Illustrative sketch, not literal V8 output.) The compiler also registers a dependency of this code on M2 (the Map's dependent_code list). If M2 later becomes deprecated or its stability assumptions break, the code is invalidated.

The bet loses. Call getX({y: 1, x: 2}). That object has Map M3 (M0 --y--> --x-->). CheckMaps fails, which is an eager deopt. The deoptimizer uses the translation table to rebuild an Ignition frame from registers and stack, and execution resumes in the interpreter at the bytecode offset. The IC slot misses, sees a second Map, and becomes polymorphic: [(M2,h1),(M3,h2)]. The next optimization emits a 2-way CheckMaps.

Follow the failed guard below. It exits to the interpreter, the IC records the second Map, and the next compile guards on both.

Elements path (in parallel). arr[i] ICs key on the Map's elements_kind (part of bit_field2). Pushing 1.5 onto a PACKED_SMI_ELEMENTS array transitions its Map to PACKED_DOUBLE_ELEMENTS and rewrites the backing store. Code that assumed Smi elements guards on the Map and deopts.

Elements kinds form a lattice with one-way arrows. Each arrow is a transition the text describes, and none of them point back.

IC state machine

UNINIT --first Map--> MONO --2nd Map--> POLY(2..4) --5th Map--> MEGA
          (never goes back)                          \-> global stub cache probe

The IC state only moves rightward. Each new Map pushes the site one state further and it never resets.

§6 · The math

A speculation pays off only if it rarely loses

Speculation wins when the miss rate p is below (ts−tf)/(ts−tf+Cd). A 1 ns fast path against a 5 ns generic path means p must be about 1e-4 to 1e-3. The IC is linear up to 4 Maps, then hashed.

There is no deep math here. There are two useful cost models and one structural count.

(a) Speculation break-even

Let tf be the cost of the guarded fast path, ts the cost of the generic path, p the probability that the guard fails on an execution, and Cd the amortized cost of one deopt plus re-tier. Expected cost per execution when speculating:

E = (1 − p)·tf + p·(ts + Cd) ≈ tf + p·(ts − tf + Cd)→ in plain terms: the fast path is cheap, and each miss adds the generic cost plus the deopt cost.

Speculation beats always-generic when E < ts, that is, when p < (ts − tf) / (ts − tf + Cd). → in plain terms: a bet is worth it only if it loses rarely enough relative to how expensive losing is. A deopt costs microseconds-ish (my estimate, unmeasured) and a fast load costs about 1 ns, so p must be tiny, around 1e-4 to 1e-3. That is why V8 waits for stable feedback and caps retries.

Using my measured numbers (tf ≈ 1.0 ns, ts ≈ 4.9 ns), the generic path is only about 4–5× slower. That is the ceiling on the benefit of the whole machinery for this micro-case.

(b) IC lookup cost by state

Tmono = tcmp + tload;   Tpoly(k) ≈ k·tcmp + tload, k ≤ 4;   Tmega = thash + 1–2 probes of a global table + handler call

Why 4? A linear scan costs more with each entry while the hit-rate gain levels off. The constant kMaxPolymorphicMapCount = 4 is an engineering cutoff, not something derived. (I checked it as a constant in the V8 source per the research notes; I did not re-open the source myself.)

(c) Shape explosion

Adding n properties in every possible order gives up to n! root-to-leaf paths and Σ n!/(n−k)! Maps. A deterministic construction order collapses this to n+1 Maps per "class". → in plain terms: this is why order consistency matters.

Stub cache sizing

The stub cache is primary and secondary, two-level and hashed on (Map, name). In stub-cache.h at main I found kPrimaryTableBits = 12 (4096 entries) and kSecondaryTableBits = 10 (1024). One research agent claimed 11 and 9. The primary source says 12 and 10, so 11 and 9 are wrong. Sizes have changed across versions.

§7 · Why it works

Speculation is only safe because deopt is always there

Remove any piece and it breaks: no Maps means hash lookups, no ICs means a lookup forever, and speculation without deopt is unsound. Deopt is the safety net that makes aggressive guards legal. Real call sites see one shape more than 90% of the time.

Core insight: programs are far more regular than the language permits. Real call sites see one shape more than 90% of the time. The Self and PIC measurements and decades of JS engine telemetry back this. I did not find a single canonical V8 number, so treat the figure as folklore with support.

The ablations show which piece carries what:

  • No Maps: per-object name tables and hash lookups. Slow and memory-heavy.
  • Maps but no ICs: still a lookup keyed on the Map. The slow path forever.
  • ICs but no speculation (Ignition and Sparkplug): one compare and one load, but no inlining, no escape analysis, and no field-type knowledge.
  • Speculation but no deopt: unsound. Any surprise miscomputes. Deopt is the safety net that makes aggressive guards legal.
  • Speculation with a bug in dependency or guard elimination: type confusion (see the "where it breaks" card).
§8 · Knobs & alternatives

Poly limit 4, dictionary mode, and 21 elements kinds

A smaller poly limit goes megamorphic sooner, and a larger one slows every check. delete drops an object to dictionary mode, where ICs can't specialize. Elements kinds only generalize one way. The cap of 4 is an engineering choice, not derived.

KnobEffect
Poly limit (4)Smaller means megamorphic sooner. Larger means slower polymorphic checks.
In-object slack trackingOver-allocate for constructors (research notes: +8 slots, counter 7), then shrink after a few allocations.
Dictionary modeUsed on delete or huge property counts. Stops using Maps and uses a hash table, so ICs can't specialize.
Elements kinds (21)Specialize arrays by Smi, Double or Tagged, and packed or holey. Transitions only generalize.
Tier thresholdsTrade warm-up against peak speed. Maglev sits at the mid tier.
Const field trackingImmutable fields can be embedded as constants in optimized code, and invalidated on write.

Alternatives. SpiderMonkey uses CacheIR, which expresses ICs as a small IR that is both interpreted and compiled. Reported: 25–30% of compiled code is IC stubs (Bernstein's CacheIR paper). JSC uses Structures with repatching ICs, plus DFG and FTL speculation. Hermes uses static shape-ish layouts with a hidden-class cache. Classic class-based languages have a static shape, so they need no guards at all.

§9 · Where it breaks

Optimizer Map bugs have repeatedly become type confusion

When the compiler removes a CheckMaps, it has proved the Map can't change. A wrong side-effect model gives type confusion, then addrof, then arbitrary read and write. CVE-2020-6418, CVE-2020-16009 and CVE-2025-2135 follow that pattern. The V8 sandbox contains these; it does not fix them.

Performance

The first failure is order. Two literals with the same keys in a different order end at different Maps, so one site sees two shapes and goes polymorphic.

  • Megamorphic cliff. My measurement (Node v24.12, one machine): mono 0.99 ns, 4-shape 4.06 ns, 8-shape 4.90 ns, 64-shape 4.80 ns per call. The loop includes i % len and an array load. The cliff is mono to poly. Megamorphic adds little on top here, because the stub cache hits.
  • delete flips the object to dictionary mode, and %HasFastProperties returns false.
  • Elements-kind generalization is one-way. A single NaN or -0 makes a Smi array double. A hole makes it holey "forever" (elements-kinds). The famous "6×" in that post is about an out-of-bounds read bug, not holes.
  • Deopt loops. Repeated deopts lead V8 to stop reoptimizing. One research agent said "~30". I could not verify the number, so treat it as unverified.

Security (the big one)

The compiler removes CheckMaps when it proves the Map can't have changed between two points. The proof depends on a precise side-effect model. A wrong model gives a wrong Map assumption, which gives type confusion, which gives addrof and fakeobj, which gives arbitrary read and write.

  • CVE-2020-6418. NodeProperties::InferReceiverMapsUnsafe special-cased kJSCreate and forgot to mark the result unreliable, though JSCreate can run user code (for example a Proxy as the third argument to Reflect.construct). The optimizer inlined Array.pop. The side effect changed the elements kind from Smi to Double mid-function, and the optimized code kept treating a double backing store as tagged. (Project Zero RCA)
  • CVE-2020-16009. Map::CanBeDeprecated() wrongly said Maps with only Double or Tagged fields can't be deprecated (pointer compression, no unboxed doubles). So no code dependency was installed, and the Map was deprecated anyway. The in-place generalization from Double to Tagged then led to Double/Tagged confusion. (Project Zero RCA)
  • CVE-2025-2135. The InferMapsUnsafe() handling of TransitionElementsKindOrCheckMap lacked an aliasing check. It returned kReliableMaps when two IR nodes referred to the same runtime object, which gave object-array vs double-array confusion. It was exploited within the V8 sandbox. (Zellic)
  • CVE-2022-1134 ("Super IC"). Confusion between lookup_start_object and receiver in the super-property IC. (GitHub Blog) I read this in the research agent's notes and did not re-fetch it.

The security cases below follow one chain. Each step is a fact the optimizer has to get right, and one wrong fact removes a guard that the rest of the code depends on.

The pattern: an optimizer reasoning about Maps and elements kinds across an effect chain is a soundness proof written in C++. The V8 sandbox (a pointer-compression cage plus indirection tables) limits what a corrupted heap can reach. It doesn't fix the logic bugs (v8.dev/blog/sandbox).

Misconceptions

  • "Hidden classes are per constructor." No: they are per transition path.
  • "Polymorphic is always bad." At 4 or fewer shapes it is fine.
  • "delete is slow because it's slow." It flips the object to a different representation, which hurts every later access.
  • "The sandbox makes JIT bugs harmless." No. It only contains them.

I dropped several CVE claims from the research notes that I could not confirm: an ID in the CVE-2026 range with a GitHub-repo-only source, and unverified root causes for CVE-2022-1096 and CVE-2023-3079.

§10 · In the wild

Real engines add tiers and deviate from textbook PICs

Maglev compiles about 10× slower than Sparkplug and 10× faster than TurboFan, and cut Speedometer energy by 10%. Turboshaft halved compile time. V8's ICs live in a heap feedback vector, not patched machine code, and megamorphic sites use a global stub cache.

  • Node and Chrome tiers. Ignition → Sparkplug → Maglev (Chrome M117) → TurboFan. Maglev compiles "roughly 10× slower than Sparkplug, 10× faster than TurboFan", and gives −10% energy on Speedometer and −3.5% on JetStream (v8.dev/blog/maglev). A research agent said 20×; the primary source says 10×.
  • Turboshaft. A CFG IR replacing Sea of Nodes in TurboFan's backend. "Compile time got divided by 2" (blog).
  • React cliff. A real-world shape and representation performance cliff documented by V8 (v8.dev/blog/react-cliff).
  • Deviations from textbook PICs. V8's ICs live in a heap-allocated feedback vector, not in patched machine code. Handlers are Smi-encoded data. Megamorphic sites use a global stub cache. Textbook PICs patch call-site code in place.

§11 · Frontier

Recent work keeps speculation sound and cheap

Mutable heap numbers (2025) avoid an allocation per update, about 2.5× on async-fs. Turboshaft's CFG IR halved compile time. Translation validation and fuzzers (TurboTV, OptFuzz, DUMPLING) hunt the optimizer bugs that keep recurring.

The settled core is old and the periphery is active. The idea is 35 years old. Recent work is on keeping speculation sound and cheap.

  • Mutable heap numbers (V8 blog, 2025-02-25). Script-context slots own a mutable HeapNumber or Int32, which avoids an allocation per update. About 2.5× on async-fs and about 1.6% on JetStream2. Verified. (v8.dev/blog/mutable-heap-number)
  • Leaving the Sea of Nodes (V8 blog, 2025-03-25). CFG IR migration, 2× compile time. Verified. The date is from the research notes. (blog)
  • CVE-2025-2135 writeup (Zellic, 2025). An aliasing bug in map inference, found through V8CTF. Verified. (Zellic)
  • Translation Validation for the V8 JIT (TurboTV) (ICSE 2024). SMT-based validation of TurboFan optimizations, which finds range-analysis bugs. Reported by a research agent; I did not open it. (paper)
  • OptFuzz (USENIX Security 2024). Optimization-path-guided fuzzing: 36 new bugs across V8, JSC, SpiderMonkey and Hermes, per the agent. Not opened. (slides)
  • DUMPLING (NDSS 2025). Fine-grained differential fuzzing that compares engine state: 8 new V8 bugs, per the agent. Not opened. (paper)
  • The agent also listed CoSSJIT (OOPSLA 2025), Understanding and Finding JIT Compiler Performance Bugs (arXiv 2603.06551), and a December 2025 data-centric fuzzing paper (arXiv 2512.18102). I did not verify these, so they are only pointers.
§11b · Open problems

Sound speculation, containment and warm-up are still open

No production-scale proof says effect-chain Map inference is correct, and the same bug family recurs from 2020 to 2025. Open questions: can the sandbox make JIT bugs non-critical, can feedback be cached without staleness, and does IC state leak timing?

  • Sound speculation. No production-scale proof exists that effect-chain Map inference is correct, and bugs recur (2020 to 2025 in the same function family). The obvious fix, always keeping CheckMaps, loses much of the benefit. Approaches: translation validation (TurboTV), differential fuzzing, and verified speculation (POPL '21, Vitek et al.).
  • Containment versus correctness. The V8 sandbox treats logic bugs as inevitable. It is an open question whether containment can get strong enough to make JIT bugs non-critical.
  • Warm-up. Feedback must be re-learned on every page load. Caching or snapshotting profiles risks stale or attacker-influenced feedback.
  • Side channels. IC state and tier changes create data-dependent timing, which is reported to undermine constant-time JS (JIT-Leaks, IEEE S&P 2020; DeJITLeak, ESEC/FSE 2022). From research notes; unopened.
  • Representation invariants across Map deprecation (the CVE-2020-16009 class) have no decidable, general checker.
§12 · Lineage

Inline caches date to 1984, and V8 added Maglev in 2023

Smalltalk-80 inline caching (1984), Self maps (1989), polymorphic ICs (1991), V8 hidden classes (2008), then Ignition and TurboFan (2017), Sparkplug (2021), Maglev (2023), and Turboshaft with the sandbox (2024–25).

Smalltalk-80 inline caching (Deutsch and Schiffman, 1984) → Self maps (Chambers, Ungar and Lee, 1989) → PICs (Hölzle, Chambers and Ungar, ECOOP '91) → V8 hidden classes (2008, Crankshaft) → Ignition and TurboFan (2017) → Sparkplug (2021) → Maglev (2023) → Turboshaft, the sandbox and mutable heap numbers (2024–25).

The Deutsch–Schiffman date is from memory and I did not check it here.

A weak reference to the Map plus a handler (typically a Smi encoding kind, in-object flag, double flag and field index).

3. What happens on getX({y:1,x:2}) after getX was optimized for {x,y}?

CheckMaps fails, then eager deopt rebuilds the Ignition frame, the IC becomes polymorphic, and a later reopt uses a 2-way check.

→ related card
4. How does push(1.5) on a Smi array change things?

The Map changes to PACKED_DOUBLE_ELEMENTS and the backing store is rewritten as unboxed doubles. The change is one-way.

→ related card
5. Where does a megamorphic site look?

The global two-level stub cache, keyed on (Map, name). On a miss it falls back to a runtime lookup.

→ related card
Why
6. Why do {x,y} and {y,x} have different Maps?

Transitions are labelled by property name in insertion order, and offsets depend on that order.

→ related card
7. Why cap polymorphism at 4?

Linear checks cost more per entry while the hit-rate gain levels off. Beyond that, a hashed global lookup is cheaper. It is an engineering constant.

→ related card
8. Why is deoptimization necessary rather than a luxury?

Guards can fail. Without a way back to a generic tier, the optimized code would have to be correct for all inputs, which defeats speculation.

→ related card
9. Why does delete hurt later reads?

The object flips to dictionary mode. It has no stable Map to key on, so ICs can't specialize.

→ related card
Counterfactual
10. What if V8 never removed redundant CheckMaps?

The CVE-2020-6418 class mostly disappears, but every property access pays a compare, which loses a chunk of optimized-code speed.

→ related card
11. What if the IC cap were 1?

Any two-shape site would go megamorphic. The common optional-field pattern would hit the stub cache constantly.

→ related card
12. What if elements kinds could transition back?

Optimized code would need more dependencies and deopts, and flip-flopping arrays would thrash. One-way transitions keep the lattice finite and monotone.

→ related card
Adversarial
13. How does an attacker turn a missing side-effect model into addrof?

They use user-controllable code (a Proxy, valueOf) at the unmodeled effect to change the Map or elements kind. The optimized code still reads with the old layout, so a double array's words are read as tagged pointers (a leak), or a crafted double is read as a pointer (a fake object).

→ related card
14. Can an attacker influence what the IC caches?

Yes. They control which shapes reach a site, so they steer the feedback and therefore which speculation the compiler makes. This is JIT-spray-like feedback grooming.

→ related card
15. Why doesn't the V8 sandbox end this class?

It bounds what corrupted pointers can reach, not the corruption itself. In-sandbox arbitrary read and write remains, and escapes target the boundary.

→ related card
Connection
16. How is this like a CPU branch predictor plus a pipeline flush?

The guard is a predicted branch and the deopt is the flush. Both bet on regularity and trade a rare large penalty for a common cheap path.

→ related card
17. How do Shapes in SpiderMonkey differ?

The idea is the same. ICs are expressed as CacheIR, so the same IR can be interpreted or compiled.

→ related card
18. How does this relate to Spectre-style attacks?

Both are speculation: one in hardware, one in software. Software speculation's guards are architecturally visible bugs, while hardware's are microarchitectural leaks.

→ related card
Open
19. Can speculative JIT optimizations be formally verified at production scale?

Unsettled. Translation validation finds bugs but does not yet gate production releases.

→ related card
20. Can feedback be persisted safely across loads?

Unsettled. It trades warm-up for staleness and attacker-influenceable state.
