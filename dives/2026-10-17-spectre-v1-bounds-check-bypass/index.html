Spectre v1: branch predictor mistraining, bounds-check bypass, cache timing reads

A CPU guesses which way an if will go before it knows, and runs ahead on that guess. Spectre v1 trains the guess to say "in bounds" on purpose, lets the CPU speculatively read out-of-bounds secret memory, and uses that secret as an index into a second array — pulling one cache line into the cache. The CPU later undoes every register change, but the warm cache line survives, and timing which of 256 lines is warm reveals the secret byte.

The whole idea in 8 scrolls

How a mistrained guess and a stopwatch read memory nobody was allowed to see

Every modern CPU runs ahead of itself. Before it knows whether an if will be true, it guesses — using the branch predictor, a small table that remembers how that branch went last time — and starts executing the path it thinks is right.

The trick starts with training. Call the checked function 25 times with a legal index. The predictor's short-memory counter locks toward "in bounds" — it has no way to know you're about to lie to it.

Now call it once with an index that points past the end of the array — straight at a secret byte. The real check hasn't resolved yet. The predictor, freshly trained, says "go ahead" anyway, and the CPU speculatively reads the out-of-bounds byte.

That secret byte (say, 81) is immediately used as an index into a second array. The CPU doesn't read the secret's value out loud — it reads one specific cache line of 256 possible ones, chosen by the secret.

Then the real check catches up: out of bounds, access denied. The CPU rolls back every register, every memory write, every flag — exactly as the architecture promises. Officially, nothing happened.

But caches were never part of that promise. One of the 256 lines is still warm. Time a read to all 256, in a shuffled order (so the hardware prefetcher can't give the game away) — 255 come back slow, one comes back fast.

Repeat the whole dance — flush, train, attack, probe — up to 999 times, voting on the winner each round. A clean signal usually wins in far fewer rounds than that.

The result: a byte of memory the program never let you read, recovered through nothing but timing. Disclosed in 2018 alongside Meltdown, Spectre v1 forced every compiler, kernel, and browser to pay a permanent tax on security-sensitive branches — and as of 2026, nobody has shipped a complete fix.

Plain English
In everyday words

A librarian who guesses ahead, and leaves a warm shelf behind

A fast librarian starts fetching a book before your badge is checked, because you usually get a yes. If the badge check fails, she puts the book back and says nothing happened — but the shelf she visited to find it stays warm, and you can feel which shelf that was.

That warmth is a secret byte, read without ever being allowed to read it.

Picture a librarian who works fast by guessing ahead. Every time you ask for a book, she doesn't wait for the front desk to confirm your library card covers that shelf — she's seen you ask for shelf-12 books a hundred times before, so while the front desk is still checking, she's already running to shelf 12, grabbing the book, and flipping to a page number written in pencil on its inside cover. If the front desk comes back and says "actually, your card doesn't cover shelf 12," she quietly puts the book back and tells you nothing happened. Officially, you never saw that book.

But she left a trace. To find that pencil-written page number fast, she memorized roughly where it was by re-visiting a different shelf — shelf-13A if the page number's first digit was 1, shelf-13B if it was 2, and so on — just enough to warm up her memory of that one spot. Now: if you ask her to re-fetch something from shelf-13B right after, she gets it to you noticeably faster than from 13A, because her memory of 13B is still warm from a few seconds ago. By timing how fast she responds across all 256 sub-shelves, you can figure out exactly which one she visited — and that tells you the pencil-written number on a page you were never allowed to read.

That's Spectre v1. The CPU is the librarian. Branch prediction is her guessing which way an if will go before the real answer (a slow, uncached bounds check) comes back. The "shelf 13" visits are cache lines. The trick isn't making the CPU read forbidden memory — it already does that, briefly, as an optimization every CPU performs billions of times a second. The trick is getting it to leave a provable, timeable fingerprint of a byte it was never supposed to look at, in a way that survives the CPU officially "undoing" the whole thing.

Everyday example

Say a program has a byte array secret[] you can't touch directly, and a function that does: if (x < array1_size) y = array2[array1[x] * 256]; — array1_size is 16, so indices 0–15 are legal. You've been calling this function with legal x values a few hundred times, training the branch predictor to expect "yes, in bounds." Then, once, you flush array1_size from cache and call it with x = 1000, pointing past the end of array1 into memory holding a secret byte — say the ASCII value for 'Q' (81). The CPU's predictor says "go ahead" before the real check resolves. It speculatively reads array1[1000] → gets 81, then speculatively reads array2[81 * 256], pulling that one cache line into the CPU's cache. Microseconds later the real check finishes, says "out of bounds," and every register change is thrown away. But the cache line for array2[81*256] is still warm. You time a read to every one of the 256 possible slots: 255 are slow, one — i=81 — is fast. You just read a byte you had no permission to read.

Context
§1 · Prerequisites

Five things to know first

  • Speculative execution: CPUs run ahead of unresolved branches and roll back if wrong.
  • Branch prediction is trainable by an attacker who controls the branch's inputs.
  • Caches are not rolled back — that's the whole bug.
  • Speculative execution: CPUs execute ahead of resolved branches/dependencies using predictions, and discard the results if the guess was wrong — a decades-old perf trick assumed to be "architecturally invisible."
  • Branch prediction: the CPU remembers past outcomes of a conditional branch and predicts the next one; it can be trained by an attacker who controls the inputs to that branch.
  • Cache timing side channel (Flush+Reload style): a recently-loaded shared cache line answers in tens of cycles; one that must come from RAM takes hundreds — timing a read reveals whether a specific address was touched.
  • "Architecturally invisible, microarchitecturally visible": registers and memory from a squashed speculative path are rolled back; caches, TLBs, and branch-predictor state are not. That gap is the covert channel.
  • Bounds check: if (x < size) array[x] — the exact pattern an optimizing compiler leaves un-fenced by default, because fencing every branch is expensive (§8).

Source: Kocher et al., "Spectre Attacks," arXiv:1801.01203 / IEEE S&P 2019; Project Zero, "Reading privileged memory with a side-channel".

§1b · Real-world context

Where it lives: browsers, kernels, crypto libraries

Disclosed Jan 2018 (CVE-2017-5753) alongside Meltdown. Mitigated piecemeal in the Linux kernel (array_index_nospec), V8/Chrome (poisoning, Site Isolation), LLVM (Speculative Load Hardening), and compilers (MSVC /Qspectre). Crypto libraries (OpenSSL, libsodium) are still a live hardening target.

Spectre v1 (CVE-2017-5753, "bounds check bypass," later called Spectre-PHT) is a class of attacks where an attacker mistrains a CPU's conditional-branch predictor so the processor speculatively executes the "in-bounds" path of a bounds check that will actually fail, reads out-of-bounds data, and uses that data as an index into a second array — pulling one specific cache line into the cache. Timing a read of that second array afterward reveals which line was touched, leaking the out-of-bounds byte. Disclosed January 3, 2018, alongside Meltdown, by researchers at Graz TU, Google Project Zero, Cyberus Technology and others.

Why it exists

Out-of-order, speculative CPUs have chased single-thread performance for 25+ years by guessing branch outcomes ahead of time; undoing a wrong guess architecturally (registers, memory) was assumed to make it "as if it never happened." Nobody budgeted for microarchitectural state — caches — as a side channel until Spectre showed it was a generic, reliable, cross-privilege-boundary leak, not a one-off bug in one CPU.

Where it's used

Browsers (Chrome/V8, Firefox, Safari)
The most exploited surface — JavaScript gives attackers a timer, a sandbox to mistrain branches in, and shared process memory with other sites' secrets.
Linux kernel
Every syscall boundary where a user-controlled index reaches a kernel array is a candidate gadget, patched incrementally.
Compilers
LLVM's Speculative Load Hardening, MSVC's /Qspectre auto-insert mitigations at detected or suspected gadgets.
Crypto libraries
OpenSSL, libsodium, NaCl, PQClean — secret-dependent branches/indices are exactly the gadget shape, a standing hardening target.
Multi-tenant / cloud
Anywhere an untrusted guest shares a core or cache with a victim process.

How it's used

You don't "use" Spectre v1 — you harden against it. A kernel dev wraps a user-controlled index with array_index_nospec(index, size); a compiler flag (-mspeculative-load-hardening, /Qspectre) auto-inserts barriers; a crypto library author runs a gadget scanner against secret-dependent branches. Typical pattern: compile hot, sensitive code (syscall entry, interpreter dispatch, crypto) with SLH or targeted fences; leave cold code unmitigated for speed.

Mitigate when: untrusted input controls an array index that's checked before use, and the checked-but-unconfirmed value can reach a second, secret-dependent access — interpreters, JIT dispatch, syscall entry, crypto.
Skip blanket hardening when: no attacker-controlled index or no adjacent secret exists — fence-every-branch is severe overhead and still provably incomplete.

Who should care: browser/JS-engine engineers, OS kernel maintainers, compiler engineers, cryptographic-library authors, and anyone running multi-tenant infrastructure where attacker and victim share a core.

Technical deep dive
§2 · The one-liner

"Tricks the CPU into running code it shouldn't" hides five things

The CPU does nothing abnormal — the bug is that rollback is architectural-only. Mistraining is just 5 good calls per 1 bad one. The leak is a 256-way vote, not a direct read. And there's no clean fix.

"Spectre v1 tricks the CPU into executing code it shouldn't, and reads the result through the cache." That hides:

  1. The CPU does nothing abnormal — it's doing exactly what branch prediction and speculative execution are supposed to do. The bug is that rollback is architectural-only.
  2. Mistraining is deliberate and cheap: ~25 "good" calls per "bad" one, no code injection needed — just control over an input that reaches a checked index.
  3. The leak isn't a single read — it's a probe over 256 possible values, repeated up to 999 times per byte, decided by majority vote.
  4. The "secret" doesn't need to be adjacent to the first array — it's whatever lands at an attacker-chosen out-of-bounds offset, including across a security boundary.
  5. There is no clean fix — mitigations are a tax on checked branches, chosen case by case, none proven to catch every gadget shape.
§3 · The problem

"Invisible" meant invisible — until caches proved otherwise

Guess first How many bytes per second did the original Spectre v1 proof-of-concept leak, end to end?

About 10 KB/s. Each byte needs up to 999 rounds of 30 victim calls plus a 256-line timing probe, so the rate is bottlenecked by that per-byte voting process, not by memory bandwidth.

A wrong speculative guess was assumed to leave zero trace. It leaves a warm cache line. That one gap leaked memory at about 10 KB/s on the original 2018 hardware — slow, but enough to steal a key in seconds.

Before Spectre, "architecturally invisible" meant invisible, full stop — a wrong speculative guess rolled back registers and memory and that was assumed to be the end of the story. Compilers and OS/kernel code freely wrote bounds checks like if (x < size) use(array[x]), trusting that even if the CPU peeked ahead on a bad guess, nothing observable happened.

The constraint Spectre forces: any microarchitectural state that a wrong-path instruction touches and that isn't rolled back (L1/L2/L3 cache lines, TLB entries, branch-predictor tables) is a covert channel if an attacker can control what gets touched and measure the state afterward with a timer.

§4 · Mental model

The librarian analogy, and where it breaks

Guess-ahead, fetch, undo, but the shelf stays warm. Breaks down because the CPU's undo really is bit-exact architecturally, and one trip isn't enough signal — it takes hundreds of repeats to beat noise.

Analogy: the librarian from the plain-English card — guesses ahead of a slow permission check, leaves a pencil-trace of what she fetched, "un-fetches" it on paper but the trace (a warm shelf) stays.

Where it breaks: real librarians don't literally run to a shelf and then "forget they ever went" — a CPU's rollback really is bit-exact at the architectural level (registers, memory, flags all restored as if the branch had resolved correctly from the start). The analogy also undersells how statistical the leak is: one trip isn't enough to beat noise; it takes hundreds of repeats before timing is reliable, because contention, prefetching, and frequency scaling all jitter the signal.

29,970 = 999 rounds × 30 calls/round. In practice the vote usually wins its 2×+5 margin far earlier, so real runs are much shorter — 999 is only the cutoff.

Flush the check, call the victim 25 times legally and 5 times maliciously, then time all 256 candidate cache lines in shuffled order. The fastest one is the secret byte.

Interactive step-through inside.

The paper's actual code (Listing 4, arXiv:1801.01203, verified against the PDF). Goal: read the byte at &secret[k], reached via malicious_x = secret - array1.

unsigned int array1_size = 16;
uint8_t array1[160] = { 1,2,3,... };   // ...secret lands past the end
uint8_t array2[256 * 512];
#define CACHE_HIT_THRESHOLD (80)       // cycles

void victim_function(size_t x) {
  if (x < array1_size) {
    temp &= array2[array1[x] * 512];
  }
}

On each of the 5 "attack" calls, the predictor — freshly trained 5-to-1 toward "in bounds" — speculates past the not-yet-resolved check, computes array1[malicious_x] (the real secret byte, say 81), and speculatively reads array2[81*512], pulling that line into cache. Microseconds later the real check resolves false and every register change is squashed — but the cache line stays warm.

Attention over the probe

Read all 256 possible array2[i*512] with rdtscp-timed loads, in shuffled order mix_i = (i*167+13) & 255 (defeats a stride prefetcher from pre-warming neighbors). Any time2 <= 80 cycles counts as a hit.

for (i = 0; i < 256; i++) {
  mix_i = ((i * 167) + 13) & 255;
  addr = &array2[mix_i * 512];
  time1 = __rdtscp(&junk);
  junk = *addr;
  time2 = __rdtscp(&junk) - time1;
  if (time2 <= CACHE_HIT_THRESHOLD && mix_i != array1[tries % array1_size])
    results[mix_i]++;
}

Repeat the whole round up to 999 times; accept the leading index once its vote beats the runner-up's by 2×+5.

§6 · The math

256-way voting turns an unreadable byte into a timeable signal

Guess first Each round makes 30 calls to the victim function. How many use the malicious (out-of-bounds) index versus the legal training index?

5 malicious, 25 training (triggered when j % 6 == 0). That 5:1 ratio is enough to keep the branch predictor's saturating counter locked toward "in bounds" without needing every call to be legal.

The secret becomes an array index, not a value — so there's something to measure. Accept a guess only when its vote count beats the runner-up by 2× + 5, because single timings are noisy.

Why 256-entry probing, not a direct read

The attacker can't read array2[secret] directly — that access never architecturally completes. Instead the index into a 256-wide array is forced to equal the secret byte, so the only thing left to measure is which of 256 possible cache lines is warm.

stride ≥ cache_line_size, and gcd(stride, line_size) keeps each index on a distinct line → in plain terms: space the targets out far enough that reading one line never accidentally warms its neighbor.

The *512 stride (or *256 in the paper's other listing) exists so each candidate index lands on a distinct 64-byte cache line with comfortable separation from prefetch bleed-through.

The confidence margin

accept j ⇔ results[j] ≥ 2·results[k] + 5 (k = runner-up) → in plain terms: don't trust a single timing; trust a landslide.

With noise (OS scheduling jitter, other cores' cache traffic, DVFS), a single round's "fast" measurement isn't reliable — a false hit can land on the wrong index by chance. Each of the 999 rounds is treated as a noisy vote; a value is accepted once its vote count is more than double the nearest rival's plus a small margin, a simple two-sample separation test rather than a fixed statistical model.

5 malicious, 25 training (triggered when j % 6 == 0). That 5:1 ratio is enough to keep the branch predictor's saturating counter locked toward "in bounds" without needing every call to be legal.

The mistrain ratio

5 training calls : 1 attack call, per round of 30 → in plain terms: the predictor has short memory and a bias toward its most recent consistent pattern, so you only need to out-vote the outlier, not eliminate it.

Branch predictors use saturating counters (commonly 2-bit) that need a handful of consistent outcomes to flip state and a comparably small number of inconsistent ones to flip back. 5:1 keeps the counter saturated toward "predict taken" even though 1-in-6 calls disagrees.

Leak rate

~10 KB/s empirically (paper, i7 Surface Pro 3) — bounded by cache-probe time (256 timed reads) × rounds-to-confidence (up to 999) per byte, serialized per byte. No closed-form "bits per cycle" is given in the paper; it's an empirically measured end-to-end rate, not a derived bound.

§7 · Why it works

Rollback restores registers, never caches

Remove mistraining, the flush, the second array, or the timing probe, and the attack dies at that step. The one thing nobody designed to be rolled back is exactly the thing that's exploitable.

Core insight: speculative execution's rollback is architectural-only by design — registers, flags, memory are restored — but caches, TLBs, and branch-predictor tables were never part of that contract, because nobody designed them to be. Any instruction that executes on a mispredicted path and touches memory leaves a trace in microarchitectural state that survives the squash, and that trace is readable by anyone who can measure timing.

About 29% — roughly half of LFENCE's 62% cost, so SLH keeps close to twice the throughput while still masking every flagged load.

LFENCE-everywhere is complete-ish but 2–3× slower. Speculative Load Hardening masks values instead of halting the pipeline, keeping far more throughput. Targeted hardening (2025) narrows the tax further, at the cost of needing a correct static analysis.

  • Probe technique: Flush+Reload (needs a shared, flushable cache and a clflush-equivalent) vs Prime+Probe (fills a whole cache set instead, noisier, needed where flush instructions are restricted).
  • Stride size (256 vs 512 across the paper's two listings): bigger strides reduce false sharing/prefetch bleed-through at the cost of touching more memory per probe.
  • Timer resolution: rdtscp gives cycle-accurate timing; browsers deliberately coarsen performance.now() (5µs → 100µs in Chrome, plus jitter) — reduces but, per the 2018 Aleph bypass, doesn't eliminate the channel.

§9 · Where it breaks

Every shipped mitigation admits it isn't complete

Guess first Within months of browsers shipping timer-coarsening as a Spectre mitigation (2018), how fast could a researcher still read secret memory from pure JavaScript?

About 1 bit/second (Aleph Security, 2018) — recovered by repeating the measurement many times and statistically filtering the added timer jitter. Coarsening raised the cost; it didn't close the channel.

Linux's own docs say annotated sites "may not cover all attack vectors." Browser timer-coarsening was defeated within months by repeating the measurement. No microcode patch ever fixed v1.

Mitigations are provably partial, by the mitigators' own admission. The Linux kernel's own docs say manually annotated array_index_nospec sites "may not cover all attack vectors." MSVC's /Qspectre docs give no full-coverage guarantee. LLVM's SLH explicitly skips constant-stack-offset loads as an optimization, leaving some loads unmasked.

Browser timer mitigations are defeated by amplification. Chrome/Firefox/Safari's coarsened/jittered timers (2018) were shown bypassed by Aleph Security within months, recovering ~1 bit/s by repeating the measurement many times and statistically filtering jitter.

Misconception: "LFENCE everywhere is enough." LFENCE is serializing and does stop speculation past it, but it's expensive everywhere it's placed (teams place it conservatively/incompletely), and SLH's own correctness argument depends on CPUs not speculating on flags or certain register values — an assumption Intel's architecture manual doesn't formally guarantee (Silberstein et al., 2018).

Misconception: "a microcode patch fixed Spectre." False for v1 — microcode/firmware updates targeted Meltdown and Spectre v2 (branch target injection, IBRS/IBPB); v1 (PHT) has stayed a software-mitigation-only problem on every mainstream CPU vendor's public guidance found in this research.

Shared-cache side channels outlive this one gadget. Speculative store bypass (CVE-2018-3639) is a sibling variant. Unrelated to Spectre mechanically but the same cache-timing family: 2025 research found 7 audited LLM API providers (including OpenAI) shared prompt caches across users, letting an attacker infer another user's prompt via time-to-first-token (Gu et al., ICML 2025).

Little is publicly characterized about v1 on some newer ARM client cores relative to Intel/AMD, per research literature gaps found here — flagged as an open area, not a settled "ARM is immune" claim.

§10 · In the wild

How browsers, kernels, and compilers actually ship it

V8 "poisons" loaded values instead of fencing; Linux hand-annotates syscall boundaries; LLVM's SLH is opt-in because of its cost; Site Isolation matters more than any in-process trick.

  • Linux kernel: case-by-case array_index_nospec()/array_index_mask_nospec() at syscall boundaries found by manual audit and later static/dynamic scanning; barrier_nospec() (an LFENCE) specifically on copy_from_user paths and the swapgs entry sequence.
  • V8/Chrome: "poisoning" — a per-branch poison register that becomes zero on a mispredicted path and is multiplied into every subsequent load's result, applied to user bounds checks and V8's own bytecode dispatch and function-entry checks; under 20% cost on Octane vs 2–3× for fencing every branch. WebAssembly gets index masking only on 32-bit (power-of-two-padded memories); 64-bit relies on guard pages. Site Isolation (default since Chrome 67, 2018) is the backstop that matters more than any in-process trick.
  • LLVM SLH: ships opt-in, not default — reflecting that teams choose it only for genuinely sensitive code given its cost; needs retpolines for indirect calls/returns and BMI2 for efficient x86 codegen of the masking sequence.
  • Compiler-generated mitigations miss near-variant gadgets: Silberstein et al. (2018) reported Microsoft's compiler-inserted LFENCEs missing some gadget shapes close to, but not identical to, the canonical pattern.
Research edge
§11 · Frontier

From finding gadgets to proving their absence

LightSLH (USENIX Sec'25) hardens only exploitable load sites, 0% overhead in half its test cases. SPS (2025–26) makes Spectre-safety a provable property. dfence (2026) proposes new silicon at under 1% overhead. SpecRL (2025) hunts leaks in black-box CPUs with reinforcement learning.

Spectre v1 detection and exploitation are settled science; the active work has moved to (a) provable, targeted hardening that doesn't pay the fence-everywhere tax, and (b) finding gadgets nobody annotated, including in silicon nobody can see inside.

  1. LightSLH — "Place Protections at the Right Place" (Zhu, Huang, Xiong; USENIX Security 2025; arXiv:2408.16220). A fixpoint static analysis finds exactly which load sites are exploitable Spectre-v1 gadgets and hardens only those. On OpenSSL, libsodium, NaCl, and PQClean it achieved 0% measured overhead in half the evaluated cases while finding two previously unknown Spectre-v1 issues.
  2. Speculation-Passing Style (SPS) (Arranz-Olmos, Barthe, Blatter, Xie, Zhang; arXiv:2510.11573, 2025–26). A program transform that reduces proving speculative constant-time security to proving ordinary constant-time security — proven sound and complete. Turns "is this crypto code Spectre-v1-safe" into a problem existing constant-time verifiers (EasyCrypt, BINSEC, ctgrind) can already answer.
  3. dfence (Davoli, Bognar, Daniel, Grégoire, Piessens, Rezk; arXiv:2608.06124, 2026). A new CPU instruction generalizing Speculative Load Hardening to cover both PHT (v1) and speculative store bypass; implemented in the Proteus research CPU at under 1% average overhead — near-zero cost, though it requires new hardware.
  4. SpecRL (Lai, Xiong, Suh, Tiwari, Luo; arXiv:2502.16756, 2025). Reinforcement learning to search black-box, post-silicon microprocessors for speculative leaks, rather than requiring source/RTL access.

Seen in search results but not independently fetched/verified in this run: Phantom Trails (pre-silicon transient-leak discovery, claimed USENIX Security 2025), SpecASan (ARM-MTE-style hardware tagging defense, claimed ISCA 2025), a claimed USENIX Security 2026 paper on Spectre against RISC-V silicon, Teapot (binary gadget scanning, claimed CGO 2025), GadgetMeter (claimed NDSS 2025). These line up with the two live threads above but should be checked at the source before being treated as established.

§11b · Open problems

No proof of absence, no hardware fix, no agreed definition

No tool proves a real binary is gadget-free. No shipped CPU fixes PHT in silicon. ARM client cores are thin in the literature. Nobody has benchmarked the newest hardening tools against each other.

  • No formal, agreed definition of "speculative-execution security." Multiple competing security notions exist (speculative constant-time, non-interference variants); SPS only closes the gap for one such notion against one gadget class.
  • No tool proves a large real binary is gadget-free at scale. Static analyses (LightSLH, Spectector-family tools) find known shapes; none claims completeness against unknown or compiler-introduced gadget shapes.
  • Whether PHT can be fixed in hardware at all remains unresolved in public documentation. Every vendor statement found in this research treats v1 as software-mitigated-only, unlike v2 and Meltdown, which got microcode/hardware responses. dfence is a research proposal, not shipped silicon.
  • Coverage on non-Intel/AMD cores is thin in the literature. Comparatively little systematic characterization of Spectre-v1 on modern ARM client cores exists relative to x86 — an open measurement gap.
  • No public head-to-head benchmark of the newest targeted-hardening tools (LightSLH, dfence, SPS) against each other on the same codebase — each paper reports its own numbers against its own baseline.

Simulate the mistraining vote in 30 seconds

python3 spectre_sim.py models the saturating-counter predictor and the 2×+5 vote, sweeping the training ratio to show why 5:1 was chosen and what happens at 1:1 or 20:1.

spectre_sim.py (in this folder) models the saturating-counter predictor and the 2×+5 vote across rounds of 30 calls, without needing real clflush/rdtscp hardware access.

python3 spectre_sim.py
attack calls/round  success rate   avg rounds   speculation fired
1/30 (train 29)    100.0%           2.1      100.0% of attack calls
5/30 (train 25)    100.0%           1.1      100.0% of attack calls  <- paper's ratio
10/30 (train 20)    100.0%           1.0      100.0% of attack calls
15/30 (train 15)    100.0%           1.0      100.0% of attack calls
25/30 (train 5)    100.0%           3.2        6.7% of attack calls
29/30 (train 1)      0.0%         999.0        0.0% of attack calls
  • At the paper's own ratio (5 attack calls per 30), speculation fires on essentially every attack call, and the vote usually resolves within 1–2 rounds in this model.
  • Push past roughly 20 attack calls per 30 and the saturating counter can't recover toward "in bounds" between attacks — speculation mostly stops firing, and the attack can fail entirely even with all 999 rounds available.
  • This confirms the mechanism's core claim: mistraining isn't about sheer repetition, it's about keeping the predictor's short-memory counter saturated the moment the attack call runs.

For the real hardware experiment (needs a Spectre-vulnerable x86-64 Linux box), compile and run the paper's reference PoC from the official disclosure site, spectreattack.com, and watch readMemoryByte recover bytes of its own hardcoded secret string.

§14 · Question ladder

Test yourself

22 questions from mechanism to open research. Reveal, then mark ✓ or ✗; marks feed your progress ring.

Answer in your head first, then reveal and mark yourself honestly. Marks are saved in this browser and feed the progress ring.

Mechanism
1. What exactly happens to the CPU's registers and memory when the real bounds check resolves "false" after speculative execution already ran?

Every architectural register, memory write, and flag that the speculative path touched is rolled back exactly as if the mispredicted branch had never been taken — the CPU's ISA-visible state ends up bit-identical to the "correct" execution. What is not rolled back is anything in caches, TLBs, or the branch predictor's own tables, because those were never part of the architectural contract.

→ related card
2. Why does the attack flush array1_size before every training/attack call, specifically?

Flushing forces the size check's load to go to RAM (hundreds of cycles) instead of resolving from cache in a handful of cycles, widening the window during which the branch predictor's guess — not the real answer — is driving execution.

→ related card
3. Why does the probe read array2[i*stride] in shuffled order instead of i = 0..255?

A hardware stride prefetcher seeing sequential accesses would start speculatively loading ahead, warming lines the attack never touched and producing false "hit" timings. Shuffling the order breaks that pattern.

→ related card
4. What does "results[j] >= 2*results[k] + 5" actually test, in plain statistical terms?

A margin-of-victory test over noisy repeated samples: accept the leading candidate once its vote count beats the runner-up's by more than double plus a small constant, rather than trusting any single round's timing.

→ related card
5. Why is the leak serialized per byte rather than parallel across bytes within one victim call?

Each call's speculative detour reads exactly one array1[x] and touches exactly one line of array2 — there's no way to get two bytes of signal out of one call sequence.

→ related card
Why
6. Why can't the attacker just read array1[1000] directly and skip the second array?

The architectural read never "completes" from the program's point of view — once the real check resolves false, every result of that speculative read is discarded. The second array exists purely to convert that unreadable value into an observable cache-state change before rollback.

→ related card
7. Why does the mistraining loop use 5 good calls per 1 bad call instead of 1:1 or 10:1?

Branch predictors use short-memory saturating counters that need a consistent run of outcomes to lock a prediction and a comparably short run of opposite outcomes to flip it back; 5:1 keeps the counter saturated toward "in bounds" and was empirically sufficient.

→ related card
8. Why do browsers coarsen performance.now() instead of removing high-resolution timing entirely?

Removing it would break legitimate uses (animation, profiling, video sync); coarsening raises the attacker's required sample count without breaking those use cases — though raising cost isn't the same as closing the channel.

→ related card
9. Why did V8 choose "poisoning" over inserting a barrier on every branch?

Barriers on every branch cost 2–3× on V8's own Octane benchmark; poisoning (masking a misspeculated load's result instead of halting the pipeline) achieved under 20% cost.

→ related card
Counterfactual
10. What happens to the attack if speculative loads never affect the cache hierarchy?

The timing channel disappears entirely — there's no warm/cold distinction to measure. This is close to what hardware proposals like dfence aim for, though none is shipped silicon yet.

→ related card
11. What happens if array1_size were a compile-time constant instead of a runtime value?

The compiler can prove the bounds check always succeeds or statically bound x, eliminating the runtime branch the attack needs to mistrain — gadgets require a runtime-resolved check.

→ related card
12. If the attacker couldn't control the timing of training calls, only their values, would mistraining still work?

Yes — mistraining depends on the values passed across repeated calls, not fine-grained call timing; precise timing is needed for the later cache-probe step, not the training step.

→ related card
13. What would change if the second array's stride were 64 bytes (one cache line) instead of 512?

Every candidate index would still land on a distinct line, but with far less spatial margin — any prefetcher or alignment quirk affecting a neighboring line becomes more likely to raise false positives.

→ related card
Adversarial
14. How would you construct a Spectre v1 gadget in a language with no raw pointers, like JavaScript?

Shape a typed-array access so a JIT-emitted runtime bounds check and a dependent, secret-influenced load both exist in the compiled machine code — e.g. if (i < arr.length) leak(arr2[arr[i]]), mirroring the C gadget once JIT-compiled.

→ related card
15. Given SLH masks loaded values via an or-with-predicate, how might an attacker find a load SLH forgot to mask?

By auditing which loads SLH's analysis classifies as "safe to skip" (e.g. constant-stack-offset loads, which LLVM's SLH explicitly excludes as an optimization) and checking whether a secret-dependent value can reach one of those excluded sites.

→ related card
16. How did the 2018 Aleph Security bypass defeat SharedArrayBuffer removal and timer coarsening at once?

By repeating the timing measurement many times and statistically filtering the added jitter rather than relying on one precise sample, recovering a reliable ~1 bit/s signal without needing either removed feature.

→ related card
17. Why does targeted hardening (LightSLH-style) trade completeness for speed, and what's the attacker's best counter-move?

It only protects load sites its static analysis actually flags as reachable gadgets; the attacker's best move is finding a load the analysis under-approximates — an indirect call, a dynamically computed address, or a path its alias analysis misses.

→ related card
Connection
18. How does Spectre v1's cache-line leak relate to the 2025 finding of shared LLM-API prompt caches leaking prompts via timing?

Both are the same attack shape — timing a shared resource to infer whether someone else recently touched specific data — applied at different layers: CPU cache lines for Spectre, server-side KV-cache hits for the LLM-API case. Neither needs a CPU vulnerability, just a shared, timeable resource.

→ related card
19. How does speculative store bypass (the v1.1 sibling) differ mechanically from bounds-check bypass?

It mistrains the memory disambiguator rather than a branch predictor, exploiting a guess that a load doesn't depend on an earlier, not-yet-completed store to the same address, letting the load speculatively return a stale value.

→ related card
20. How does Flush+Reload relate to Prime+Probe, and when would an attacker need the latter?

Flush+Reload needs the ability to evict a specific shared line (clflush) and time a reload of it; Prime+Probe fills an entire cache set with attacker data and times a re-read instead, useful where clflush-equivalent instructions are restricted or unavailable.

→ related card
Open
21. Is there a hardware fix for Spectre-PHT that doesn't just move the cost to silicon, or is this permanently a software-patched problem?

Open. Every current vendor/compiler response treats v1 as software-mitigated-only; a 2026 hardware proposal (dfence) exists only as a research CPU, not shipped silicon.

→ related card
22. Can a static analysis ever be complete against all gadget shapes, including ones compilers introduce by accident?

Open. Targeted-hardening tools (LightSLH, SPS) are sound and complete relative to a defined gadget model, but that completeness is bounded by the model's assumptions about CPU behavior, not proven against future undocumented speculation.

→ related card

§15 · Go deeper next

Three dives that build on this

Spectre v2 (branch target injection) · Meltdown (breaking the privilege check itself) · speculative constant-time verification.

  1. Spectre v2 (branch target injection): mistraining the indirect branch predictor (BTB) instead of a conditional-branch predictor — the variant that did get hardware mitigations (IBRS/IBPB).
  2. Meltdown: the sibling 2018 disclosure that breaks the privilege check itself, letting speculative execution read kernel memory directly; got a different mitigation path (KPTI) than Spectre.
  3. Speculative constant-time verification tooling (Spectector-family, SPS): the formal-methods line of work trying to make "is this code Spectre-safe" a decidable, checkable property instead of a case-by-case audit.
